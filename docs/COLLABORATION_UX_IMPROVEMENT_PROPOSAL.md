# 사람-AI Agent 협업 철학·UI·프로세스 개선 제안 — 외부 사례 기반

사용자 요청(2026-10-08): "Agent-Human 협업 관련으로 오픈소스, 상용서비스
등을 외부 검색하여 현재 HAIR-Platform의 철학/개념/원칙 및 UI, Process에
대해 개선 방안을 제안해줘. (현재 UI와 프로세스, 제공되는 정보 및 기능으로는
실사용에 너무 많이 부족해)"

`docs/ROLE_TASK_CLASSIFICATION.md`(2026-09-29, 관리자/사용자 권한 분리
리서치)와 같은 성격의 문서다 — **기획 문서, 코드 변경 없음**. 오픈소스
프레임워크 5곳·상용 서비스 6곳을 리서치하고, 이 세션에서 시나리오를
라이브로 7번 반복 실행하며 직접 겪은 실측 갭(`docs/LIMITS.md` §41·
§63·§70·§71·§73, `docs/MULTI_PARTY_TEAM_COLLABORATION_PLAN.md` §5
Phase 4 등)과 대조해 제안을 만든다. 어떤 항목을 실제로 구현할지는
사용자 결정 후 별도 진행한다.

## 1. 외부 사례 리서치

### 1-1. 오픈소스 프레임워크

**LangGraph(LangChain)** — `interrupt()`로 그래프 실행을 **노드
단위로 즉시 정지**시키고 `Command(resume=...)`로 재개한다. 용도가
승인/반려뿐 아니라 **사람이 Agent의 진행 중 상태를 직접 고쳐 쓰는
것**(edit state), 개별 도구 호출 하나하나를 검토하는 것까지 포함한다
— "끝난 결과물만 본다"가 아니라 "진행 중에 개입한다"는 철학이다.

**AutoGen/AG2(Microsoft)** — `UserProxyAgent`가 멀티에이전트 대화에
**사람을 정식 참가자로 앉힌다**(기본값: 매 턴 사람 입력 대기). "AI가
제출하고 사람이 결재한다"가 아니라 "사람과 AI가 같은 대화에 함께
있다"는, 페어 프로그래밍에 가까운 철학.

**CrewAI(HAIR가 이미 쓰는 프레임워크 그 자체)** — `human_input=True`
Task 플래그(마무리 전에 Agent가 사람에게 확인 질문)와 최근 추가된
**Execution Hooks**("before LLM call" 훅으로 승인 게이트 구현 가능)를
이미 제공한다. **HAIR는 둘 다 안 쓴다** — `run_crew()`는 `kickoff()`
전체를 감쌀 뿐, 그 안의 개별 LLM 호출/도구 호출 단위로 멈출 지점이
없다. CrewAI 공식 문서 자체가 "`human_input`은 보안/정책 게이트가
아니다 — 진짜 승인이 필요하면 Task가 아니라 **도구(tool)**를
감싸라"고 명시한다.

**HumanLayer** — `@hl.require_approval()` 데코레이터를 **함수(=도구)
단위**로 건다. 승인 요청이 Slack/이메일로 가고, 누가/언제/무엇을
승인했는지가 "컴플라이언스 아티팩트"로 못박힌다. 라우팅은 조직도가
아니라 **그 함수를 처리할 자격이 있는 사람/팀**으로 간다.

**OpenDevin/SWE-agent 계열 연구 도구(SeaView, AgentStepper, IBM Agent
Trajectory Explorer)** — 전부 "Agent가 **왜** 이 결과를 냈는지"를
보여주는 게 핵심 과제라고 본다. 추론+도구 호출을 구조화된 대화로
펼쳐 보여주고, 중간 지점에 브레이크포인트를 걸고, 프롬프트를 그
자리에서 고쳐 재시도하게 한다. "최종 점수 하나"가 아니라 "과정 전체"가
검토 대상이다.

### 1-2. 상용 서비스

**Microsoft Copilot Studio** — 가장 바로 옮겨올 수 있는 패턴:
**도구 단위 승인 토글**. 제작자가 "이메일 발송", "결제 처리" 같은
특정 도구를 "승인 필요"로 표시해두면, Agent가 그 도구를 쓰려는 순간
**실행이 멈추고** "무엇을 하려는지"를 평이한 말로 보여준 뒤 승인/
세션 동안 승인/거부를 받는다 — **실행 전**이지 사후가 아니다.

**ServiceNow AI Agents** — 신뢰도가 낮은 출력은 자동으로 사람에게
라우팅되고, 사람은 끝난 뒤가 아니라 **진행 중에** 검토·지도·override
할 수 있다. 업계 전반이 "오케스트레이션 거버넌스(감사 추적+권한
스코프+HITL 통제)가 모델 성능 자체보다 더 중요한 구매 기준"으로
이동했다고 본다.

**UiPath Agentic Automation** — 예외를 이진 pass/fail로 안 다루고
Agent가 먼저 분류·해결을 시도한 뒤, 정말 애매한 것만 전체 맥락(건
ID·로그·스크린샷)과 함께 사람에게 넘긴다. 사람이 고치면 Agent가
**처음부터 다시가 아니라 그 지점에서 재개**한다.

**Sierra** — 가드레일을 프롬프트에 암묵적으로 묻지 않고 SDK로
**명시적으로 선언**("30일 이내 환불만 처리" 등)해, 비개발자도 "이
Agent가 뭘 하고 안 하는지"를 사전에 감사할 수 있게 한다. 신뢰를
사후 점수가 아니라 "확인 가능한 한계"로 판다.

**Asana AI Studio / monday.com** — HAIR와 구조가 가장 비슷한
사례(업무 도구에 Agent를 얹은 것). 승인이 "별도 결재 화면"이 아니라
**기존 업무 단계 안에 끼워진 체크포인트**다. 고위험 행동(외부
메일 발송 등)만 승인을 요구하고, 저위험은 그냥 진행한다 — **위험도
차등**이 기본값이다.

### 1-3. 공통 패턴(HAIR에 없는 것 4가지)

1. **실행 전/중 개입** — 전부 "다 끝난 뒤 검토"가 아니라 위험한
   단계 **직전**에 멈춘다.
2. **위험도 차등 승인** — 모든 산출물을 똑같이 승인받지 않고, 위험한
   행동만 게이트를 건다.
3. **과정 가시성** — 최종 점수 하나가 아니라 "무엇을 근거로/어떻게"
   도달했는지를 보여준다.
4. **제자리 재개** — 사람이 고치면 처음부터 다시가 아니라 그 지점에서
   이어간다.

## 2. HAIR 현재 설계와의 대조(실제 코드 기준)

| 축 | 외부 공통 패턴 | HAIR 현재 |
|---|---|---|
| 개입 시점 | 실행 전/중(도구 호출 단위) | **사후뿐** — `deliverables.run_agent_execution_job()`/`run_team_crew_job()`은 `kickoff()`/LLM 호출이 전부 끝난 뒤에야 결과를 만든다. 멈출 지점 자체가 없다(Phase C로 스코프 밖 처리됨, §25) |
| 승인 차등 | 위험도 기반 게이트 | **없음** — `approvals.create_approval_chain()`은 Gate 점수와 무관하게 매번 똑같은 체인을 만든다. Gate A-G 전부 pass여도 승인 절차는 똑같다 |
| 승인 라우팅 | 자격/위험 기반(조직도와 분리) | **조직도 전용** — `build_manager_chain(conn, requested_by)` 하나뿐(`approvals.py:40`). `auth.py`가 스스로 "manager_id(직속상사)와 RBAC role은 별개 개념"이라고 원칙을 적어두고도, 승인 라우팅은 여전히 manager_id 하나로만 묶여 있다 — **이미 세운 원칙을 실제로는 완성 못 한 상태** |
| 과정 가시성 | 근거/추론 과정 노출 | **VectorDB 그라운딩 1건만**(`retrieved_context`, §41) — 나머지 전부(시나리오 1·2·3·5·6·7)는 프롬프트→결과만 있고 "왜"가 안 보인다. CrewAI 위임(delegation) 이벤트는 이미 캡처되는데(`crew_runtime.py`) UI엔 전혀 노출 안 됨 — 시나리오 7에서 한 Agent가 "다른 Agent에게 요청했다"고만 쓰고 끝났을 때, 실제로 위임이 일어났는지조차 화면에서 확인할 길이 없었다 |
| 비용 사전 고지 | 예상 비용/리스크 사전 노출 | **경고 문구뿐** — `webui.py`의 모든 실행 버튼이 "(비용 발생)"이라고만 쓰고 실제 예상 금액은 안 보여준다(`webui.py:947,994,1017` 등) |
| 작업 간 연결 | 관련 작업 참조/링크 가능 | **완전 격리** — 같은 브리프의 다른 Task끼리도 전혀 연결이 안 된다(§63 "갭 2", 이번 세션 시나리오 1·3에서도 반복 확인) |

## 3. 철학/원칙 수준 제안

**(A) "직원-매니저" 은유를 넘어선다.** HAIR는 지금 "Agent가 결과물을
제출하면 매니저가 승인한다"는 단일 은유로 설계돼 있다. 이건 AutoGen의
"AI는 대화의 동료"나 LangGraph의 "AI는 중간에 멈춰서 사람과 함께
일하는 과정"과 다른 선택이다 — 틀린 게 아니라, **의도적으로 재확인할
가치가 있는 선택**이다. 제안: 이 은유를 유지하되, "제출 전 확인이
필요한 위험한 단계"만큼은 LangGraph식 `interrupt()`를 부분적으로
들여와 "사후 승인"과 "사전 게이트"를 **공존**시킨다(아래 4-A).

**(B) 신뢰는 점수가 아니라 투명성에서 온다.** Gate A-G는 훌륭한
인프라지만 "0.85 pass"라는 숫자 자체가 신뢰를 만들진 않는다(Sierra·
IBM·UiPath 사례가 공통으로 보여주는 것). 제안: Gate 점수 옆에 "근거
보기"(프롬프트·CrewAI 위임 로그·참고 자료)를 상시 노출해, 승인자가
숫자가 아니라 과정을 보고 판단하게 한다(아래 4-C).

**(C) 조직도와 승인 권한을 실제로 분리한다.** `auth.py`가 이미 적어둔
"manager_id와 RBAC role은 별개"라는 원칙을 승인 라우팅에도 끝까지
적용한다 — Task/Team 단위로 "이 업무는 조직도 대신 이 사람(들)이
승인"을 지정할 수 있게 한다(아래 4-B).

## 4. 구체적 UI/Process 개선 제안

우선순위는 "구현 비용 대비 체감 효과"로 매겼다 — ★★★이 가장 싸고
효과가 큰 것.

### ★★★ (A) CrewAI 위임·중간 과정 노출 (당장 가능 — 이미 캡처된 데이터)

`crew_runtime.py`가 CrewAI 이벤트버스에서 위임 발동 여부를 이미
캡처하고 있다(코드 주석에 명시, "추측 아님"). 그런데 그 정보가 DB에
저장도 안 되고 화면에도 안 보인다. 시나리오 7에서 "AI 연동 로직
개발자에게 요청한..."이라고만 쓰고 끝난 Agent가 실제로 위임했는지,
아니면 그냥 핑계만 댄 건지 **지금은 아무도 알 수 없다.** `agent_
execution_jobs`에 위임 이벤트 로그 컬럼을 추가하고, 협업 워크스페이스에
"실행 과정 보기"(접이식, §41의 "참고한 근거" 블록과 같은 패턴)로
노출한다.

### ★★★ (B) Gate 통과 시 자동 승인 옵션 (당장 가능 — 승인 체인 로직만 변경)

Task 또는 Team 단위로 "Gate A-G 전부 pass면 자동 승인"을 옵션으로
켤 수 있게 한다. 위험도 차등 승인(외부 사례 공통 패턴)의 가장 싼
버전이다 — `approvals.create_approval_chain()` 호출 직전에 Gate
점수를 확인해, 전부 pass면 체인 생성 자체를 건너뛰고 바로
`approved`로 만드는 분기만 추가하면 된다.

### ★★☆ (C) 예상 비용 사전 고지 (모델 레지스트리 확장 필요)

`model_registry`에 "1회 호출 예상 비용"(또는 토큰당 단가) 필드를
추가하고, 실행 버튼의 `confirm()` 문구를 "비용 발생" → "예상 비용:
약 $0.02"처럼 구체화한다. 로컬 Ollama는 "$0(로컬 실행, 시간 소요
가능)"로 표시해 시나리오 7에서 겪은 "로컬 모델은 느리다"는 트레이드
오프도 미리 알려준다.

### ★★☆ (D) Task별 승인자 지정(조직도 override)

Task/Team 생성 시 "이 업무의 승인자"를 명시적으로 지정하는 선택
필드를 추가한다(기본값은 기존 `build_manager_chain()` 유지 — 하위
호환). §63에서 반복 발견된 "결재자가 그 Task의 참가자가 아니다"
문제의 근본 해결책이다(지금은 "사유" 필드로 증상만 완화한 상태,
GC235-236).

### ★☆☆ (E) 도구 호출 단위 사전 승인(MCP 도구 한정)

전체 범위는 크지만, `mcp_stdio`/`mcp_remote`(실행 시 실제 외부
네트워크에 접속하는 유일한 위험 지점, `docs/ROLE_TASK_CLASSIFICATION.md`
갭 1에서 이미 admin 전용 등록으로 1차 조치됨)로 범위를 좁히면
현실적이다. 이 두 종류의 도구를 가진 Agent를 실행하기 전에만
Copilot Studio식 "이 Agent가 이런 외부 서버에 접속하려 합니다" 확인
모달을 추가한다.

### ★☆☆ (F) Task 간 참조 링크

같은 브리프 안에서 "이 Task는 저 Task를 참고"라는 관계를 추가해,
참고하는 쪽에 최소 읽기 권한을 준다. §63 "갭 2"(QA 담당자가 백엔드
개발 Task에 맥락을 못 남김)의 근본 해결책 — 지금까지는 "다중
confirmed 배정"으로 매번 우회해왔다.

### (G) 이미 알려진 것 — N:M 워크스페이스 UI

`MULTI_PARTY_TEAM_COLLABORATION_PLAN.md` §5 Phase 4(승인된 산출물이
여러 건이어도 "최종 결과물" 카드는 1건만 고정)는 이미 자체적으로
인지된 갭이다 — 외부 사례(Asana의 서브태스크 나란히 보기)와 비교해도
우선순위가 여전히 유효함을 재확인한다.

## 5. 이번 세션 실측과의 연결(근거)

이 제안들은 추상적 벤치마킹이 아니라, 같은 세션에서 시나리오 1-7을
라이브로 반복 실행하며 **직접 부딪힌** 문제들이다:

- §41(Tool/Skill 그라운딩 근거가 사라짐) → 4-A의 확장판
- §63 "갭 2"(Task 간 완전 격리) → 4-F
- GC235-236(결재자가 참가자가 아니어서 댓글 불가) → 4-D
- §71·§73(팀 Crew의 두 Agent가 완전히 같거나, 한쪽이 위임만 하고
  끝남) → 4-A가 없으면 **이런 상황 자체를 사람이 알아챌 방법이 없다**
- §73(로컬 Ollama 실행이 6분 걸림, 사전 고지 없음) → 4-C
- 바로 전 턴(스킬/툴 미등록이 조용히 무효화됨, UI에 경고 없음) →
  이것도 "과정 불투명성"의 또 다른 사례 — 4-A/4-C와 같은 뿌리

## 6. 다음 액션 제안(열린 질문)

이 문서는 리서치·제안까지다. 실제로 진행하려면 아래를 확인해야 한다:

1. **범위**: 4-A~4-G 중 어디까지, 어떤 순서로 진행할지(★★★부터
   권장하지만 최종 판단은 사용자 몫).
2. **철학 재확인(3-A)**: "사후 승인" 중심을 유지하면서 위험한 지점만
   "사전 게이트"를 더하는 **혼합 모델**로 갈지, 아니면 이번 기회에
   HAIR의 정체성 자체를 재정의할지.
3. **승인 라우팅(4-D)**: 조직도 기반을 기본값으로 유지하고 override만
   추가할지, 아니면 아예 다른 축(risk-tier 등)으로 재설계할지.

이 중 진행할 항목을 알려주면 각각 별도로 구현한다.
