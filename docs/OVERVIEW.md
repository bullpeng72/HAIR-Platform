# HAIR-Platform 개요

> 처음 읽는다면 이 문서 전체를 다 외울 필요는 없습니다. 1절만 읽고
> 바로 실제 화면에서 시작하고 싶다면 로그인 후 **"이용 가이드"** 탭을,
> 설치부터 하고 싶다면 저장소 루트의 `README.md`를 먼저 보세요. 이
> 문서는 "왜 이렇게 만들었는지"와 "전체적으로 뭘 할 수 있는지"를
> 한 번에 정리해주는 자료입니다.

## 1. 한 줄로 말하면

HAIR(Human-AI Resource Management)는 **사람과 AI Agent를 같은
조직도 위에 올려놓고, 같은 방식으로 일을 배분·승인·실행·평가하는
협업 플랫폼**입니다.

"AI Agent 자체를 어떻게 잘 만드는가"는 이 프로젝트가 다루는 문제가
아닙니다(그건 자매 프로젝트인 AgentForge의 영역입니다). HAIR가
다루는 문제는 **이미 만들어진 사람과 AI Agent를, 회사 조직처럼
배치하고 업무를 맡기고 결과를 확인하는 절차를 어떻게 통일하는가**
입니다.

이 플랫폼을 이해하는 데 필요한 전제는 딱 3가지뿐입니다.

### 전제 1 — 사람과 Agent는 "같은 조직도" 위에 있습니다

조직도에 배치하고, 업무를 배분하고, 결재를 받고, 팀을 구성하는
절차는 사람이든 AI Agent든 **완전히 똑같은 화면·같은 흐름**을
탑니다. 예를 들어 "이 업무, 김 과장한테 맡길까 AI한테 맡길까"를
고민할 때 서로 다른 화면을 오갈 필요가 없습니다 — 같은 배정 화면에서
둘 다 후보로 뜹니다.

(단, Agent를 처음 "만드는" 화면과 사람을 "등록하는" 화면은 당연히
따로 있습니다. 태어나는 방식이 다르니까요. 통일된 건 **일단 조직에
들어온 뒤**의 절차입니다.)

### 전제 2 — AI가 혼자 결정하는 일은 없습니다 (HITL)

AI Agent가 뭔가를 만들어내도, 그게 회사의 "확정된 결과"로 인정받기
전에는 반드시 사람의 결재를 거칩니다. 이렇게 "사람이 중간에서 한 번
확인하고 지나간다"는 원칙을 줄여서 **HITL**(Human-In-the-Loop)이라고
부릅니다 — 이 플랫폼 전체에 깔린 가장 중요한 안전장치입니다.

예외가 하나 있는데, 반복적으로 자동 진행되는 단계(파이프라인)는
"정해둔 기준을 통과하면 그 자체를 승인으로 본다"는 규칙으로
사람 개입을 줄여줍니다 — 그래도 기준을 못 넘기면 결국 사람에게
돌아옵니다. "완전 무인 운영"은 어디에도 없습니다.

### 전제 3 — "잘했다"는 느낌이 아니라 숫자로 남습니다

AI Agent가 만든 모든 결과물은 7가지 기준(**Gate A~G**)으로 자동
채점됩니다. 사람이 "음, 괜찮아 보이네" 하고 넘기는 게 아니라, 매번
같은 잣대로 측정된 숫자가 기록에 남습니다. Gate가 정확히 뭘 보는지는
2절에서 설명합니다.

## 2. 핵심 개념 — 이 플랫폼의 언어

### Pool — "한 번 등록하면 계속 재사용"

사람(Human Pool)·AI Agent(Agent Pool)·외부 도구(Tool Pool)·역량
태그(Skill Pool)·LLM 모델(Model Registry)·역할 그룹(Team) — 이
여섯 가지는 전부 같은 패턴을 따릅니다. **한 번 등록해두면, 그 뒤로는
여러 업무에서 드롭다운으로 골라 쓰기만 하면 됩니다.**

예를 들어 "백엔드 개발"이라는 역량 태그를 Skill Pool에 등록해두면,
그 태그를 가진 사람이나 Agent에게 관련 도구가 **자동으로** 붙습니다 —
매번 수동으로 연결해줄 필요가 없습니다.

### 배치 → 배분 → 승인 — 업무를 맡기는 기본 절차

업무(Task)에 사람이나 Agent를 연결하는 절차는 기본적으로 2단계입니다.

1. **배정 요청** — 누구나 "이 후보가 이 업무를 맡으면 좋겠다"고
   제안합니다(아직 확정 아님, `requested` 상태).
2. **다단계 결재** — 조직도의 상사 체인을 따라 승인을 받으면
   **확정**(`confirmed`)됩니다.

몇 가지 세부 규칙이 있습니다.

- **자기 자신이 요청한 걸 자기가 승인할 수는 없습니다**(자기 승인
  방지) — 다만 **본인 스스로를 배정하는 경우**(예: "나 이거 할게")는
  예외입니다. 본인 시간만 쓰는 일이라 "남의 자원을 함부로 못 쓰게
  막는다"는 결재의 목적 자체가 성립하지 않으므로, 결재를 거치지
  않고 그 자리에서 바로 확정됩니다.
- **한 업무에 여러 명이 동시에 배정될 수 있습니다** — 사람 여러
  명 + Agent 여러 개가 같이 투입되는 구조가 기본값입니다.
- **후보 추천은 자동입니다** — 역할 이름이 비슷한 후보 중 필요한
  스킬을 전부 가진 후보가 있으면 그것부터 추천합니다. 그런 후보가
  없으면 가용성·실적·비용을 가중치로 점수 매겨 상위 3명을
  보여줍니다(실적이 아직 없는 신규 인력/Agent는 가용성·비용만으로
  점수를 매깁니다). 그래도 후보가 전혀 안 보이면 "AI로 추천 받기"
  버튼으로 LLM에게 전체 인력/Agent 풀에서 의미상 맞는 후보를
  찾아달라고 요청할 수 있습니다(버튼을 눌러야만 호출되고, 이때는
  비용이 발생합니다).

### 위임 — Agent 전용 "가벼운 배정"

결재를 기다릴 필요 없이 Agent를 바로 업무에 연결하는 방법입니다.
위임은 즉시 확정 상태가 되지만, 누가 언제 위임했는지는 감사
기록에 그대로 남습니다 — "가볍게 연결했다"는 "결과물 품질을
안 본다"는 뜻이 아닙니다. 위임으로 만들어진 결과물도 일반 배정과
똑같이 Gate A-G 채점과 결재를 거칩니다.

### 결과물(Deliverable)과 Gate A-G — 품질을 숫자로 보는 법

업무의 결과물은 사람이 쓰든 Agent가 만들든 같은 곳에 쌓이고, 같은
방식으로 결재됩니다. 텍스트/마크다운/HTML/코드 중 형식을 지정할 수
있고, 화면은 그 형식에 맞게 보여줍니다(마크다운 서식, 코드 문법
강조, HTML 미리보기 전부 지원).

**Gate A-G**는 결과물을 7개 관점에서 자동으로 측정하는 기준입니다.

| Gate | 보는 것 |
|------|---------|
| A | 목표 달성 — 원래 시킨 일을 실제로 해냈는가 |
| B | 행동 무결성 — 하라고 한 것만 하고 엉뚱한 일을 벌이지 않았는가 |
| C | 신뢰성 — 같은 조건이면 비슷한 결과가 나오는가, 사실을 지어내지 않았는가 |
| D | 성능 계약 — 정해둔 시간·자원 안에서 끝났는가 |
| E | 보안 경계 — 하면 안 되는 접근/행동을 하지 않았는가 |
| F | 다중 에이전트 협업 — 여러 Agent가 같이 일할 때 역할을 지키고 충돌 없이 협력했는가 |
| G | 관측성 — 무슨 일이 있었는지 나중에 확인할 수 있게 기록을 남겼는가 |

Agent가 만든 결과물은 생성 즉시 이 7개 기준으로 채점되고, 결재
체인도 자동으로 걸립니다. 사람이 직접 쓴 결과물은 초안 상태로
있다가 본인이 "검토 요청"을 눌러야 같은 결재 절차에 들어갑니다 —
Agent 경로와 대칭이지만 자동으로 시작되지는 않습니다.

### 협업 워크스페이스 vs 대화 — 무겁게 할지, 가볍게 할지

업무 하나에는 두 가지 작업 공간이 붙을 수 있습니다.

- **협업 워크스페이스** — 결과물 타임라인·댓글·배정·결재가 다
  모이는 "정식" 화면입니다. 결재·Gate 채점이 필요한 진짜 업무는
  여기서 처리합니다.
- **대화** — `@멘션`으로 특정 Agent/Team을 불러 그 자리에서 즉시
  실행시키는 가벼운 채팅입니다. 업무에 종속될 수도 있고(그 업무
  전용 대화), 업무와 무관한 완전히 독립된 대화로 시작할 수도
  있습니다(로그인 직후 바로 쓸 수 있는 자유 대화).

**대화와 업무 요청(Brief)은 서로 독립된 두 트랙입니다.** 대화를
나누다가 "이건 정식으로 결재까지 받아야겠다" 싶으면, 내용을 복사해
업무 요청 작성란에 직접 옮겨 적어야 합니다 — 대화가 알아서 정식
업무로 바뀌는 자동 전환 기능은 없습니다. (예외적으로, 아직 업무에
연결되지 않은 대화에서 메시지를 "결과물로 저장"하면 그 내용을 담을
최소한의 업무 틀이 뒤에서 자동으로 하나 생기긴 합니다 — 이건
"대화를 정식 업무로 승격시켜주는 기능"이 아니라, 저장할 그릇이
없을 때 빈 그릇을 하나 마련해주는 보조 장치입니다.)

### 여러 Agent가 함께 일하기 (CrewAI)

여러 Agent를 하나의 팀(Crew)으로 묶어 실제로 협업시킬 수 있습니다.
두 가지 방식이 있습니다.

- **순차(sequential)** — 앞 Agent의 결과물이 다음 Agent에게
  자동으로 전달됩니다(릴레이 방식).
- **위임형(hierarchical)** — 매니저 역할의 Agent가 나머지 팀원에게
  작업을 쪼개 맡깁니다.

누가 누구에게 어떤 작업을 넘겼는지는 추측하지 않고 실제로 일어난
이벤트를 그대로 캡처해 협업 관계도(다이어그램)로 보여줍니다. 같은
업무를 재실행한 적이 있다면 바로 이전 실행과 최종 결과물을 줄 단위로
비교(추가된 부분은 초록, 삭제된 부분은 빨강)할 수도 있습니다 — 재시도
할 때마다 전에 되던 기능이 조용히 사라지는 걸("두더지 잡기" 퇴행)
사람이 한눈에 알아챌 수 있게 하는 장치입니다.

### 자동 재시도와 에스컬레이션 — 언제 사람을 부르는가

Gate 기준에 못 미치면 자동으로 재시도합니다. **마지막으로 자동
재시도하는 순서에서는** Agent가 자기 초안을 원래 요구사항과 한 줄씩
대조해 스스로 고치는 "자가검토" 모드가 자동으로 켜집니다 — 일반
재시도와 사람 에스컬레이션 사이의 한 단계 더 꼼꼼한 중간 단계입니다.
이렇게까지 해도 기준을 못 넘기면, 그때 비로소 사람에게 결재 요청이
올라갑니다 — 그리고 승인 권한이 있는 사람이 그 대화에 아직 없다면
시스템이 자동으로 초대해, 실제로 알림을 받게 합니다.

업무 전체에는 선택적으로 **재시도 예산**을 걸 수 있습니다(admin/
manager 전용) — 파이프라인 재시도 수와 Crew 재실행 수를 합쳐서
상한을 넘기면, 그 단계 자체의 재시도 기회가 남아 있어도 즉시
사람에게 넘깁니다. 같은 업무를 반복 재시도하며 비용만 계속 쓰는
걸 막는 안전장치이고, 설정하지 않으면(기본값) 아무 제한도 걸리지
않습니다.

## 3. 어떻게 만들어져 있나 (조금 더 기술적인 내용)

여기부터는 "왜 이렇게 동작하는지"가 궁금한 분을 위한 내용입니다 —
실제로 이 플랫폼을 쓰는 데는 꼭 필요하지 않습니다.

### Agent를 "만든다"는 것의 3단계

Agent를 만들 때 실제로 고르는 건 세 가지 중 하나입니다 — 아래로
갈수록 더 똑똑해지지만 비용도 올라가고, **명시적으로 선택해야만**
비용이 발생하는 단계로 올라갑니다(기본값은 항상 무료입니다).

| 단계 | 방식 | 비용 |
|---|---|---|
| 스텁(stub) | 규칙 기반 — 실제 LLM 호출 없음 | 무료, 기본값 |
| 1회성 LLM | Anthropic/OpenAI/Ollama 중 하나를 한 번 호출 | 명시적으로 켜야 발생 |
| CrewAI | 실제 CrewAI Agent — 도구 호출·위임 가능 | 명시적으로 켜야 발생 |

### 데이터는 어디에 저장되나

SQLite 데이터베이스 하나에 전부 저장됩니다(WAL 모드 — 여러 읽기가
동시에 가능). 누가 언제 뭘 바꿨는지 남기는 감사 기록(audit log)은
한 번 쓰면 수정도 삭제도 불가능하게 막아둬서, 나중에 조작될 걱정이
없습니다.

### 화면(Web UI)

별도 설치나 빌드 과정 없이, 서버에 접속하면 바로 전체 화면이
뜨는 단일 페이지 앱입니다. 로그인 후 역할(`admin`/`manager`/
`member`/`viewer`)에 따라 보이는 메뉴와 할 수 있는 동작이
달라집니다(아래 "권한" 참고). 같은 브라우저에서 여러 탭을 열어
서로 다른 계정으로 동시에 로그인해둘 수도 있습니다.

**권한(RBAC)** — "이 역할은 이 화면에서 이것만 할 수 있다"는 규칙은
문서로 따로 관리하지 않고, 서버 코드 자체에 있는 권한 검사 하나로만
정해집니다 — 문서와 실제 동작이 서로 어긋날 가능성을 원천적으로
없애는 선택입니다. 이 권한 규칙이 실제로 지켜지는지는 "역할별로
허용돼야 할 동작/막혀야 할 동작"을 자동 테스트로 반복 확인합니다.

### 명령어(CLI)

`hair`라는 명령어 하나로 전부 처리합니다.

- `hair serve` — 서버 실행
- `hair bootstrap-admin` — 맨 처음 관리자 계정 만들기
- `hair reset-data` — 운영 중 쌓인 데이터만 공장 초기화(Agent/Tool/
  Skill/파이프라인 템플릿은 그대로 둠)
- `hair eval` — Gate 기준을 수동으로 측정

자세한 옵션은 `hair --version`, `hair <명령어> --help`로 확인할 수
있습니다.

## 4. 지금 쓸 수 있는 기능들

아래 전부 실제로 동작하는 코드로 구현돼 있습니다(스텁이나 겉보기
목업이 아닙니다) — 테스트 924건 통과, API 175개, 화면(탭) 27개,
기본 제공 파이프라인 템플릿 4개가 지금 기준 실측값입니다.

### 사람-Agent 통합 조직도
배치·배분(앞서 설명한 자동 매칭 알고리즘)·승인·팀 단위 그룹 등록과
실행을 한 화면 흐름에서 처리합니다.

### Agent 생성과 실행
Job Queue + 샌드박스(Docker)로 신규 Agent를 만들고, 필요할 때마다
비동기로 실행합니다(상태는 폴링으로 확인). 모든 실행에 Gate A-G가
자동으로 붙고, CrewAI로 여러 Agent를 묶어 실제 협업시킬 수 있습니다.

### 도구·스킬·모델 등록
기본으로 제공되는 도구:

- **지식검색**(VectorDB) — 과거에 저장해둔 결과물을 찾아봅니다.
- **관계조회**(GraphDB) — 조직 내 관계를 질의합니다.
- **일반 웹검색**(Parallel AI) — CrewAI 실행 중에만 동작합니다.
- **실시간 웹검색**(Tavily, API 키 필요) — 대화창과 Crew 실행 양쪽
  모두에서 동작합니다.

이 외에도 MCP 표준으로 외부 도구를 추가 연결할 수 있습니다. 기본
등록된 Skill Pool은 51개(그중 18개는 "방법론 절차" 전용), Tool
Pool은 12개입니다. 각 스킬은 "개발업무"/"일반업무"로 분류돼 있어,
대화창의 스킬 선택 드롭다운은 평소엔 일반업무만 보여주고 "개발업무
스킬도 보기"를 켜야 개발업무 스킬이 보입니다(실제 Agent 실행·배정
자체에는 이 숨김이 적용되지 않습니다 — 화면 표시만 걸러줍니다).

파일 업로드(.md/.pdf/.html)는 대화창·협업 워크스페이스·지식 베이스
세 곳 모두에서 할 수 있지만, **영구히 저장돼 나중에도 검색되는 건
"지식 베이스"에 올린 것뿐**입니다. 대화창·협업 워크스페이스에서
올리는 파일은 그 순간 1회 응답에만 참고되고 저장되지 않습니다
("지식 베이스" 관리 화면에서 색인된 내용과 조직 관계 데이터를
조회·삭제·통계까지 관리합니다).

### 기본 제공 레퍼런스 Agent — 26개
바로 쓸 수 있도록 미리 등록해둔 Agent들입니다. 업무 영역별로 묶어서
소개하면:

- **소프트웨어 개발**(6개) — 요구사항 분석가·스펙 작성자·코드베이스
  분석가·백엔드 개발자·코드 검증가·QA 기능테스터
- **경영/사업전략**(6개) — 외부 자료 조사가·3C4P SWOT 분석가·기획서
  작성자·사업전략 수립가·C-level 보고서 작성자·프레젠테이션 자료
  작성자
- **기획→개발 실행팀**(7개) — PM·AA/DA 아키텍트·개발 계획 수립가·
  UI 기획자·테스트 계획 수립가·품질 관리자
- **"자율 개발 크루"**(4명 — 그중 백엔드 개발자는 위 소프트웨어
  개발 6종과 같은 Agent를 그대로 재사용, 나머지 프론트엔드/데이터·
  인프라/풀스택 개발자 3명이 신규) — 실행팀이 매니저 1명을 세워
  이 4명에게 모듈을 나눠 위임하는 구조입니다.
- 그 외 **콘텐츠 카피라이팅**(1개), **데이터 분석가·제안서 작성자·
  실적 보고서 작성자**(3개)가 각각 전용 파이프라인의 특정 단계를
  위해 추가돼 있습니다.

> 참고: "자율 개발 크루"라는 **이름의 팀**은 기본으로 만들어져 있지
> 않습니다 — "팀 관리" 화면에서 정확히 이 이름으로 직접 만들어야
> 합니다(만들면 파이프라인 연결과 멤버 구성이 자동으로 채워집니다).
> Agent 자체는 이미 등록돼 있으니 팀만 새로 구성하면 됩니다.

### 단계형 파이프라인 엔진
"단독 실행"·"순서대로 이어받기"·"매니저가 나눠 위임하기" 3가지
방식으로 업무 단계를 구성하는 범용 엔진입니다. 각 단계는 Gate
기준으로 자동 채점되고, 기준 미달이면 피드백을 반영해 자동
재시도하다가 반복 실패해야만 사람에게 올라갑니다(계획 단계에서
한 번만 사람이 승인하면 그 뒤로는 최소한의 사람 개입으로 진행됩니다).

화면에서 직접 단계를 구성하는 빌더가 있어, 소프트웨어 개발이 아닌
업무(시장조사·전략 등)에도 같은 엔진을 그대로 재사용할 수 있습니다.
업무를 등록할 때 LLM에게 "이 업무를 어떤 역할들로 나누면 좋을지"
제안을 받아 한 번에 여러 할 일을 만들 수도 있습니다(선행 업무
관계까지 함께 제안됩니다).

기본으로 제공되는 파이프라인 템플릿은 4개입니다.

1. **소프트웨어 개발 파이프라인** — 요구분석 → 설계 → 개발 계획 →
   구현 → 코드 검증 → QA → 품질 관리, 7단계.
2. **사업/기획 업무 처리 파이프라인** — 같은 엔진을 경영·기획
   업무에 적용한 버전. 자료 조사부터 최종 승인까지 7단계.
3. **제안서 작성 파이프라인** — 2번에서 "제안서 하나만 필요한
   경우"를 위해 분리해낸 버전(발주처 평가 대응을 위한 "표현 검토"
   단계를 그대로 유지).
4. **실적 보고 파이프라인** — 2번에서 "정기 실적 보고서"를 위해
   분리해낸, 더 가벼운 버전.

### 콘텐츠 형식별 자동 검증
Gate A-G 외에도, 결과물에 실제 코드가 들어있으면 그 코드가 문법
오류 없이 실행 가능한지 결정론적으로 검사합니다(Python은
`compile()`, JavaScript/HTML의 스크립트는 `node`로). "코드 검증"
단계에서는 완성된 결과물이 원래 요구사항을 실제로 다 반영했는지도
LLM에게 추가로 확인받습니다. 이 두 검사는 **참고 정보로만
기록되고, 기존 Gate 통과/차단 판정에는 영향을 주지 않습니다** —
화면에는 점수가 그대로 보이지만, 아직 충분히 검증되지 않은 새
지표가 기존 파이프라인의 통과 기준을 조용히 바꿔버리는 일이 없도록
의도적으로 분리해뒀습니다.

### Agent별 LLM 설정 추천
역할의 성격(기획/분석/설계 vs 구현/리뷰/QA vs 일반 응답)을 분석해
적합한 LLM provider·모델·세부 설정(temperature 등)을 추천합니다.
26개 레퍼런스 역할은 이미 실측으로 검증된 설정을 그대로 재사용하고,
새로 만든 역할은 스킬 태그를 기반으로 추정합니다. "모델 레지스트리"
화면에서 모델별로 어느 등급(심층추론/정밀·신속/표준)에 쓸지 직접
지정해두면, 그 지정이 항상 추정보다 먼저 추천 후보로 올라옵니다 —
새 모델이 나오거나 provider를 바꿀 때 코드를 고치지 않고 화면에서
설정만 바꾸면 됩니다. 추천은 1위 모델만 주는 게 아니라 등록된 활성
모델 전체를 순위표로 보여주므로, admin은 언제든 다른 모델을 직접
골라 적용할 수 있습니다. 필요하면 LLM에게 추천을 한 번 더
검토받을 수도 있습니다.

### 운영 관리
통합 인박스(결재 대기·실행 실패·낮은 품질 경고·완료 알림을 한
곳에서), 매니저 대시보드, 감사 기록, 데이터 삭제/보관기간 정책.
목록이 있는 화면은 전부 검색 필터와 정렬 가능한 헤더를 기본으로
제공합니다.

### 결과물 뷰어
복사·다운로드·미리보기/원본 전환이 되는 결과물 카드입니다. 마크다운은
표·인용문·이미지까지 그대로 렌더링하고, 코드는 언어를 인식해 문법
강조가 적용되며, 코드 블록이 `mermaid`/`chart`로 표시돼 있으면
다이어그램·차트로 바로 그려줍니다. HTML 결과물은 격리된 영역에서
안전하게 렌더링됩니다.

## 5. 아직 안 되는 것(알려진 한계)

- **결과물 "수정 후 재제출" 이력 관리** — 반려된 결과물을 고쳐서
  다시 낼 때, 이전 버전과 묶어서 보여주는 기능은 아직 없습니다.
- **Slack/Discord/Git 같은 외부 도구 연동** — 현재는 다루지
  않습니다.
- **모바일 화면 대응은 일부뿐** — 기본은 고정된 넓은 화면
  레이아웃이고, "내 업무"/"인박스"처럼 승인 알림을 확인하는 핵심
  화면만 좁은 화면에서도 쓸 수 있게 다듬어져 있습니다.
- **다크 모드 없음(의도적)** — 과거 시도에서 폼 컨트롤과 충돌하는
  버그가 실제로 발견돼, 지금은 밝은 화면 전용으로 고정해뒀습니다.

그 외 세부적인 결정 배경이나 과거에 고친 버그 이력은 git 커밋
로그에 날짜·요청 내용과 함께 남아 있습니다.
