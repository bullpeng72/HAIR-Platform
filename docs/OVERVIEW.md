# HAIR-Platform 개요

## 1. 지향점 — 이게 왜 있는가

HAIR(Human-AI Resource Management)는 **사람과 AI Agent를 하나의 조직도
위에서 함께 관리**하는 협업 플랫폼이다. "AI Agent를 어떻게 잘 만드는가"
(AgentForge, 이 프로젝트의 자매 프로젝트가 다루는 문제)가 아니라, **이미
만들어진 사람과 AI Agent를 어떻게 같은 조직 체계·같은 승인 절차·같은
성과 기준으로 배치·배분·협업시키는가**를 다룬다.

핵심 전제 3개:

1. **사람과 Agent는 같은 테이블, 다른 역할이다** — 조직도·배분·
   승인·성과리뷰가 전부 `resource_type IN ('human', 'agent',
   'team')` 하나의 축으로 통일돼 있다. "Agent 전용 관리 화면"과 "사람
   전용 관리 화면"을 따로 만들지 않는다.
2. **승인 없이 조직에 반영되는 변화는 없다(HITL)** — Agent가 뭔가를
   만들어내도(Deliverable) 그게 "확정된 결과"가 되려면 다단계
   결재(조직도 매니저 체인)를 거쳐야 한다. 유일한 예외가 "위임"인데,
   그것도 감사로그에는 남는다 — "아무도 모르게 반영"은
   없다.
3. **측정 없이 신뢰하지 않는다** — Agent가 만든 모든 결과물은 Gate A-G
   (목표달성·행동무결성·신뢰성·성능계약·보안경계·다중에이전트협업·
   관측성)로 자동 채점된다. "느낌상 잘 됐다"가 아니라 숫자로 남는다.

## 2. 핵심 개념

### Pool — "등록 → 재사용"

사람(Human Pool)·AI Agent(Agent Pool)·외부 도구(Tool Pool)·역량
태그(Skill Pool)·LLM 모델(Model Registry)·역할 그룹(Team) — 전부 같은
패턴이다: 한 번 등록해두면 여러 업무에서 드롭다운으로 재사용한다.
`skill_tags`(Agent/사람이 가진 역량 태그)가 `skill_pool`에 등록된
이름과 일치하면 그 역량에 연결된 Tool이 **자동으로** 붙는다(코드
하드코딩이 아니라 데이터 매핑).

### 배치 → 배분 → 승인

업무(Task)에 사람/Agent/Team을 연결하는 절차는 기본적으로 2단계다 —
배정 요청(`requested`, 누구나 후보를 제안) → 조직도 매니저 체인을 따른
다단계 승인 → 확정(`confirmed`). 자기 자신이 요청한 걸 자기가 승인할
수 없다(self-approval 방지). 한 업무에 **여러 건의 confirmed 배정이
공존**할 수 있다(사람 여러 명 + Agent 여러 개가 같은 업무를 같이
처리하는 구조를 기본으로 지원).

### 위임 — 배정의 경량 버전(Agent 전용)

결재를 기다릴 필요가 없는 가벼운 연결. "배정"과 달리 결재 체인을 만들지
않고 즉시 확정 상태가 된다 — 대신 `agent_delegated`로 감사로그에 구분
기록되고, Agent가 실제로 산출물을 내면 Gate A-G는 배정 경로와 동일하게
적용된다("가볍게 연결했다"와 "결과물 품질을 안 본다"는 별개다).

### 결과물(Deliverable)과 Gate A-G

업무의 산출물은 사람이 쓰든 Agent가 만들든 같은 `deliverables` 테이블에
쌓인다(텍스트/마크다운/HTML/코드 형식 선택 가능, 화면에서 형식에 맞게
렌더링). Agent가 만든 결과물은 생성 즉시 Gate A-G 채점이 붙고, 결재
체인도 자동으로 걸린다. 사람이 쓴 결과물은 초안(`draft`) 상태로 있다가
본인이 "검토 요청"을 눌러야 같은 결재 체인에 들어간다 — Agent 경로와
대칭이지만 자동이 아니다.

### 협업 워크스페이스 vs 대화 중심 작업공간

업무(Task) 하나에는 **협업 워크스페이스**(결과물 타임라인·댓글·배정·
결재가 다 모이는 "정식" 화면)와, 선택적으로 그 업무에 종속된 **대화**
(가벼운 채팅, `@멘션`으로 특정 Agent/Team을 부르면 그 자리에서 실행)가
같이 붙을 수 있다. 업무와 무관한 독립 대화(로그인 직후 바로 시작하는
자유 대화, 기본 AI 자동응답)도 있고, 필요하면 그 대화를 업무(Brief)로
승격시킬 수 있다. 무거운 절차(결재가 필요한 "정식 결과물")와 가벼운
절차(결재 없는 "대화") 두 트랙이 같은 Agent/Team 등록을 공유한다.

### CrewAI 다중 Agent 협업

여러 Agent를 하나의 Crew로 묶어 순차(sequential, 앞 Agent의 산출물이
다음 Agent에게 자동 전달) 또는 위임형(hierarchical, 매니저 Agent가
조율)으로 실제 협업시킬 수 있다. 실제로 발생한 위임/질의 이벤트를
추측 없이 캡처해 협업 관계를 SVG 다이어그램으로 보여준다.

## 3. 아키텍처

### 실행 모델 3단계

Agent를 "만든다"는 게 실제로는 세 가지 중 하나다 — 전부 비용이 다르고,
명시적으로 선택해야만 비용이 발생하는 단계로 올라간다(기본값은 항상
무료):

| 단계 | 방식 | 비용 |
|---|---|---|
| `stub` | 규칙기반 스텁(실제 LLM 호출 없음) | 무료, 기본값 |
| `simple_llm` | 1회성 LLM 호출(Anthropic/OpenAI/Ollama) | `use_llm=true`를 명시해야 발생 |
| `crewai` | 실제 CrewAI Agent 루프(Tool 호출·위임 가능) | `framework="crewai"`를 명시해야 발생 |

### 데이터 계층

SQLite(WAL 모드) 하나로 전부 저장한다 — `users`/`human_pool`/
`agent_pool`/`tool_pool`/`skill_pool`/`model_registry`/`teams`/
`tasks`/`assignments`/`approvals`/`deliverables`/`conversations`/
`audit_log` 등. `audit_log`는 append-only(수정·삭제를 DB 트리거로
막음) — "누가 언제 뭘 바꿨는지"는 절대 사후에 조작할 수 없다.

### Web UI

단일 페이지, 바닐라 JS(빌드 스텝·외부 프레임워크 없음) — `GET /`가
전체 HTML+CSS+JS를 그대로 서빙한다. 세션 인증(쿠키) 기반이되, 같은
브라우저의 여러 탭에서 서로 다른 계정을 동시에 쓸 수 있도록 탭별
토큰(`sessionStorage` + `Authorization` 헤더)도 쿠키보다 우선 적용된다.
RBAC 4종 역할(`admin`/`manager`/`member`/`viewer`)에 따라 보이는 탭·
가능한 동작이 갈린다.

### CLI

`hair` 하나의 진입점 — `hair serve`(서버 실행), `hair bootstrap-admin`
(콜드스타트 최초 관리자 계정), `hair reset-data`(운영 데이터 공장
초기화 — Agent/Tool/Skill/팀/파이프라인 템플릿은 유지), `hair eval`
(Gate A/B/D/E/G 수동 측정). `hair --version`, `hair <subcommand>
--help`로 자세한 옵션을 확인한다.

## 4. 주요 기능(현재 상태 기준)

- **사람-Agent 통합 조직도**: 배치·배분(결정론적 매칭 알고리즘
  — 완전일치 우선, 없으면 가용성·적합도·비용 가중 스코어링)·승인·
  팀 단위 그룹 등록 및 실행.
- **Agent 생성·실행**: Job Queue+샌드박스(Docker)로 신규 Agent 생성,
  온디맨드 실행(비동기, 상태 폴링), Gate A-G 자동 채점, CrewAI 다중
  Agent 협업.
- **Tool/Skill/Model 등록**: VectorDB(과거 산출물 검색)·GraphDB(조직
  관계 질의)·일반 웹검색(Parallel AI, MCP)·실시간 웹검색(Tavily, API
  키 필요)이 기본 제공되고, MCP로 외부 도구를 추가 연결할 수 있다.
  Parallel AI는 MCP라 CrewAI 실행에서만 동작하지만, Tavily는 네이티브
  함수라 대화창·Crew 실행 양쪽에서 동일하게 동작한다. Wikipedia 검색은
  2026-10-26 기준 이 배포 환경의 IP가 Wikimedia에 지속 차단돼 있어
  기본 시드에서 뺐다(코드는 `websearch.py`에 남아 있어 다른 환경에선
  복원 가능). 하니스
  방법론 절차 Skill 18개를 포함해 Skill Pool 48개·Tool Pool 11개가
  기본 등록돼 있다. 대화창·AI 에이전트 관리·지식 자료실에서 로컬
  파일(.md/.pdf/.html)을 업로드하거나 텍스트를 직접 입력하면
  VectorDB에 바로 색인되고(`documents.py`), Admin "지식 베이스" 탭에서
  색인된 조각 조회/삭제+통계와 GraphDB 관계 조회+통계를 관리한다.
- **레퍼런스 Agent 22개가 기본 등록**돼 있다(전부 `agent_pool`에
  즉시 active) — 소프트웨어 개발 파이프라인(요구사항 분석가·스펙
  작성자·코드베이스 분석가·백엔드 개발자·코드 검증가·QA 기능테스터
  6종),
  경영/사업전략 파이프라인(외부 자료 조사가·3C4P SWOT 분석가·기획서
  작성자·사업전략 수립가·C-level 보고서 작성자·프레젠테이션 자료
  작성자 6종), 기획→개발 실행팀(PM·AA/DA 아키텍트·개발 계획
  수립가·UI 기획자·테스트 계획 수립가·품질 관리자 7종), 그리고 그
  실행팀이 모듈을 나눠 위임할 "자율 개발 크루"(백엔드/프론트엔드/
  데이터·인프라/풀스택 개발자 4명 — 그중 "개발 계획 수립가"를
  매니저로 둔 hierarchical CrewAI Crew로 실행하면 4명에게 작업이
  자율적으로 위임된다). 영역별로 한 명씩만 둔 이유: CrewAI
  hierarchical은 Task를 매니저에게 하나만 주고 매니저가 "Delegate
  work to coworker" 도구로 그때그때 동적으로 위임하므로(같은 영역에
  여러 Agent를 둬도 매니저가 구분해 쓸 근거가 없다 — skill_tags가
  완전히 동일한 클론이었다), 매니저가 같은 코워커에게 하위 과업을
  여러 번 나눠 위임하는 것으로 충분하다. "자율 개발 크루"
  Team(`teams`)은 기본 등록돼 있어 바로 팀 배정/Crew 실행에 쓸 수
  있다 — (2026-10-28) 아래 파이프라인 엔진에 연결되면서 멤버 구성도
  "구현" 단계 6명(매니저+개발자 4명+UI 기획자)에서 파이프라인 7단계
  전체가 참조하는 13명(+요구사항 분석가·AA·DA·코드 검증가·테스트
  계획 수립가·QA 기능테스터·품질 관리자)으로 넓어졌다.
- **단계형 개발 파이프라인 엔진**(`pipeline_runtime.py`): "단독/순차
  릴레이/병행 위임" 3가지 모드로 단계를 구성하는 범용 엔진 — 각 단계가
  Gate A-G 기준으로 자동 채점되고, 기준 미달 시 피드백을 반영해
  자동 재시도하다가 반복 실패해야만 사람에게 에스컬레이션된다(BMAD-
  METHOD식 "계획 승인은 1회, 이후는 최소 HITL"). 화면에서 직접 단계를
  구성하는 빌더 UI 포함, 개발 외 업무(시장조사·전략 등)에도 같은
  엔진을 재사용할 수 있도록 설계. (2026-10-28) `teams.pipeline_
  template_id`로 "자율 개발 크루" 팀이 기본 제공 "소프트웨어 개발
  파이프라인"에 연결돼 있어, 대화에서 `@자율 개발 크루`로 멘션하면
  단발 Crew 실행이 아니라 이 엔진(코드 검증/QA/품질 관리 단계는
  Gate 통과 기준 0.5로 실제 품질 검증)을 그대로 탄다 — 연결 안 된
  다른 팀은 여전히 기존 단발 실행 그대로.
- **Agent별 LLM 모델/설정 최적화 추천**(`agent_optimizer.py`, admin):
  역할의 목표·기능·스킬 특성을 분석해 적합한 provider/model/
  tuning_config(temperature·reasoning 등)를 추천한다 — 22개 레퍼런스
  역할은 이 플랫폼에서 실측으로 이미 검증된 설정을 그대로 재사용하고,
  새 역할은 스킬 태그 기반 규칙으로 추정한다. 모델 랭킹은 기본적으로
  모델명 패턴 추정이지만, "모델 레지스트리" 화면에서 모델별로 어떤
  tier(심층추론/정밀·신속/표준)에 직접 적용되는지 매핑할 수 있다
  (`model_registry.optimization_tiers`, 모델 하나가 여러 tier에 동시
  매핑 가능) — 매핑된 모델이 있으면 그 tier의 추천에서 패턴 추정보다
  항상 먼저 후보로 오르므로, 새 모델 출시·provider 교체 때 코드 수정
  없이 이 매핑만 바꾸면 추천 랭킹에 바로 반영된다. 추천은 1위 모델
  하나만이 아니라 등록된 활성 모델 전체를 이 기준으로 순위 매긴 후보
  목록으로 오고(직접 매핑된 모델은 ★ 표시), admin은 개별/일괄 화면
  모두에서 1위 대신 다른 등록 모델을 직접 선택할 수 있으며 — 이미
  추천과 같거나 한 번 적용한 Agent도 다시 선택해 다른 모델로 재적용할
  수 있다. 개별 Agent 화면에서는 미리보기만(admin이 직접 저장), 일괄
  화면에서는 선택한 Agent에 바로 적용. 선택적으로 LLM에게 추천을
  보정받을 수 있다(실제 등록된 모델 밖의 추천은
  자동으로 거부).
- **운영 관리**: 통합 인박스(결재 대기+실행 실패+낮은 Gate 경고),
  매니저 대시보드, 감사로그, 데이터 삭제/보관기간 정책. 목록 화면은
  전부(24곳 공유) 검색 필터 + 정렬 가능한 헤더를 기본 제공한다.
- **결과물 뷰어**: 복사·다운로드·미리보기/소스 토글이 있는 결과물
  블록(Claude Artifact 스타일). marked.js+DOMPurify로 마크다운을
  렌더링(표·인용문·이미지 포함), highlight.js로 실제 언어 인식 코드
  하이라이팅, 코드펜스 언어가 `mermaid`/`chart`면 각각 Mermaid
  다이어그램/Chart.js 차트로 렌더링(CDN 라이브러리를 못 불러오는
  환경에서도 평문 폴백으로 깨지지 않음). HTML은 격리된 sandboxed
  iframe에서 렌더링. 토큰 사용량 요약.

## 5. 알려진 한계(핵심만)

- **"수정 후 재제출"(버전 히스토리) 미구현** — 결과물 재제출 시 이전
  버전과 묶는 기능은 스키마만 있고 쓰기 경로가 없다. 결재 반려→재제출
  정책과 함께 재설계가 필요한 상태로 남아 있다.
- **외부 워크플로우 도구 연동 없음** — Slack/Discord/Git 같은 사람들이
  이미 쓰는 도구와의 연동은 범위 밖이다.
- **반응형 UI는 일부 화면만** — 고정 1100px 레이아웃이 기본이고, 모바일
  대응은 "내 업무"/"인박스" 등 승인 알림 확인 경로만 좁혀뒀다.
- **다크 모드 없음(의도적)** — 네이티브 다크모드가 폼 컨트롤과 충돌하는
  버그가 실측으로 발견돼 라이트 전용으로 고정했다. 색상은 CSS 변수로
  토큰화돼 있어 추가하려면 전체를 명시적으로 오버라이드하면 된다.
- 그 외 세부 갭·결정 배경은 git 커밋 로그에 날짜·사용자 요청 원문과
  함께 남아 있다(`git log --oneline --all`).
