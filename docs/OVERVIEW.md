## 1. 한 줄로 말하면

HAIR(Human-AI Resource Management)는 **사람과 AI Agent를 같은
조직도 위에 올려놓고, 같은 방식으로 일을 배분·승인·실행·평가하는
협업 플랫폼**입니다.

"AI Agent 자체를 어떻게 잘 만드는가"는 이 프로젝트가 다루는 문제가
아닙니다(그건 자매 프로젝트인 AgentForge의 영역입니다). HAIR가
다루는 문제는 **이미 만들어진 사람과 AI Agent를, 회사 조직처럼
배치하고 업무를 맡기고 결과를 확인하는 절차를 어떻게 통일하는가**
입니다.

이 플랫폼을 이해하는 데 필요한 전제는 딱 3가지뿐입니다.

### 전제 1 — 사람과 Agent는 "같은 조직도" 위에 있습니다

조직도에 배치하고, 업무를 배분하고, 결재를 받고, 팀을 구성하는
절차는 사람이든 AI Agent든 **완전히 똑같은 화면·같은 흐름**을
탑니다. 예를 들어 "이 업무, 김 과장한테 맡길까 AI한테 맡길까"를
고민할 때 서로 다른 화면을 오갈 필요가 없습니다 — 같은 배정 화면에서
둘 다 후보로 뜹니다.

(단, Agent를 처음 "만드는" 화면과 사람을 "등록하는" 화면은 당연히
따로 있습니다. 태어나는 방식이 다르니까요. 통일된 건 **일단 조직에
들어온 뒤**의 절차입니다.)

### 전제 2 — AI가 혼자 결정하는 일은 없습니다 (HITL)

AI Agent가 뭔가를 만들어내도, 그게 회사의 "확정된 결과"로 인정받기
전에는 반드시 사람의 결재를 거칩니다. 이렇게 "사람이 중간에서 한 번
확인하고 지나간다"는 원칙을 줄여서 **HITL**(Human-In-the-Loop)이라고
부릅니다 — 이 플랫폼 전체에 깔린 가장 중요한 안전장치입니다.

예외가 하나 있는데, 반복적으로 자동 진행되는 단계(파이프라인)는
"정해둔 기준을 통과하면 그 자체를 승인으로 본다"는 규칙으로
사람 개입을 줄여줍니다 — 그래도 기준을 못 넘기면 결국 사람에게
돌아옵니다. "완전 무인 운영"은 어디에도 없습니다.

### 전제 3 — "잘했다"는 느낌이 아니라 숫자로 남습니다

AI Agent가 만든 모든 결과물은 7가지 기준(**Gate A~G**)으로 자동
채점됩니다. 사람이 "음, 괜찮아 보이네" 하고 넘기는 게 아니라, 매번
같은 잣대로 측정된 숫자가 기록에 남습니다. Gate가 정확히 뭘 보는지는
2절에서 설명합니다.

## 2. 핵심 개념 — 이 플랫폼의 언어

### Pool — "한 번 등록하면 계속 재사용"

사람(Human Pool)·AI Agent(Agent Pool)·외부 도구(Tool Pool)·역량
태그(Skill Pool)·LLM 모델(Model Registry)·역할 그룹(Team) — 이
여섯 가지는 전부 같은 패턴을 따릅니다. **한 번 등록해두면, 그 뒤로는
여러 업무에서 드롭다운으로 골라 쓰기만 하면 됩니다.**

예를 들어 "백엔드 개발"이라는 역량 태그를 Skill Pool에 등록해두면,
그 태그를 가진 사람이나 Agent에게 관련 도구가 **자동으로** 붙습니다 —
매번 수동으로 연결해줄 필요가 없습니다.

### 배치 → 배분 → 승인 — 업무를 맡기는 기본 절차

업무(Task)에 사람이나 Agent를 연결하는 절차는 기본적으로 2단계입니다.

1. **배정 요청** — 누구나 "이 후보가 이 업무를 맡으면 좋겠다"고
   제안합니다(아직 확정 아님, `requested` 상태).
2. **다단계 결재** — 조직도의 상사 체인을 따라 승인을 받으면
   **확정**(`confirmed`)됩니다.

몇 가지 세부 규칙이 있습니다.

- **자기 자신이 요청한 걸 자기가 승인할 수는 없습니다**(자기 승인
  방지) — 다만 **본인 스스로를 배정하는 경우**(예: "나 이거 할게")는
  예외입니다. 본인 시간만 쓰는 일이라 "남의 자원을 함부로 못 쓰게
  막는다"는 결재의 목적 자체가 성립하지 않으므로, 결재를 거치지
  않고 그 자리에서 바로 확정됩니다.
- **한 업무에 여러 명이 동시에 배정될 수 있습니다** — 사람 여러
  명 + Agent 여러 개가 같이 투입되는 구조가 기본값입니다.
- **후보 추천은 자동입니다** — 역할 이름이 비슷한 후보 중 필요한
  스킬을 전부 가진 후보가 있으면 그것부터 추천합니다. 그런 후보가
  없으면 가용성(남은 용량·부재·모델 대기 반영)·실적·비용을 가중치로 점수 매겨 상위 3명을
  보여줍니다(실적이 아직 없는 신규 인력/Agent는 가용성·비용만으로
  점수를 매깁니다). 그래도 후보가 전혀 안 보이면 "AI로 추천 받기"
  버튼으로 LLM에게 전체 인력/Agent 풀에서 의미상 맞는 후보를
  찾아달라고 요청할 수 있습니다(버튼을 눌러야만 호출되고, 이때는
  비용이 발생합니다).

### 위임 — Agent 전용 "가벼운 배정"

결재를 기다릴 필요 없이 Agent를 바로 업무에 연결하는 방법입니다.
위임은 즉시 확정 상태가 되지만, 누가 언제 위임했는지는 감사
기록에 그대로 남습니다 — "가볍게 연결했다"는 "결과물 품질을
안 본다"는 뜻이 아닙니다. 위임으로 만들어진 결과물도 일반 배정과
똑같이 Gate A-G 채점과 결재를 거칩니다.

### 결과물(Deliverable)과 Gate A-G — 품질을 숫자로 보는 법

업무의 결과물은 사람이 쓰든 Agent가 만들든 같은 곳에 쌓이고, 같은
방식으로 결재됩니다. 텍스트/마크다운/HTML/코드 중 형식을 지정할 수
있고, 화면은 그 형식에 맞게 보여줍니다(마크다운 서식, 코드 문법
강조, HTML 미리보기 전부 지원).

**Gate A-G**는 결과물을 7개 관점에서 자동으로 측정하는 기준입니다.

| Gate | 보는 것 |
|------|---------|
| A | 목표 달성 — 원래 시킨 일을 실제로 해냈는가 |
| B | 행동 무결성 — 하라고 한 것만 하고 엉뚱한 일을 벌이지 않았는가 |
| C | 신뢰성 — 같은 조건이면 비슷한 결과가 나오는가, 사실을 지어내지 않았는가 |
| D | 성능 계약 — 정해둔 시간·자원 안에서 끝났는가 |
| E | 보안 경계 — 하면 안 되는 접근/행동을 하지 않았는가 |
| F | 다중 에이전트 협업 — 여러 Agent가 같이 일할 때 역할을 지키고 충돌 없이 협력했는가 |
| G | 관측성 — 무슨 일이 있었는지 나중에 확인할 수 있게 기록을 남겼는가 |

Agent가 만든 결과물은 생성 즉시 이 7개 기준으로 채점되고, 결재
체인도 자동으로 걸립니다. 사람이 직접 쓴 결과물은 초안 상태로
있다가 본인이 "검토 요청"을 눌러야 같은 결재 절차에 들어갑니다 —
Agent 경로와 대칭이지만 자동으로 시작되지는 않습니다.

채점할 때마다 Agent-Evaluator가 만든 **평가 리포트**(Gate별 점수·지표·원인
진단·개선 제안을 담은 HTML 한 장)가 결과물과 대화 응답에 함께 저장되고,
카드의 "평가 리포트" 링크로 열 수 있습니다. Gate별 통과 기준(기본 0.7)·응답
시간 SLA·추론 표지는 admin이 설정 → 운영 관리 → **"평가 기준"**에서 바꾸며,
다음 평가부터 적용됩니다(평가 도구 CLI용 `.aoo/targets.json`으로 내보내기·가져오기 가능).

### 협업 워크스페이스 vs 대화 — 무겁게 할지, 가볍게 할지

업무 하나에는 두 가지 작업 공간이 붙을 수 있습니다.

- **협업 워크스페이스** — 결과물 타임라인·댓글·배정·결재가 다
  모이는 "정식" 화면입니다. 결재·Gate 채점이 필요한 진짜 업무는
  여기서 처리합니다.
- **대화** — `@멘션`으로 특정 Agent/Team을 불러 그 자리에서 즉시
  실행시키는 가벼운 채팅입니다. 업무에 종속될 수도 있고(그 업무
  전용 대화), 업무와 무관한 완전히 독립된 대화로 시작할 수도
  있습니다(메뉴 "대화"에서 바로 쓸 수 있는 자유 대화 — 로그인하면 먼저 열리는 **홈**의
  "AI에게 일 맡기기"가 대화·Agent·파이프라인 중 맞는 길을 추천해 줍니다).

**대화와 업무 요청(Brief)은 서로 독립된 두 트랙입니다.** 대화를
나누다가 "이건 정식으로 결재까지 받아야겠다" 싶으면, 대화 상단의
"업무 요청으로 전환"으로 이 대화 내용을 담은 업무 요청 초안을 만들어
(원하면 AI가 목표·요구사항·완료 기준으로 정리) 다듬은 뒤 제출합니다 —
어느 대화에서 왔는지 업무 요청에 남고, 대화에는 전환 사실이 기록됩니다.
대화가 저절로 업무로 바뀌지는 않습니다. (예외적으로, 아직 업무에
연결되지 않은 대화에서 메시지를 "결과물로 저장"하면 그 내용을 담을
최소한의 업무 틀이 뒤에서 자동으로 하나 생기긴 합니다 — 이건
"대화를 정식 업무로 승격시켜주는 기능"이 아니라, 저장할 그릇이
없을 때 빈 그릇을 하나 마련해주는 보조 장치입니다.)

### 여러 Agent가 함께 일하기 (CrewAI)

여러 Agent를 하나의 팀(Crew)으로 묶어 실제로 협업시킬 수 있습니다.
두 가지 방식이 있습니다.

- **순차(sequential)** — 앞 Agent의 결과물이 다음 Agent에게
  자동으로 전달됩니다(릴레이 방식).
- **위임형(hierarchical)** — 매니저 역할의 Agent가 나머지 팀원에게
  작업을 쪼개 맡깁니다. 다만 매니저가 실제로 위임하지 않고 계획만
  요약하는 경우가 반복 확인돼, 팀에는 새로 지정할 수 없고(이미
  위임형으로 쓰던 팀만 유지) Crew 빌더에서도 순차 방식을 권장합니다.

누가 누구에게 어떤 작업을 넘겼는지는 추측하지 않고 실제로 일어난
이벤트를 그대로 캡처해 협업 관계도(다이어그램)로 보여줍니다. 같은
업무를 재실행한 적이 있다면 바로 이전 실행과 최종 결과물을 줄 단위로
비교(추가된 부분은 초록, 삭제된 부분은 빨강)할 수도 있습니다 — 재시도
할 때마다 전에 되던 기능이 조용히 사라지는 걸("두더지 잡기" 퇴행)
사람이 한눈에 알아챌 수 있게 하는 장치입니다.

### 자동 재시도와 에스컬레이션 — 언제 사람을 부르는가

Gate 기준에 못 미치면 자동으로 재시도합니다. **마지막으로 자동
재시도하는 순서에서는** Agent가 자기 초안을 원래 요구사항과 한 줄씩
대조해 스스로 고치는 "자가검토" 모드가 자동으로 켜집니다 — 일반
재시도와 사람 에스컬레이션 사이의 한 단계 더 꼼꼼한 중간 단계입니다.
이렇게까지 해도 기준을 못 넘기면, 그때 비로소 사람에게 결재 요청이
올라갑니다 — 그리고 승인 권한이 있는 사람이 그 대화에 아직 없다면
시스템이 자동으로 초대해, 실제로 알림을 받게 합니다.

업무 전체에는 선택적으로 **재시도 예산**을 걸 수 있습니다(admin/
manager 전용) — 파이프라인 재시도 수와 Crew 재실행 수를 합쳐서
상한을 넘기면, 그 단계 자체의 재시도 기회가 남아 있어도 즉시
사람에게 넘깁니다. 같은 업무를 반복 재시도하며 비용만 계속 쓰는
걸 막는 안전장치이고, 설정하지 않으면(기본값) 아무 제한도 걸리지
않습니다.

## 3. 어떻게 만들어져 있나 (조금 더 기술적인 내용)

여기부터는 "왜 이렇게 동작하는지"가 궁금한 분을 위한 내용입니다 —
실제로 이 플랫폼을 쓰는 데는 꼭 필요하지 않습니다.

### Agent를 "만든다"는 것의 3단계

Agent를 만들 때 실제로 고르는 건 세 가지 중 하나입니다 — 아래로
갈수록 더 똑똑해지지만 비용도 올라갑니다. 기본 선택은 실제로 일할 수
있는 **CrewAI**이고(CrewAI가 설치되지 않은 기본 설치본이면 1회성 LLM),
무료 스텁은 흐름만 채워볼 때 직접 골라야 합니다.

| 단계 | 방식 | 비용 |
|---|---|---|
| CrewAI | 실제 CrewAI Agent — 도구 호출·위임 가능(`crewai` extra 필요) | 발생, 기본 선택 |
| 1회성 LLM | Anthropic/OpenAI/Ollama 중 하나를 한 번 호출 | 발생(Ollama는 로컬이라 API 비용 없음) |
| 스텁(stub) | 규칙 기반 — 실제 LLM 호출 없음(실제로 일하지는 못함) | 무료, 직접 선택 |

### 시스템 구성 한눈에

| 층 | 구성 | 비고 |
|---|---|---|
| 웹 서버 | FastAPI(Python 3.11+) — `hair serve`, API 266개 | 라우트는 영역별 `routes_*.py`로 나뉘고 `create_app()`이 조립 |
| 화면 | 빌드 없는 바닐라 JS 단일 페이지(화면 31개) | `webui_assets/`(셸·CSS·화면별 JS 30개·이용 가이드 마크다운)를 기동 때 이어 붙여 `GET /`로 서빙 |
| 데이터 | SQLite 하나(WAL) + 지식 벡터 폴더(ChromaDB) | 업로드 문서·평가 리포트도 DB 안(압축) — 아래 "데이터는 어디에 저장되나" |
| 실행 | 백그라운드 작업 큐 + 선택적 작업 프로세스(`hair worker`) | 아래 "AI 실행은 어떻게 도나" |
| AI 호출 | Anthropic·OpenAI·Ollama 직접 호출(`llm.py`), 여러 Agent 협업은 CrewAI(litellm 경유) | 모델별 동시 호출 상한·우선순위가 두 경로 모두에 걸림 |
| 평가 | Agent-Evaluator SDK(Gate A-G·HTML 리포트) + 플랫폼의 결정적 점검(수치·인용·용어·코드·화면) | 아래 4절 "콘텐츠 형식별 자동 검증" |

선택 설치(extras)로 기능을 더합니다 — `llm`(클라우드 SDK)·`crewai`(Agent 협업)·`mcp`(외부 도구)·`documents`(PDF·Office
읽기·내보내기)·`graph`(LangGraph 실행엔진)·`korean`(낱말 분석기)·`vectordb`(ChromaDB)·`dbconnect`(PostgreSQL·MySQL 조회)·
`e2e`(Playwright — 화면 테스트와 HTML 결과물 화면 실행 점검). 코드는 `src/hair_platform/` 아래 모듈 111개입니다.

### 데이터는 어디에 저장되나

SQLite 데이터베이스 하나에 전부 저장됩니다(WAL 모드 — 여러 읽기가
동시에 가능, 웹 서버는 연결 하나를 공유하고 작업 프로세스는 작업마다 자기 연결을 씁니다). 누가 언제 뭘
바꿨는지 남기는 감사 기록(audit log)은 DB 트리거로 수정도 삭제도 불가능하게 막아둬서, 나중에 조작될 걱정이
없습니다.

- **지식 검색**: 문서 조각의 임베딩(OpenAI 또는 Ollama 임베딩 모델 하나)을 SQLite에 저장하고, `vectordb`가 설치돼
  있으면 DB 파일 옆 `<db>-vectors/`의 ChromaDB로 찾습니다(없으면 모든 조각과 코사인 유사도 비교 — 1만 개에서 약 1.7초 vs
  0.04초). 검색은 요청한 사람이 볼 수 있는 문서(공개 범위)만 씁니다. 색인이 어긋나면 `hair reindex-vectors`.
- **스키마 변경**: 기동할 때 `init_schema()`가 표를 만들고, 한 번만 돌아야 하는 데이터 보정은 이름 붙은 마이그레이션으로
  기록해 다시 돌지 않게 합니다(`db.py` 스키마·연결 / `db_migrations.py` / `db_seed.py` 기본 Pool).
- **백업**: `hair backup`은 SQLite 온라인 백업 API로(쓰는 중이어도 일관된 사본, WAL 내용 포함) DB와 벡터 폴더를
  `.tar.gz` 하나로 묶습니다. `hair serve`가 하루 한 번 자동으로 뜨고(최근 7개), `hair reset-data` 전에도 뜹니다.
  `hair restore`는 경로·무결성을 검사한 뒤 지금 데이터를 옆에 남기고 교체합니다. DB 파일을 그냥 복사하면 WAL에만 있는
  최근 변경이 빠질 수 있습니다.

### AI 실행은 어떻게 도나

- **작업 큐**: 대화 응답·Agent 실행·파이프라인 단계·Crew·지식 등록은 모두 `background_jobs` 표에 작업으로 들어갑니다.
  기본(`embedded`)은 웹 서버 안에서 실행하고, `HAIR_WORKER_MODE=external`이면 웹 서버는 기록만 하고 별도
  작업 프로세스(`hair worker`, 하나만)가 실행합니다 — 웹 서버를 재시작해도 실행이 이어집니다.
- **우선순위와 모델 자리**: 작업마다 우선순위가 있습니다(대화 응답 0 · 일반 1 · 파이프라인·Crew·지식 등록 2). 같은 모델에
  한 번에 보내는 호출 수는 모델 레지스트리의 "동시 실행 상한"(Ollama 기본 1 — Ollama는 한 모델에 요청을 하나씩 처리)으로
  막고, 기다리는 호출 중 우선순위가 높은 것부터 자리를 받습니다. 실측: 긴 생성 3개가 줄 서 있을 때 대화 응답
  107~121초 → 39~42초. 작업 프로세스는 자리 하나를 늘 대화용으로 남깁니다.
- **파이프라인 엔진**: 기본은 직접 실행기(`stage_runner`), 선택으로 LangGraph 그래프 엔진(`graph` extra — 단계마다
  체크포인트를 남겨 재시작해도 그 지점부터)이고, 두 엔진이 같은 단계 실행 코드를 씁니다. 단계가 45분 동안 진척이
  없으면 멈춤 감시가 정리하고 모든 스레드의 스택을 활동 기록에 남깁니다(`HAIR_STAGE_STALL_SECONDS`). 서버
  재시작으로 멈춘 실행은 "이어서 실행"으로 끝난 단계를 건너뛰고 다시 돕니다.
- **진행 표시**: 실행 중 단계·Agent·도구 호출·작성 중인 글이 진행 기록으로 남아 화면이 몇 초마다 읽어 갑니다.
  모델이 실제로 부른 도구는 실행·단계·시도별로 저장돼(`tool_calls`) "점검했다고만 쓰고 안 부른" 경우를 잡습니다.
- **Ollama 특화**: 추론(생각) 끄기를 Agent 설정에서 실제 호출의 `think`로 보내고(요구사항 정리·검토 역할은 기본 끔 —
  실측 파이프라인 34분 → 8분), 로컬 모델에서는 CrewAI의 작업 전 계획을 끄고 도구 반복 상한을 8로 둡니다.

### 보안·격리

- **인증**: 비밀번호는 bcrypt. 세션 쿠키와 탭별 토큰(같은 브라우저에서 탭마다 다른 계정 가능) 모두 비밀번호 표지를 담아,
  비밀번호를 바꾸거나 관리자가 재설정하면 그 전의 로그인이 끊깁니다. 같은 아이디로 5번·한 주소에서 20번 틀리면 15분 잠금.
  다른 PC에서 접속하게 띄우면 세션 서명 키(`HAIR_PLATFORM_SECRET_KEY`)가 필수입니다.
- **권한**: 아래 "화면(Web UI)"의 RBAC — 서버의 권한 검사 하나로만 정하고 자동 테스트로 확인합니다.
- **외부 데이터는 지시가 아니다**: 메일·캘린더·사내 DB·웹 검색·MCP 결과는 "외부 데이터" 표시로 감싸 전달하고, 외부
  데이터를 읽은 실행에서는 외부로 쓰거나 실행하는 도구를 자동으로 막아 사람 승인으로 넘깁니다(프롬프트 주입 대비).
- **연동 비밀값**: 사내 DB 비밀번호·메일 앱 비밀번호·비공개 iCal 주소는 DB에 저장하지 않고, 화면에는 서버
  환경변수 **이름**만 적습니다. 사내 DB는 SQL 검사 + 읽기 전용 연결 두 겹, 행 수·시간 상한.
- **AI가 만든 코드·화면 실행**: 코드 테스트는 네트워크를 막은 Docker(`python:3.11-slim`·`node:22-slim`, 메모리·CPU·
  프로세스 수 제한)에서만 돌리고, Docker가 없으면 관리자가 `HAIR_ALLOW_LOCAL_CODE_RUN=1`로 허용할 때만 로컬에서 돌립니다.
  HTML 결과물은 Chromium 샌드박스로 `about:blank`에 띄우고 모든 네트워크 요청을 막습니다. 평가 리포트는 HAIR 세션과
  분리된 격리 출처로 열립니다.

### 운영·품질 관리

- **프로세스 성과 측정**: 리드타임 = `pipeline_runs.created_at→finished_at`, AI 작업 = 단계 기록의 `started_at→created_at`,
  사람 대기 = 단계 기록 → 그 결재의 마지막 결정 시각(`audit_log`의 `approval_approved/rejected`, 두 실행 엔진 공통),
  건당 비용 = 실행 기간의 `llm_usage.task_id` 합계. 새로 저장하는 값은 `pipeline_templates.baseline_minutes` 하나.
- **학습 루프·변경 관리**: `stage_lessons`(후보→적용/무시/끄기, 적용분만 두 실행 엔진의 단계 지시문에 주입, 단계당 8개·1,500자),
  `process_changes`(단계 설정은 바뀐 값만 전·후 값으로 기록, 되돌리기는 그 뒤 같은 값이 다시 바뀌지 않았을 때만).
- **위험 기반 결재**: `approval_recommendations`(단계 기록마다 위험도·추천·사람 결정·자동/표본 여부). 자동 승인 판정
  (`approval_assist.auto_approval_check`)은 두 실행 엔진이 같은 함수를 쓰고, 단계 설정의 사람 승인만 대상이다.
- **외부 입력·실행 동작**: `inbound_triggers`/`inbound_events`(트리거·외부 키 유일, 상태 queued→started, 시작한 실행에
  `tool_calls.external=1` 기록으로 외부 데이터 경계 적용), `POST /api/inbound/{id}`는 로그인 없이 트리거 토큰(해시 비교)만.
  `stage_actions`/`action_executions`(단계 결과당 한 번, `ApprovalDecision.run_action`이 참일 때만 발송).
- **상태 확인**: admin "시스템 상태" 화면(서버·DB 무결성·백업·디스크·작업 큐·모델 연결·외부 연결)과, 감시 도구용
  `GET /health`(로그인 불필요, 내부 정보 없음, DB를 읽을 수 없으면 503).
- **환경 설정**: `.env`의 환경변수를 `hair init`(대화형)·`hair check`(빠진 값·잘못된 값, `--db-path`면 연동 비밀값과
  작업 프로세스까지)로 관리합니다. 버전은 `pyproject.toml` 하나가 기준이고 `hair --version`·화면 상단·API 문서가
  설치 메타데이터에서 같은 값을 읽습니다.
- **테스트**: 1,800건 이상의 단위·통합 테스트는 외부 네트워크와 로컬 Ollama 접속을 막고 전부 가짜 응답으로 돕니다
  (어느 PC·CI에서나 같은 결과). 그 밖에 실제 서버+Chromium으로 모든 화면을 여는 화면 테스트(폰 폭 넘침·JS 오류 0건 포함),
  실제 PostgreSQL·MySQL·메일 서버를 Docker로 띄우는 통합 테스트가 있습니다. CI는 테스트를 파일별 실행 시간으로 4묶음에
  나눠 병렬로 돌립니다(약 27분 → 8분, `scripts/ci_shard.py`). 의존성은 `constraints.txt`로 테스트를 통과한 조합에 고정합니다.

### 화면(Web UI)

별도 설치나 빌드 과정 없이, 서버에 접속하면 바로 전체 화면이
뜨는 단일 페이지 앱입니다. 로그인 후 역할(`admin`/`manager`/
`member`/`viewer`)에 따라 보이는 메뉴와 할 수 있는 동작이
달라집니다(아래 "권한" 참고). 같은 브라우저에서 여러 탭을 열어
서로 다른 계정으로 동시에 로그인해둘 수도 있습니다.

**권한(RBAC)** — "이 역할은 이 화면에서 이것만 할 수 있다"는 규칙은
문서로 따로 관리하지 않고, 서버 코드 자체에 있는 권한 검사 하나로만
정해집니다 — 문서와 실제 동작이 서로 어긋날 가능성을 원천적으로
없애는 선택입니다. 이 권한 규칙이 실제로 지켜지는지는 "역할별로
허용돼야 할 동작/막혀야 할 동작"을 자동 테스트로 반복 확인합니다.

### 명령어(CLI)

`hair`라는 명령어 하나로 전부 처리합니다.

- `hair init` — `.env` 환경변수 설정(대화형, 최초 1회)
- `hair check` — `.env`/환경변수 점검(provider·API 키·SMTP 설정 불일치를 찾아줌)
- `hair serve` — 서버 실행(켜져 있는 동안 하루 한 번 자동 백업)
- `hair worker` — 작업 프로세스(`HAIR_WORKER_MODE=external`일 때 — 웹 서버를 재시작해도 AI 실행이 계속됨)
- `hair bootstrap-admin` — 맨 처음 관리자 계정 만들기
- `hair backup` / `hair restore` — 데이터 백업(DB+지식 벡터를 `.tar.gz` 하나로, 서버가 켜져 있어도 됨)과
  복원(서버를 끄고 실행, 지금 데이터는 옆에 남겨 둠)
- `hair reset-data` — 운영 중 쌓인 데이터만 공장 초기화(Agent/Tool/
  Skill/파이프라인 템플릿·조직 정책·"초기화 시 보호" 팀은 그대로 둠, 관리자가 만든
  Agent의 상태도 유지, 지우기 전에 자동 백업)
- `hair reindex-vectors` — 지식 베이스 벡터 색인을 저장된 임베딩으로 다시 맞추기(AI 비용 없음)
- `hair eval` — Gate 기준을 수동으로 측정(결과 JSON과 Gate A-G 종합 HTML 리포트를
  `results/`에 저장)

자세한 옵션은 `hair --help`, `hair <명령어> --help`로, 버전은 `hair --version`으로
확인할 수 있습니다.

## 4. 지금 쓸 수 있는 기능들

아래 전부 실제로 동작하는 코드로 구현돼 있습니다(스텁이나 겉보기
목업이 아닙니다) — 테스트 1,800건 이상 통과, API 266개, 화면(탭) 31개,
기본 제공 파이프라인 템플릿 8개가 지금 기준 실측값입니다(v0.3.2).

### 사람-Agent 통합 조직도
배치·배분(앞서 설명한 자동 매칭 알고리즘)·승인·팀 단위 그룹 등록과
실행을 한 화면 흐름에서 처리합니다.

### Agent 생성과 실행
할 일의 역할로 신규 Agent를 만들고(CrewAI·1회성 LLM·스텁 — 3절), admin이 온보딩 승인하면 배정·대화·파이프라인에서
씁니다. 실행은 작업 큐에서 비동기로 돌고(화면은 진행 기록을 몇 초마다 읽음), 모든 실행에 Gate A-G가 자동으로 붙으며,
CrewAI로 여러 Agent를 묶어 실제 협업시킬 수 있습니다. Agent마다 모델·파인튜닝(온도·추론 모드·반복 상한 등)·스킬·
도구·MCP 서버를 정하고, 되돌리기 어려운 오프보딩·삭제는 설정 창의 "위험 구역"에 둡니다.

### 도구·스킬·모델 등록
기본으로 제공되는 도구:

- **내부지식검색**(VectorDB) — 과거에 저장해둔 결과물을 찾아봅니다.
- **조직배정관계조회**(GraphDB) — 조직 내 관계를 질의합니다.
- **일반 웹검색**(Parallel AI, MCP) — 대화창과 Crew 실행 양쪽에서 동작합니다(MCP 서버에
  접속할 수 있을 때 — v0.3.0 이후 대화·단일 Agent 실행도 MCP 도구를 실제로 호출).
- **실시간 웹검색**(Tavily, API 키 필요) — 대화창과 Crew 실행 양쪽
  모두에서 동작합니다.
- **코드 저장소 조회** — 관리자가 "연동 설정"에서 등록한 Git 저장소의
  커밋된 파일을 개발 Agent가 직접 읽습니다(읽기 전용, 비밀 파일 제외).

  전용 두 겹, 행 수·시간 상한, 조회마다 활동 기록, 비밀번호는 환경변수).

  검색·열람합니다(읽기 전용, 읽음 표시 유지, 메일함별 공개 범위, 조회 기록).

- **재무 지표 계산기·영업 퍼널 계산기·계약 조항 점검기·인사 지표 계산기·채용 공고 점검기** — 업무 영역
  템플릿의 계산·점검을 코드로 합니다(모델이 직접 계산한 비율·NPV가 틀리는 문제를 줄이기 위해).
- **수치 데이터 분석기·차트 생성기** — 합계·평균·증감률·표준편차를 코드로 계산하고 차트를 그립니다(대화에서도 실제 실행).

이 외에도 MCP 표준으로 외부 도구를 추가 연결하거나, admin이 Python 함수를 직접 도구로 등록할 수 있습니다(Docker가

등록된 Skill Pool은 85개(그중 18개는 "방법론 절차" 전용), Tool

파일 업로드(.md/.txt/.html/.pdf/.csv/.xlsx/.docx/.pptx)는 대화창·협업 워크스페이스·지식 베이스

### 단계형 파이프라인 엔진
"단독 실행"·"순서대로 이어받기"·"계획 분담"(리드가 팀원별 하위 작업을 나누고, 팀원이 각자 수행한 뒤,
리드가 하나로 합침) 3가지 방식으로 업무 단계를 구성하는 범용 엔진입니다(예전의 "매니저가 그때그때 위임하기"는
실제로 위임하지 않는 경우가 반복돼 2026-11-26에 계획 분담으로 바꿨습니다). 각 단계는 Gate
기준으로 자동 채점되고, 기준 미달이면 피드백을 반영해 자동
재시도하다가 반복 실패해야만 사람에게 올라갑니다(계획 단계에서
한 번만 사람이 승인하면 그 뒤로는 최소한의 사람 개입으로 진행됩니다).
**계획 분담**은 위임을 모델의 즉흥적인 도구 호출에 맡기지 않습니다 — 리드가 팀원별 하위 작업을 JSON 계획으로
내면 플랫폼이 팀원에게 나눠 실행시키고(리드가 빠뜨린 팀원은 단계 지시로 자동 배정), 리드가 결과를 하나로 병합합니다
(두 실행엔진 모두 지원). 사업/기획 파이프라인의 "자료 조사·분석" 단계가 이 방식입니다(실측 순차 릴레이 대비
29% 빠르고 결과물이 한 편으로 정리됨). 예전 병행 위임 단계는 기동 때 같은 리드·팀원의 계획 분담으로 자동 전환됩니다.
단계마다 **모델을 따로 지정**할 수 있고(가벼운 단계만 작은 모델로), **필수 도구**를 지정하면 그 도구를 실제로
부르지 않은 시도는 재시도합니다. 검토자가 승인하면서 고칠 곳을 짚으면 "조건부 승인"으로 표시하고(엄격 검토를
켜면 되돌려 고침), 점검기가 있는 단계는 검토 승인 뒤 최종본을 점검기에 다시 넣어 판정이 다르면 사람에게 올립니다. 로컬(Ollama) 모델에서는 Agent의 작업 전 계획을 끄고 도구 반복 상한을
8회로 둡니다(`HAIR_OLLAMA_AGENT_PLANNING=1`로 계획을 다시 켤 수 있음). 검토 단계는 Gate 점수와 함께 검토자의 `## 판정`도
따릅니다 — "보완 요청"이면 작성 단계로 되돌려 검토 의견대로 다시 쓰게 하고,
재시도를 다 써도 안 되면 사람에게 올립니다. 파이프라인은 "연동 설정"(헤더 ⚙ 내 설정)에서 매일/평일/매주
정한 시각에 **정기 실행**되게 하거나, 앞 파이프라인이 끝나면 다음 파이프라인을 시작하는 **이벤트 트리거**로 이을 수 있습니다.

화면에서 직접 단계를 구성하는 빌더가 있어, 소프트웨어 개발이 아닌
업무(시장조사·전략 등)에도 같은 엔진을 그대로 재사용할 수 있습니다.
업무를 등록할 때 LLM에게 "이 업무를 어떤 역할들로 나누면 좋을지"
제안을 받아 한 번에 여러 할 일을 만들 수도 있습니다(선행 업무
관계까지 함께 제안됩니다).

기본으로 제공되는 파이프라인 템플릿은 8개입니다(5번이 4종).

1. **소프트웨어 개발 파이프라인** — 요구분석 → 설계 → 개발 계획 →
   구현 → 코드 검증 → QA → 품질 관리, 7단계.
2. **사업/기획 업무 처리 파이프라인** — 같은 엔진을 경영·기획
   업무에 적용한 버전. 자료 조사부터 최종 승인까지 7단계.
3. **제안서 작성 파이프라인** — 2번에서 "제안서 하나만 필요한
   경우"를 위해 분리해낸 버전(발주처 평가 대응을 위한 "표현 검토"
   단계를 그대로 유지).
4. **실적 보고 파이프라인** — 2번에서 "정기 실적 보고서"를 위해
   분리해낸, 더 가벼운 버전.
5. **업무 영역 템플릿**(재무·영업/고객지원·법무·인사) — 재무 분석 보고,
   영업 제안 메일, 계약서 1차 검토, 채용 공고·면접 설계 파이프라인과
   영역별 도구(재무 지표 계산기·영업 퍼널 계산기·계약 조항 점검기·인사
   지표 계산기·채용 공고 점검기)·스킬·Agent. 계산과 점검은 도구가 코드로
   하고, 법무·채용 점검 결과는 1차 점검용(법률 자문 아님).

소프트웨어 개발의 "구현" 단계는 풀스택 개발자 한 명이 실행 가능한
완성본을 한 번에 작성하고, **실행 가능성 Gate**(완성된 단일 결과물이
있는지, 골격·자리표시자·구문 오류가 없는지)를 통과해야 다음 단계로
넘어갑니다(예전 4명 릴레이는 조각만 남기고 실행 가능한 완성본 없이
끝나는 일이 있었습니다). 검증 단계가 기준에 못 미치면 같은 검토를
다시 돌리지 않고, 지정한 작성 단계로 돌아가 검토 의견을 반영해 다시
쓰게 할 수 있습니다(기본 템플릿 8종은 모두 이렇게 설정돼 있음).
요구사항 추적성의 기준이 되는 "요구사항 정의 단계"도 단계마다 지정할
수 있습니다(지정이 없으면 1단계).

Agent 출력에 섞이는 내부 추론·실행되지 않은 도구 호출·영어 작업
메모·같은 문장 반복·중간에 잘린 HTML은 저장 전에 걷어 내거나, 걷어
낼 수 없으면 결과물만 다시 쓰게 재시도시킵니다(마지막 시도는 그대로
받아 Gate·사람 검토가 판단합니다).

### 콘텐츠 형식별 자동 검증
Gate A-G 외에도, 결과물에 실제 코드가 들어있으면 그 코드가 문법
오류 없이 실행 가능한지 결정론적으로 검사합니다(Python은
`compile()`, JavaScript/HTML의 스크립트는 `node`로). 검증 단계에서는
완성된 결과물이 요구사항 정의 단계의 요구사항을 실제로 다 반영했는지도
LLM에게 추가로 확인받습니다(요구사항 추적성).

v0.3.0부터는 내용 자체도 기계적으로 검증합니다. 결과물의 퍼센트 수치가
요청·조회 자료·도구 결과의 숫자로 실제 재현되는지 계산해 보고(수치 근거),
근거 없는 문장만 한 번 고치며 남으면 "⚠ 수치 확인 필요"를 붙입니다.
개발 결과물에 Python·JavaScript 코드와 테스트가 있으면 네트워크를 막은 Docker에서
실제로 실행합니다(테스트 실행 — Python은 pytest 최소 대체 실행기, JavaScript는 Jest 형식과 Node `node:test` 모두,
언어별 통과 수 기록). HTML 결과물은 실제 브라우저(Chromium 샌드박스, 네트워크 차단)로 열어 스크립트 오류·빈 화면을
보고 보이는 버튼을 눌러 본 뒤의 오류까지 기록합니다(화면 실행, `e2e` extra). 두 점검은 기본으로 기록만 하고, 단계
Gate에 넣으면 통과 조건이 됩니다. 한국어 결과물에 섞인 한자·외국 문자는
모든 경로(대화·단독 실행·파이프라인 단계)에서 자동 교정합니다(문장 교정으로 안 고쳐진
줄은 한자 조각만 앞뒤 문맥과 함께 다시 교정). 한국어 글자로 된 뜻 없는 낱말(모델이 지어낸 낱말)은
형태소 분석기 사전으로 찾아 참고용 "낱말확인" 배지로 알립니다(통과 판정에는 넣지 않음, `korean` 선택 설치).
인용 표지("…라고", "…에 따르면")와 함께 따옴표로 옮긴 문장이 근거 자료에 실제로
있는지(인용 근거), 근거 자료의 낱말에서 한 음절이 빠지거나 바뀐 용어가 있는지(용어
확인 — 예: "1분기 착수"→"1분 착수")도 대조해 배지로 남깁니다.

파이프라인 단계의 통과 여부는 **그 단계에 지정한 Gate 목록만으로**
판정합니다. 실제 실행 점검(2026-11)에서 C(신뢰성)·D(응답 시간)·F(협업
구조)·G(관측성)는 파이프라인 경로에서 결과물 내용과 무관하게 늘 같은
값이 나와, 기본 검증 단계는 A(목표 달성)와 요구사항 추적성으로만
판정하고(추적성을 재는 단계는 둘 다 통과해야 함) 나머지는 기록·표시만
합니다. 구현 단계는 실행 가능성 Gate로 판정합니다. v0.3.0에서 원인을
정리해, 여러 LLM 호출로 몇 분씩 걸리는 크루·파이프라인 실행의 C·D(단일
호출 기준 30초 응답 시간)와 Agent가 1명인 단계의 F는 상수 대신 "측정 안
됨"(사유 표시)으로 기록하고, G는 한국어 근거 표현(근거·때문·므로 등)도
인식합니다. "측정 안 됨"은 통과 비율과 Agent 평균에서 빠집니다.

### Agent별 LLM 설정 추천
역할의 성격(기획/분석/설계 vs 구현/리뷰/QA vs 일반 응답)을 분석해
적합한 LLM provider·모델·세부 설정(temperature 등)을 추천합니다.
39개 레퍼런스 역할은 이미 실측으로 검증된 설정을 그대로 재사용하고,
새로 만든 역할은 스킬 태그를 기반으로 추정합니다. "모델 레지스트리"
화면에서 모델별로 어느 등급(심층추론/정밀·신속/표준)에 쓸지 직접
지정해두면, 그 지정이 항상 추정보다 먼저 추천 후보로 올라옵니다 —
새 모델이 나오거나 provider를 바꿀 때 코드를 고치지 않고 화면에서
설정만 바꾸면 됩니다. 추천은 1위 모델만 주는 게 아니라 등록된 활성
모델 전체를 순위표로 보여주므로, admin은 언제든 다른 모델을 직접
골라 적용할 수 있습니다. 필요하면 LLM에게 추천을 한 번 더
검토받을 수도 있습니다.

같은 화면의 **성능 테스트**는 두 가지입니다. **빠른 측정**은 모델을 올리는 첫 호출(예열)을 빼고 같은 질문 3회의
중앙값으로 생성 속도(tok/s, 생각 토큰 포함)를 잽니다. **전체 점검**은 여기에 규칙으로 판정하는 능력 점검 — 도구
호출(가짜 조회 도구를 실제로 부르는지)·JSON 형식·수치 보존·한국어(영어 독백·한자 섞임)·생각 끄기·긴 문서(약 7천
토큰, 입력 처리 속도) — 을 더해 **단계 1회 예상 시간**(입력 8,000토큰 + 출력 1,500토큰)을 내고, 그 결과로 tier를
추천합니다(실측 예: exaone 7.8B는 도구 미지원 → 정밀·신속만, Ornith 35B는 모든 점검 통과·단계 예상 46초). Agent별
최적화 추천은 이 결과를 반영해, 도구를 쓰는 Agent에는 **도구 호출을 못 하는 모델을 제외**하고 수치 변형·한국어 혼입은
순위를 뒤로 미룹니다. 모델을 등록할 때는 모델 정보(최대 컨텍스트·층 구조·권장 샘플링)와 이 PC 메모리로 컨텍스트
한도·생성 옵션 추천값을 채울 수 있습니다.

### 운영 관리
통합 인박스(결재 대기·실행 실패·낮은 품질 경고·완료 알림을 한
곳에서), 매니저 대시보드, 감사 기록, 데이터 삭제/보관기간 정책.
admin의 **시스템 상태** 화면은 서버·DB 무결성·백업·디스크 여유·작업 큐·기본 모델과 Ollama 연결·외부 연결을
한 화면에 모으고, 바깥 감시 도구는 로그인 없이 `GET /health`로 상태를 확인합니다. 데이터는 **하루 한 번
자동 백업**되고(최근 7개, `hair backup`·`hair restore`), 로그인은 같은 아이디로 5번·한 주소에서 20번 틀리면
15분 막히며, 비밀번호를 바꾸면(본인·관리자 재설정) 다른 곳의 로그인이 모두 끊깁니다. 업무 요청의
**진행 보기**는 요청 → 할 일 → 배정 → 결과물 → 결재 단계와 할 일마다 "다음에 할 일" 버튼을 보여 줍니다.
비용 탭의 **AI 사용 한도**로 사용자별·조직 전체 월 한도(USD)와 viewer의 AI 호출 허용 여부를 정합니다.
**현황 → 자원 운용**은 할 일의 기한·예상 시간과 사람의 주당 시간·부재로 앞으로 4주 사람별 활용도, 기한 지남·임박,
인원 부족, 역할별 수요와 공급을 보여 줍니다(`resource_planning.py`). 매칭은 사람마다 동시 용량·부재 기간과 지금 부하를
반영합니다(`resource_capacity.py`). 퇴사·부재 전 **인계 점검**, 기간 **결재 위임**, 오래 머문 결재의 **자동 에스컬레이션**,
업무 요청별 **사람 인건비(추정)+AI 실측 비용과 예산**은 `resource_lifecycle.py`입니다. **현황 → 자원 분석**은 역할별 사람 vs AI
비교와 추천, 채워지지 않은 수요, 스킬 수요·공급, 팀, 업무 분배를 보여 줍니다(`resource_insights.py`). 스킬마다 숙련도(근거·확인·
본인 기재)를 두고 매칭에 반영합니다(`skill_levels.py`). 자원 운용의 **만약에**와 사람 인력 관리의 **인사 자료 가져오기**(CSV,
미리 보기 → 적용)는 `resource_scenarios.py`입니다.
**현황 → 프로세스 성과**는 파이프라인(업무 프로세스)마다 완료까지 걸린 시간을 AI 작업·사람 대기·그 밖으로
나누고, 한 번에 완료된 비율·재작업·자동 처리율(사람 결재 없이 넘어간 단계)·건당 비용·단계별 병목을 보여 줍니다.
예전 방식으로 한 건에 걸리던 **기준 시간**을 넣으면 AI가 맡은 작업량과 속도 비교가 나옵니다. 모두 이미 쌓이는
실행·결재 기록에서 계산합니다(`process_metrics.py`). 결재에서 단계를 반려하며 적은 사유와 되풀이되는 품질 기준 미달은
단계별 **개선 제안**이 되고, 운영자가 적용하면 다음 실행부터 그 단계 지시문에 "이전 실행에서 배운 점"으로 들어갑니다.
단계 설정 변경·배운 점 적용은 **변경 기록**에 남아 전·후 30일 지표로 비교하고 되돌릴 수 있습니다(`process_learning.py`).
결재 화면의 **결재 도우미**는 위험도·추천·점검 요약·이전 판과의 차이·확인할 점을 한 화면에 모으고, 추천이 사람 결정과
충분히 맞으면(낮음 20건·95% 승인) admin이 파이프라인별로 **낮은 위험 자동 승인**을 켤 수 있습니다(5건마다 1건 표본 검토,
조건이 깨지면 자동 중단, `approval_assist.py`). 파이프라인 관리의 **업무 설명으로 초안 만들기**는 하는 일을 글로 적으면 AI가
단계·담당·검토·사람 승인 위치를 제안하고 사람이 고쳐서 저장합니다(`pipeline_drafting.py`). 연동 설정의 **외부 입력 트리거**는
메일 도착·웹훅·다가오는 일정으로 파이프라인을 시작하고(들어온 내용은 외부 데이터로 표시, 그 실행은 쓰기 도구 차단,
`inbound.py`), **결재 후 실행 동작**은 사람이 "승인하고 실행"을 고를 때만 결과를 메일·Slack/Teams·JSON 웹훅으로 실제로
보냅니다(`stage_actions.py`). 프로세스 성과의 **처리 용량**은 작업 큐 기록으로 대기·실행 시간과 지금 맡기면 걸릴 시간을
보여 줍니다(`capacity.py`). 사람이 승인한 깨끗한 결과는 단계별 **좋은 결과 예시**로 골라 다음 실행에 형식 참고로
붙일 수 있고(외부 데이터를 읽은 실행은 제외), 사람 1시간 비용을 넣으면 파이프라인별 **건당 가치·AI 비용 대비 배수·추정 순절감**이
나옵니다.
**홈** 탭은 처리할 일·AI에게 일을 맡기는 방법·admin 관리 점검을 한
화면에 모읍니다. 맨 위 **AI에게 일 맡기기**에 할 일을 한 문장으로 적으면 빠른 질문·특정
Agent·파이프라인·정기 실행 중 맞는 방법을 이유와 함께 추천하고 버튼 하나로 시작합니다(대화를
열고 Agent를 초대해 메시지를 채워 두거나, 업무 요청·할 일을 만들어 파이프라인을 실행). 로그인하면
홈이 열리고, 메뉴는 업무 흐름대로 **일하기 · 검토·결재 · 현황▾**와(admin·manager는) **설정▾** 두 줄입니다. 대화·워크스페이스의 AI 응답은 **작성 중인 글이 그대로 미리
보이고**(생각 중 → 답변 작성 중), 실행 중인 파이프라인은 몇 번째 단계인지·지금
어느 Agent가 무엇을 하는지(작업·도구·위임)·경과 시간을 진행 막대와 함께 보여 줍니다. **연동 설정**에서는 개인 API 키(외부 시스템이 내 권한으로
API 호출), Slack·Teams 웹훅·메일 알림, 파이프라인 정기 실행, **이벤트 트리거**(파이프라인
완료·결과물 승인 → 다음 파이프라인, 앞 결과물을 넘겨 이어 붙임), 코드 저장소를 등록합니다. 비용 탭의 **실제 AI 사용량**은 업무별·Agent별 호출·토큰·금액과
파이프라인 평균 소요·사람 결재 수를 보여 줍니다. admin은 **기본 구성
점검**으로 운영 DB가 현재 버전의 기본 구성과 어디가 다른지 보고 빠진
것을 반영하며, **보조 작업 모델**로 언어·수치 교정 호출만 다른 모델로
보낼 수 있습니다(본 모델과 동시에 돌 수 있을 때만 대기가 줄어듭니다).
결과물은 다시 낼 때마다 **버전 이력**으로 묶여 이전 버전과 비교되고,
Word(.docx)로 내보낼 수 있습니다.
**부분 수정 요청**은 고른 섹션·구간만 AI가 다시 쓴 수정안을 원문과 비교해 보여 주고,
사람이 수락해야 반영합니다(나머지는 원문 그대로, 깨진 낱말은 수락 전에 경고).
결과물은 **Word·Excel(표마다 시트, 숫자는 숫자로)·PowerPoint(제목마다 슬라이드, 표는
표로)**로 내보낼 수 있습니다.
목록이 있는 화면은 전부 검색 필터와 정렬 가능한 헤더를 기본으로
제공합니다. 모든 LLM 호출의 실제 토큰 사용량이 provider·모델별로
기록되고("모델 레지스트리"의 "실제 사용량"), 모델별 단가를 입력하면
금액도 계산됩니다(단가가 없는 모델은 토큰 수만 — 금액을 지어내지
않습니다). 조직 정책에서 사번 형식과 **결과물 언어**(한국어·영어·
일본어·중국어·베트남어)를 정할 수 있습니다.

### 결과물 뷰어
복사·다운로드·미리보기/원본 전환이 되는 결과물 카드입니다. 마크다운은
표·인용문·이미지까지 그대로 렌더링하고, 코드는 언어를 인식해 문법
강조가 적용되며, 코드 블록이 `mermaid`/`chart`로 표시돼 있으면
다이어그램·차트로 바로 그려줍니다. HTML 결과물은 격리된 영역에서
안전하게 렌더링됩니다.

## 5. 아직 안 되는 것(알려진 한계)

- **메신저에서 바로 승인하는 양방향 연동 없음** — Slack·Teams로는
  결재 대기·파이프라인 완료 같은 알림을 보낼 수 있고(수신 웹훅), 외부
  시스템은 개인 API 키로 HAIR API를 부를 수 있지만, 메신저 안에서 바로
  승인하는 연동은 아직 없습니다(Git 저장소는 읽기·로컬 커밋·브랜치 push·
  PR 자동 생성까지 됩니다).
- **외부 업무 시스템은 읽기만** — 사내 DB·메일 수신함·캘린더는 등록하면
  Agent가 조회할 수 있지만 읽기 전용입니다(DB 쓰기·메일 발송/정리·
  일정 생성은 하지 않음 — 회신·일정은 결과물 초안으로 제안). PostgreSQL·
  MySQL·IMAP·iCal 접속은 형식·가짜 서버로 검증했고 실제 사내 시스템
  접속은 설치처에서 "연결 확인"으로 확인해야 합니다.
- **실제 실행 검증의 범위** — Python·JavaScript 테스트와 HTML 화면은 실제로 실행하지만(v0.3.2), TypeScript·JSX와
  그 밖의 언어는 구조·구문까지만 봅니다. 코드 테스트는 Docker가 있어야 돌고(없으면 미평가 — 관리자가 로컬 실행을
  허용하지 않는 한), 화면 실행은 Playwright·Chromium 설치가 필요합니다. 화면 점검은 버튼 누르기까지라 입력이 필요한
  기능 흐름은 사람이나 QA 단계가 확인해야 합니다.
- **화면은 데스크톱 우선** — 모든 화면이 폰 폭(약 400px)에서 가로로 넘치지 않고 표는 표 안에서 옆으로 넘겨 볼 수
  있게 맞췄지만(화면 테스트로 확인), 입력이 많은 관리 화면은 넓은 화면에서 쓰는 것을 전제로 합니다.
- **한 서버·한 DB 구성** — SQLite 하나와 작업 프로세스 하나로 동작합니다. 사내 팀 규모에는 충분하지만, 동시 사용자가
  많아지면 PostgreSQL 지원과 여러 작업 프로세스가 필요합니다(계획 단계). 로그인 잠금 기록은 서버 메모리에 있어
  서버를 다시 켜면 풀립니다.
- **다크 모드 없음(의도적)** — 과거 시도에서 폼 컨트롤과 충돌하는
  버그가 실제로 발견돼, 지금은 밝은 화면 전용으로 고정해뒀습니다.

그 외 세부적인 결정 배경이나 과거에 고친 버그 이력은 git 커밋
로그에 날짜·요청 내용과 함께 남아 있습니다.
