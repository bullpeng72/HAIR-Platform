# 관리자·사용자 고유 업무 vs 공통 업무 분류 — 외부 사례 리서치 기반 재분석

사용자 요청(2026-09-29): "HAIR(사람과 AI Agent 협업, 협업을 위한 리소스
관리 등) 관점에서 외부 사례들을 조사하고 프로세스를 다시 분석해
관리자와 사용자 고유 업무와 공통 업무를 구분해줘. (여러 사용자 대상
표준화 및 관리가 필요한 업무는 관리자 역할로 배정 등)"

이 문서는 (1) 외부 서비스 4곳의 실제 admin/user 권한 분리 방식을
리서치하고, (2) HAIR-Platform의 **실제 코드**(`require_role()` 호출
전수 조사, `app.py` 전체 라우트)를 다시 훑어 기능을 3그룹(관리자 고유
/ 관리자+매니저 공용 / 전체 공통)으로 분류하며, (3) 외부 사례에서 뽑은
원칙과 HAIR 현재 설계를 대조해 실제로 어긋나는 지점을 찾는다. **기획
문서다 — 코드 변경 없음.** 어떤 항목을 고칠지는 사용자 확인 후 별도
진행한다.

## 1. 외부 사례 리서치

### 1-1. GitHub Copilot(AI 코딩 에이전트, 엔터프라이즈) — HAIR와 가장
가까운 사례

Admin이 **조직 전체 차원에서 AI 에이전트가 할 수 있는 행동의 정책**
(shell 명령·파일 접근·네트워크 도메인)을 설정하고, 이 제한은 **개별
사용자·워크스페이스 설정으로 약화시킬 수 없다**("Managed restrictions
can't be weakened by user or workspace settings, auto-approval, or
previously saved approvals"). 조직/엔터프라이즈 설정에서 Copilot
활성화 범위(전체/팀별/개별)도 admin이 결정한다.

→ **원칙 1: AI 에이전트가 조직 차원에서 뭘 할 수 있는지의 "정책"은
admin 전용이며, 일반 사용자가 override할 수 없어야 한다.**

### 1-2. Asana / monday.com — 협업 툴의 표준적 admin/member 분리

Admin은 **보안·과금·사용자/팀 관리**, 그리고 "자동화·연동(integration)
생성, API 토큰 발급, 워크스페이스 생성" 같은 **조직 전체에 영향을 주는
기능 on/off**를 관리한다. Member는 배정된 팀/프로젝트 안에서 프로젝트·
업무를 만들고 협업하는 일상 업무를 한다.

→ **원칙 2: 사용자·조직 구조 관리(초대/역할 지정/billing)와, 조직
전체가 공유하는 "기능 카탈로그"(연동·자동화·API 접근)를 여는 것은
admin 전용이다.**

### 1-3. LangSmith(AI Ops 플랫폼) — 아직 성숙하지 않은 세분화

기본 역할은 Admin(워크스페이스 내 모든 리소스 전체 접근)과
Viewer(읽기 전용)뿐이고, 세분화된 RBAC(커스텀 역할)은 **엔터프라이즈
전용 유료 기능**이다. SSO/SCIM(사용자 자동 프로비저닝)도 admin/엔터
프라이즈 영역이다.

→ **원칙 3: AI 플랫폼은 역할을 잘게 쪼개기보다 "admin(전권) vs
나머지(제한)"로 단순하게 시작하는 경우가 많다 — 세분화는 규모가 커질
때 나중에 얹는 것이지, 처음부터 과도하게 잘게 나누지 않는다.**

### 1-4. ServiceNow ITSM — 카탈로그 정의 vs 요청/승인 참여의 분리

카탈로그 항목·워크플로우 "정의"는 기술 지식이 필요한 admin/catalog
admin 영역이라고 명시하면서도, 커뮤니티 자체가 "admin 역할을 너무
잘게 쪼개는 건(catalog admin과 admin을 반씩 나누는 식) 효과적이지
않다"고 경고한다. 반면 **승인만 하는 사람**은 `approver_user`처럼
"자신이 승인자로 지정된 요청만" 처리하는 **좁게 스코프된 별도 역할**로
분리돼 있다 — admin 권한 전체를 안 줘도 승인 참여는 가능하게 한다.

→ **원칙 4: "정의/설정"은 admin, "승인 같은 제한된 참여"는 admin
전체 권한 없이도 스코프를 좁혀 가능하게 한다.**
→ **원칙 5: admin 역할 자체를 과도하게 세분화하는 것은 오히려 비효율
적이다 — 소수의 명확한 역할이 낫다.**

## 2. HAIR-Platform 현재 프로세스 실측 재분류

`app.py`의 `require_role()` 호출을 전수 조사했다(추측이 아니라 실제
코드 라인 기준).

### 2-1. 관리자(admin) 고유 — 13개 엔드포인트

| 기능 | 엔드포인트 |
|---|---|
| 사용자 계정 생성 | `POST /api/users` |
| 상사(manager_id) 지정 | `PATCH /api/users/{id}/manager` |
| 전체 사용자 목록 조회 | `GET /api/users` |
| 업무 요청(브리프) 완전 삭제 | `DELETE /api/briefs/{id}` |
| 할 일(Task) 완전 삭제 | `DELETE /api/briefs/{id}/tasks/{id}` |
| 사람 인력 레코드 완전 삭제 | `DELETE /api/human-pool/{id}` |
| 도구 완전 삭제 | `DELETE /api/tool-pool/{id}` |
| 스킬 완전 삭제 | `DELETE /api/skill-pool/{id}` |
| Agent 온보딩 승인 | `POST /api/agent-pool/{id}/onboard` |
| Agent 오프보딩 | `POST /api/agent-pool/{id}/deprecate` |
| Agent 완전 삭제 | `DELETE /api/agent-pool/{id}` |
| Agent 성과 점수 수동 입력 | `POST /api/agent-pool/{id}/performance` |
| Agent 비용 수동 입력 | `POST /api/agent-pool/{id}/cost` |

**공통 성격**: (a) 조직 구조·계정 자체를 다룸, (b) 되돌릴 수 없는
완전 삭제, (c) Agent를 조직에 편입/제외시키는 결정, (d) 평가적 판단이
들어가는 수치의 "수동 확정". → **원칙 1·2·4와 정확히 일치**하는
설계다.

### 2-2. 관리자+매니저 공용(운영 업무) — 약 29개 엔드포인트

브리프 Task 분해(F2), 배정 요청·승인(F5-F7), Human/Agent Pool
등록·조회·수정(삭제 제외), Tool/Skill Pool 등록·조회(삭제 제외),
AI 에이전트 생성(F4), Crew 실행, 비용/공정성/활동 기록 조회, 매니저
대시보드, Agent 모델 설정·지식 색인. 지난 대화에서 "관리자 도구"라는
메뉴 그룹 라벨 아래 있지만 실제로는 매니저도 쓰는 10개 탭이 정확히
여기 해당한다.

### 2-3. 전체 공통(로그인만 하면, viewer 포함) — 약 10개 엔드포인트

`GET /api/me`, 로그인/로그아웃, 인박스, 내 업무, 브리프 목록 조회,
할 일 목록 조회, 결과물 조회(참가자 또는 admin/manager), 인력 검색,
조직도, 결재함 조회(scope=mine/inbox).

### 2-4. admin/manager/member 공용(viewer만 제외) — 3개 엔드포인트

`POST /api/briefs`(브리프 제출), `POST /api/approvals`(배정 요청),
`GET /api/performance-review`(본인 성과 조회). Viewer는 "만들거나
요청하는" 행위 자체를 못 한다 — 순수 조회 역할이라는 설계가 일관되게
적용돼 있다.

## 3. 원칙 대조 — 잘 지켜지는 것과 실제 갭

### 3-1. 잘 지켜지는 것

- 사용자 계정/조직 구조, 완전 삭제, Agent 온보딩/오프보딩, Agent
  비용·성과 수동값 — **전부 admin 전용**(§2-1). 원칙 1·2·4와 정확히
  일치.
- 4개 역할(admin/manager/member/viewer)뿐, 세분화된 커스텀 역할 없음
  — 원칙 3·5("과도한 세분화는 비효율")와 일치. HAIR는 이미 단순한
  쪽을 택하고 있다.
- 배정 승인은 "다단계 결재라인"(F7)으로 스코프가 좁혀져 있어(자기
  라인만 처리), admin 권한 전체 없이도 매니저가 승인에 참여
  — 원칙 4("승인은 스코프를 좁혀 참여")와 일치.

### 3-2. 실측으로 발견한 갭 2건

**갭 1 — Tool Pool(특히 MCP 서버 등록)이 admin 전용이 아니다.**
`POST /api/tool-pool`(`app.py:1059`)은 admin+manager 공용이다. 그런데
이 엔드포인트로 등록하는 `mcp_stdio`/`mcp_remote` 도구는, Pool
Registry 화면 자체의 안내 문구가 이미 경고하듯("이 두 종류는 Agent가
실행될 때마다 실제로 서버에 접속을 시도"), **Agent가 실행될 때 실제
외부 프로세스/네트워크에 접속하는 능력**을 조직 전체 Agent에 부여하는
행위다. 원칙 1(GitHub Copilot: "AI 에이전트가 할 수 있는 행동의 정책은
admin 전용, 일반 사용자가 override 불가")과 대조하면, HAIR는 이
영역을 매니저에게도 열어두고 있다 — 매니저 한 명이 잘못된/악의적인
MCP 서버 주소를 등록하면 그 스킬을 가진 **모든 Agent**의 실행이 그
주소로 접속을 시도하게 된다(조직 전체 영향, admin 승인 없이).

**갭 2 — Human Pool과 Agent Pool의 "비용/성과" 수정 권한이 비대칭이다.**
Agent의 `performance_score`/`cost_estimate`는 전용 엔드포인트로
admin만 수정 가능하다(§2-1). 반면 Human Pool의 같은 두 필드는
`PATCH /api/human-pool/{id}`(`app.py:326`, admin+manager 공용)
하나로 묶여 있어 **매니저가 자유롭게 수정할 수 있다**. 사람 쪽은
NF9(사전 동의)라는 별도 보호장치가 있어 "노출" 축은 보호되지만,
"누가 그 값을 설정할 수 있는가" 축에서는 Agent보다 느슨하다 — 이게
의도된 차이(매니저가 원래 팀원 인사 정보를 다루는 건 자연스러움)인지,
아니면 Agent 쪽만 나중에 강화되고 Human 쪽은 그대로 남은 비대칭인지
재확인이 필요하다.

**참고(새 발견 아님, 지난 대화에서 이미 나온 것)**: "관리자 도구"
메뉴 그룹 라벨이 실제 권한(admin+manager 공용 10개 + admin 전용 1개)과
안 맞아 혼동을 유발한다는 점도 이 분류와 같은 뿌리의 문제다 — §2-2의
"운영 업무"라는 실제 성격을 라벨이 못 담고 있다.

## 4. 최종 분류 요약표

| 분류 | 판단 기준(이번 리서치로 뽑은 원칙) | HAIR 현재 해당 기능 |
|---|---|---|
| **관리자 고유** | 조직 구조/계정 자체, 되돌릴 수 없는 삭제, Agent 조직 편입/제외 결정, 평가적 수치의 수동 확정 | §2-1의 13개 |
| **관리자+매니저 공용(운영)** | 일상적 리소스 운영(등록·조회·수정), 팀 단위 승인 참여, 실행 트리거 | §2-2의 ~29개(**단, 갭 1의 MCP 도구 등록은 재검토 대상**) |
| **전체 공통(viewer 포함)** | 조회·본인 업무 확인 | §2-3의 ~10개 |
| **admin/manager/member 공용** | "만들기/요청하기"(viewer는 제외) | §2-4의 3개 |

## 5. 다음 액션 제안(열린 질문 — 진행 전 확인 필요)

1. **갭 1(MCP 도구 등록)**: `kind IN ('mcp_stdio','mcp_remote')`인
   Tool Pool 등록만 admin 전용으로 좁힐지, 아니면 현행 유지(매니저도
   가능)로 둘지 — 등록 즉시 접속을 시도하는 게 아니라 "그 스킬을 가진
   Agent가 실행될 때"라는 지연된 리스크라 시급도는 낮지만, 원칙상은
   admin 전용이 더 맞다.
2. **갭 2(Human/Agent 비용·성과 비대칭)**: 의도된 설계(매니저의 정상
   인사 업무)로 확정하고 문서에만 명시할지, 아니면 Human Pool
   cost_estimate도 admin 전용으로 좁힐지.
3. **라벨링**: "관리자 도구" → "운영 도구" 같은 이름으로 바꿔 매니저
   접근 가능 범위를 명확히 할지(지난 대화에서 이미 제안됨, 아직 미결정).

이 문서는 분류·분석까지다 — 위 3건 중 진행할 항목을 알려주면 각각
별도로 구현한다.

## 6. 결정 및 구현(2026-09-29)

사용자가 "결정이 필요한 내용들을 종합적으로 정리해줘" 요청 이후, 이
문서의 갭 1·2를 포함한 총 8건(이 문서 밖 `docs/SPEC.md` §12 오픈
이슈 6건 포함)을 한 번에 확인받아 전부 구현했다 — 상세는
`docs/LIMITS.md` §47 참고.

- **갭 1(MCP 도구 등록)**: **(a) admin 전용으로 좁힘**을 선택. `kind IN
  ('mcp_stdio', 'mcp_remote')`인 `POST /api/tool-pool` 요청만 admin
  전용이고, native 도구 등록은 매니저도 여전히 가능하다.
- **갭 2(Human/Agent 비용·성과 비대칭)**: **(b) Human Pool도 admin
  전용으로 좁힘**을 선택. `PATCH /api/human-pool/{id}`의 `cost_estimate`
  필드와 `POST /api/human-pool/{id}/performance`를 admin 전용으로
  바꿔 Agent Pool과 대칭을 맞췄다(다른 필드는 매니저의 정상 인사
  업무로 그대로 둠).
- **라벨링**: §37에서 이미 "운영 관리"로 개명 완료(이 결정보다 먼저
  해결된 항목).
