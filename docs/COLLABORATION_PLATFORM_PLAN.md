# 사람-AI 협업 플랫폼 기획안 — HAIR-Platform 다음 단계

사용자 요청(2026-09-28): "HAIR의 핵심은 사람과 AI Agent가 협업하여 일하는
구조야. 사람이 한 결과물을 AI Agent에게 전달, 사람이 HITL(Human-in-the-
loop), HOTL(Human-on-the-loop)로 AI Agent 업무 감독 등이 가능해야해" →
"HAIR 관련으로 외부 리서치 및 [flow.team 등] 유사 서비스를 분석해 사람과
AI가 협업하는 플랫폼을 기획해줘".

이 문서는 두 단계로 구성된다: (1) 현재 HAIR-Platform 실측 갭 분석(직전
세션에서 코드를 직접 읽어 확인), (2) 외부 서비스 6곳 리서치로 뽑아낸
공통 패턴을 근거로 한 3단계 개선 로드맵. **추정이나 마케팅 문구가 아니라
실제 코드 인용·실제 제품 기능 설명에 근거한다.**

## 1. 현재 HAIR-Platform의 실측 갭

직전 세션에서 코드베이스를 직접 조사해 확인한 사실(파일:라인 근거는
대화 기록 참고, 핵심만 요약):

| 패턴 | 현재 상태 | 근거 |
|---|---|---|
| 사람→AI 결과물 전달 | **없음** | `human_pool` 테이블에 산출물 저장 필드 자체가 없음(`db.py:44-55`). `run_crew()`의 `Task.context` 체이닝(`crew_runtime.py:274-284`)은 Agent 산출물→Agent 입력만 연결. 업로드/첨부/문서 개념 전체 코드베이스에 없음 |
| HITL(산출물 승인) | **배정 승인만 있음, 산출물 승인 없음** | `approvals.subject_type`은 `"assignment"`(F6 배정)·`"brief"`(F1 브리프) 둘뿐(`app.py:1223`이 다른 값을 명시적으로 거부). Agent가 만든 결과물은 생성 즉시 저장되고 승인/반려/수정 게이트가 전혀 없음. CrewAI의 `Task.human_input=True`를 실제로 검토했으나 블로킹 `input()`이라 웹서버와 비호환이라 의도적으로 보류함(`docs/LIMITS.md` §17) |
| HOTL(실행 중 감독) | **완전 동기 블로킹, 개입 지점 없음** | `crew.kickoff()`(`crew_runtime.py:158,359`), LLM 호출 전부 스트리밍 없는 단일 블로킹 호출. `/api/crew/run` 등은 HTTP 요청 안에서 끝까지 실행 후 반환(job ID 폴링 구조 아님, `docs/LIMITS.md` §3). `task_callback`은 메모리에만 쌓고 감사로그는 Crew 전체 종료 후 일괄 기록(`crew_runtime.py:317,385-421`). 일시정지/취소/재지시 엔드포인트 없음 |

**결론**: F5~F7(누구를 배정할지 승인)은 잘 갖춰져 있지만, "업무 내용
자체"에 대한 사람-AI 협업(결과물 릴레이, 산출물 리뷰, 실행 중 개입)은
설계에 없다.

## 2. 외부 서비스 리서치

### 2-1. flow.team (사용자가 지목한 서비스)

한국 팀 협업/메신저+업무관리 SaaS. AI 기능은 확인됐으나 **HITL/HOTL
관점에서는 얕다** — AI 프로젝트 템플릿 생성, 채팅 명령/엑셀→업무 변환,
반복업무 챗봇, 문서 초안, 일일 요약, 권한 준수 통합검색 정도이고
월 50회 사용량 제한이 있다. **AI 산출물에 대한 별도 승인/편집 게이트나
실시간 가시성 기능은 찾지 못했다** — 구조상 AI 산출물이 그냥 일반
"게시물/업무"로 바로 등록되고, 사람이 그걸 다른 게시물처럼 나중에 보고
고치는 방식으로 보인다(전용 리뷰 메커니즘이 따로 없다는 뜻). 1차 리서치
수준(검색 스니펫 기반)이라 신뢰도는 아래 항목들보다 낮게 잡아야 한다.

### 2-2. GitHub Copilot Coding Agent — 가장 근접한 사례

- **핸드오프**: 사람이 이미 만든 GitHub 이슈를 그대로 Copilot에게
  할당(이슈 = 사람이 만든 작업물이 AI 입력이 되는 실제 사례).
- **HOTL**: GitHub Actions 워크스페이스에서 저장소를 탐색·계획하고,
  **draft PR에 커밋을 순차적으로 실시간으로 푸시** — "작업이 실시간으로
  일어나는 걸 보고, 이상하면 언제든 개입할 수 있다."
- **HITL(산출물 승인)**: 작업은 draft PR 형태로만 존재하고, **머지 전
  사람 리뷰가 필수**다. 여러 차례 리뷰/수정 사이클이 일반적.
- **자기 승인 방지**: "Copilot에게 작업을 할당한 사람은 그 결과 PR을
  본인이 승인할 수 없다" — **HAIR의 ADR 결정 3-A(self-approval 방지)와
  원리가 완전히 같다.**

### 2-3. Relay.app — 가장 깔끔한 선언적 패턴

- AI 스텝마다 "사람이 이 AI 출력을 리뷰해야 하나?" **토글이 스텝 단위로
  붙어 있다** — 별도의 전역 승인 시스템이 아니라 스텝에 부착 가능한
  속성.
- 트리거되면 **워크플로가 멈추고**, 리뷰어에게 맥락과 함께 결과물을
  전달(이메일/Slack)하며 **승인/반려/수정** 버튼을 준다. 클릭하면 워크플로가
  재개되거나 중단된다.
- 같은 메커니즘을 "실행 전 승인"·"누락 데이터 수집"·"작업 배정"·"발송 전
  리뷰/수정"에 재사용한다 — **승인/편집이 "1급 워크플로 노드 타입"**이다.

### 2-4. Lindy.ai

- 액션 단위 "확인 요청" — 에이전트가 그 지점까지 실행하고 멈춰서
  기다림(이메일/인앱 알림으로 승인).
- 조건부 에스컬레이션 규칙(사용자가 "사람"을 요청, 반복 실패, 금지
  주제)으로 라이브 대화를 사람에게 넘김.
- 실시간 활동 피드는 확인 못 했다(사후 리포팅만 확인).

### 2-5. LangGraph `interrupt` — 실제 엔지니어링 메커니즘

- 노드가 `interrupt(value)`를 호출하면 `GraphInterrupt`가 발생해 실행이
  멈추고, 그 값이 클라이언트로 전달된다.
- **체크포인터가 그래프의 전체 상태(어느 노드, 모든 상태값, 정확한 실행
  지점)를 영속화**해서 실행을 무기한 중단해둘 수 있다.
- 사람이 `Command` 객체로 응답하면, **같은 노드를 처음부터 재진입해
  interrupt 지점까지 재생(replay)한 뒤** 사람의 입력으로 교체해 이어간다.
- **"평소엔 동기적인 에이전트 루프를, HTTP 요청을 계속 열어두지 않고도
  멈출 수 있게 만드는" 방법에 대한 구체적 답**이다: 상태를 외부에
  영속화하고, 재진입/재생으로 중단 지점까지 도달한 뒤, 주입된 입력으로
  재개한다.

### 2-6. Asana AI Teammates

- **AI가 사람과 똑같은 방식으로 업무에 배정된다**("팀원에게 업무를
  맡기듯 AI Teammate에게 배정") — **HAIR가 이미 가진
  `resource_type: human|agent` 다형성과 원리가 완전히 같다.**
- AI가 작업을 하위작업으로 쪼개고, **사람이 쓰는 것과 같은 업무 댓글
  스레드에 진행상황을 남긴다** — "팀이 언제든 초안을 리뷰하거나 수정을
  요청할 수 있다."
- "AI Studio"(반복작업 완전자동화)와 "AI Teammates"(판단이 필요한
  협업작업, 사람이 결과를 리뷰·가이드·의사결정을 직접 가져올 수 있음)를
  명확히 구분한다. 복잡/모호한 요청은 자동으로 사람 리뷰 플래그가
  붙는다.

### 2-7. 공통 패턴 (가장 중요한 발견)

**여기서 조사한 어떤 제품도 "단일 동기 RPC 호출이 끝난 결과물을
반환"하는 방식으로 이 문제를 풀지 않는다.** 잘 되는 제품은 다음 두
형태 중 하나(또는 둘 다)를 쓴다:

1. **공유 스레드/피드 모델** (GitHub PR 커밋, Asana 업무 댓글, Flow
   게시물): AI의 작업을 사람이 이미 보고 있는 **같은 객체에 점진적인
   post/commit/comment로 쪼개 넣는다** — "실시간 가시성"과 "언제든
   개입"이 별도 모니터링 기능이 아니라 사람과 협업할 때 쓰는 것과 같은
   UI 표면이라서 저절로 따라온다.
2. **명시적 일시정지-스텝 모델** (Relay의 스텝별 리뷰 토글, Lindy의
   "확인 요청", LangGraph의 `interrupt`+체크포인트): 워크플로/그래프를
   상태가 영속화되는 스텝의 나열로 모델링하고, 어떤 스텝이든 "여기서
   사람 응답 전까지 멈춰라"를 선언할 수 있다 — 이건 AI 실행 자체가
   태생적으로 재개 가능(resumable)/비동기여야 가능하지, 단일 블로킹
   함수 호출 위에 나중에 덧붙일 수 있는 게 아니다.

두 패턴 모두 "AI의 작업 단위"를 **상태를 가지고 점진적으로 보이며
승인/편집 게이트를 붙일 수 있는 객체**로 다뤄야 한다는 공통 요구를
갖는다 — 지금 HAIR처럼 "실행이 끝나야 문자열 하나가 한 번 나오는 불투명한
블로킹 호출"로는 안 된다.

## 3. HAIR-Platform이 이미 가진, 재사용 가능한 기반

다행히 완전히 새로 설계할 필요는 없다 — 조사해보니 HAIR는 이미 위
패턴들의 핵심 전제 두 가지를 갖고 있다:

1. **`assignments.resource_type: 'human' | 'agent'` 다형성** — Asana
   "AI를 사람처럼 배정"과 원리가 동일하다. F6/F7이 이미 사람이든
   Agent든 같은 배정·승인 파이프라인을 태운다.
2. **ADR 결정 3-A(자기 승인 방지)** — GitHub Copilot의 "할당자는 본인
   결과물을 승인 못 함"과 원리가 동일하다. 이미 검증된 코드(`app.py`
   self-approval 체크)가 있으니 산출물 승인에도 그대로 확장하면 된다.
3. **Skill Pool의 skill_tags 매칭 조회 로직**(§18, `skill_pool WHERE
   name IN (...)`) — 지금은 Agent에게 Tool을 자동으로 붙이는 데
   쓰지만, 같은 조회를 "사람에게 지식을 프롬프트로 주입"하는 데도 그대로
   재사용할 수 있다(4-3).

부족한 건 "산출물을 담을 그릇"(공유 스레드/피드에 해당하는 엔티티)과
"실행을 멈췄다 재개할 수 있는 상태 저장 구조"(LangGraph의 체크포인트에
해당) 두 가지다.

## 4. 제안 로드맵 — 3단계

### Phase A — 결과물(Deliverable) 엔티티: "결과물 전달" 문제 해결

사용자 추가 요청(2026-09-28): "팀이 승인되고 특정 HAIR로 해결할 업무가
확정되면 해당 업무가 내 업무 메뉴에서 확인되고, 해당 업무의 경우
사람-에이전트 협업 프로세스로 펼쳐지고 입출력을 처리할 수 있도록" —
이 요청은 Phase A를 "테이블 설계"에서 그치지 않고 **진입 흐름(배정 확정
→ 내 업무 노출 → 협업 워크스페이스로 펼침)까지 구체화**하라는 것이므로,
아래 4-1을 Phase A의 핵심 산출물로 명시한다.

#### 4-1. 진입 흐름 — "배정 확정" → "내 업무" 노출 → 협업 워크스페이스

1. **트리거**: F7 결재가 승인돼 `assignments.status = 'confirmed'`가 되는
   순간(이미 존재하는 이벤트, 새로 만들 필요 없음).
2. **노출(신규)**: 지금 "내 업무" 그룹(업무 요청/결재/인력 검색/조직도/
   성과 리뷰)에는 "내가 실제로 처리해야 할 확정 업무 목록"이 **없다** —
   이 갭을 메우는 신규 탭 `myWork`("내 할당 업무")을 "내 업무" 그룹에
   추가한다. 신규 엔드포인트 `GET /api/my-work`가 다음 두 경우를 모두
   반환한다:
   - 내가 **확정된 human 배정의 당사자**인 task(`assignments.resource_type
     = 'human' AND human_pool.user_id = 나`) — "내가 직접 할 일".
   - 내가 **확정된 agent 배정의 요청자**인 task(`assignments.resource_type
     = 'agent' AND assignments.requested_by = 나`) — "내가 AI에게 맡긴
     일"(감독 대상). 관리자/매니저가 Agent에게 업무를 맡겼다면 그
     Agent가 하는 일을 계속 들여다볼 진입점이 필요하기 때문에 이
     경우도 포함한다.
   - member/manager/admin은 위 조건에 걸리는 자기 업무를 보고, viewer는
     기존 RBAC 관례대로 조회만 가능하게 한다(신규 승인/쓰기 권한 추가
     아님).
3. **펼침(신규, "사람-에이전트 협업 워크스페이스")**: `myWork` 목록에서
   행 하나를 클릭하면, 그 task 전용 화면이 펼쳐진다 — 이게 바로 4-2의
   결과물 타임라인이다. **사람 배정 task든 Agent 배정 task든 같은 화면
   컴포넌트를 쓴다**(사람이 산출물을 올리는 쪽이냐 Agent 실행을 트리거/
   리뷰하는 쪽이냐만 다름) — GitHub Copilot의 "이슈 하나 = PR 스레드
   하나"와 같은 원칙: task 하나 = 협업 워크스페이스 하나.

#### 4-2. 결과물(Deliverable) 엔티티 — "입출력 처리"의 실제 구현

- 신규 테이블 `deliverables`: `id, task_id, author_type(human|agent),
  author_id, content, kind(draft|final), created_at`.
- 신규 테이블 `deliverable_comments`(공유 스레드/피드 모델 차용): 같은
  `task_id` 위에서 사람과 Agent가 번갈아 post를 남기는 타임라인.
- **입력 처리**: 협업 워크스페이스에서 사람이 텍스트/산출물을 올리면
  `deliverables`에 `author_type='human'`으로 저장되고, 그 화면에 있는
  "이 내용으로 Agent 실행" 버튼이 `crewai_agent_generator()`/`run_crew()`
  를 **이 task로 스코프해서** 트리거한다.
- **출력 처리**: `crewai_agent_generator()`/`run_crew()`가 Task
  description을 조립할 때, 그 task에 이미 있는 사람 작성 deliverable을
  **자동으로 프롬프트 컨텍스트에 포함**시키고(현재는 이 연결이 전혀
  없음, `crew_runtime.py` 수정 필요), 실행 결과는 다시
  `author_type='agent'`인 deliverable로 같은 타임라인에 쌓인다 — 사람이
  새로고침 없이 "AI가 방금 뭘 냈는지"를 그 자리에서 본다.
- Web UI: "내 업무 → myWork" 탭에서 펼친 화면이 곧 "결과물 타임라인"
  이다(할 일마다 사람/Agent 산출물이 시간순으로 보임) — 별도 화면을 두
  곳에 중복 구현하지 않는다.

#### 4-3. Skill/Tool 역할 재정의 — 사람의 LLM 활용 업무 지원 (사용자 요청,
     2026-09-28)

사용자 요청: "사람이 하는 업무의 경우 단순 simple_llm 호출을 포함하고
이 경우 사람이 업무 지식 기반인 skill을 사용할 수 있도록 하려고 해...
향후로는 skill은 사람이 LLM 활용업무 처리에, Tool은 AI Agent가
사용하도록." 즉 협업 워크스페이스(4-1)에서 사람이 처리하는 업무도
LLM 호출을 보조 수단으로 쓸 수 있어야 하고, 그때 참고할 지식 베이스로
**Skill Pool의 역할을 사람 쪽으로 재정의**한다.

**역할 재정의**:

| | 지금(§18/§20 구현) | 앞으로 |
|---|---|---|
| **Skill(Skill Pool)** | Agent의 skill_tags 매칭용 — `augmentation_mode='tool'`이면 매칭된 Agent에게 Tool을 자동 부착 | **사람이 LLM 활용 업무를 할 때 쓰는 지식 베이스** — 워크스페이스의 "LLM으로 도와줘" 호출에 컨텍스트로 주입 |
| **Tool(Tool Pool)** | AI Agent가 CrewAI 실행 중 호출하는 실행 가능한 함수(native/MCP) | **AI Agent 전용으로 그대로 유지** — 변화 없음 |

**구체적으로 무엇이 바뀌나**:

- 협업 워크스페이스(4-1)에 **"LLM으로 이 업무 도와줘" 버튼**을
  추가한다 — 누르면 `llm.call_llm()`을 1회 호출한다(F4의 `simple_llm`과
  같은 성격의 단발성 호출이지만, 이번엔 신규 Agent를 만드는 게 아니라
  **사람의 현재 task를 돕는 용도**). 결과는 사람이 검토·편집한 뒤
  `deliverables`에 `author_type='human'`으로 올린다 — LLM이 초안을
  도왔어도 최종 책임/소유는 사람에게 남는다(에이전트 산출물과 구분).
- **Skill 선택/자동 주입**: 그 task의 `required_skills`와 이름이
  일치하는 Skill Pool 항목이 있으면, 그 지식(`description`, 그리고
  향후 필요하면 추가할 상세 지식 필드)을 이 LLM 호출의 시스템 프롬프트에
  자동으로 포함한다 — Agent의 skill_tags 매칭과 **같은 조회 로직**
  (`skill_pool WHERE name IN (...)`)을 재사용하되, 그 결과로 "도구를
  붙이는" 대신 **지식 텍스트를 프롬프트에 주입한다**는 점이 다르다.
- **이미 나와 있는 실사례**: §20에서 시드해둔 18개 Agent-Evaluator 절차
  스킬이 이 원칙을 그대로 보여준다 — `tdd-ai-workflow-checklist`·
  `spec-driven-artifacts` 같은 17개는 원래부터 "사람(또는 Claude Code
  세션)이 읽고 따르는 절차"였지 CrewAI Agent가 함수로 호출할 도구가
  아니었기 때문에 `augmentation_mode='none'`으로 등록해뒀다 — 이번
  재정의는 그 직관을 공식 원칙으로 승격하는 것뿐이다. 다만
  `recommend-fix-workflow` 하나는 실제 MCP Tool로도 승격해뒀는데,
  이건 "사람도 Agent도 둘 다 쓸 수 있는 경계 사례"로 남겨둔다(강제로
  양자택일하지 않는다 — 같은 지식이 사람에게는 Skill로, Agent에게는
  Tool로 동시에 노출될 수 있다).

**마이그레이션 고려사항(오픈 이슈로 남김, 이 문서에서 미리 정하지
않음)**:

- 지금 있는 "Agent의 skill_tags → Tool 자동 부착" 기능(F6/§18)은
  Skill Pool을 매개로 동작한다. 이걸 그대로 유지할지, 아니면 Tool
  Pool에 `applicable_skill_tags` 같은 필드를 직접 둬서 Skill Pool을
  거치지 않고 Agent-Tool 매칭을 분리할지는 **별도 ADR이 필요한 결정**
  이라 여기서 미리 정하지 않는다.
- 최소한 "사람용 지식 스킬"과 "Agent 자동연결용 스킬"이 Web UI
  "도구/스킬 Pool" 탭에서 뒤섞여 보이면 혼란스러우므로, 이 재정의를
  실제로 진행하기 전에 **"용도: 사람 지원 / Agent 자동연결" 배지
  구분**을 먼저 넣는 것을 권장한다(스키마 변경 없이 `augmentation_mode`
  값 기준으로도 최소한의 구분 표시는 지금 당장 가능 — `'none'`은 대체로
  사람 지식용, `'tool'`/`'always'`는 Agent 자동연결용이라는 현재
  데이터의 실제 패턴과도 일치한다).

### Phase B — 산출물 단위 승인 게이트: "HITL" 문제 해결 (Phase A 의존)

Phase A의 협업 워크스페이스(4-1)가 이미 열려 있는 화면이므로, 승인/반려/
수정 버튼은 **별도 화면(결재 탭)으로 보내지 않고 그 워크스페이스 안에서
바로 처리**한다 — 다만 감사 추적을 위해 `approvals` 레코드는 그대로
생성하고, "결재" 탭의 "내가 처리할 건" 목록에도 함께 뜨게 해서(F7과
동일한 큐를 재사용) 워크스페이스를 안 열어본 사람도 결재 탭에서 놓치지
않게 한다.

- `approvals.subject_type`에 `"deliverable"` 추가(현재 `app.py:1223`이
  하드코딩으로 막고 있는 지점을 확장).
- Agent 실행 완료 시 `deliverables`가 기본 `draft` 상태로 생기고, Relay
  패턴처럼 "이 스킬/이 Task는 리뷰 필요?" 설정(스킬 단위 또는 Task
  단위, `skill_pool`처럼 데이터로 관리)이 켜져 있으면 자동으로 승인
  요청이 걸린다.
- 승인 화면에서 **승인/반려**뿐 아니라 **수정(edit)**까지 가능해야
  한다 — 지금 HAIR엔 "산출물을 사람이 고친다"는 개념 자체가 없다는 게
  이번 조사에서 드러난 진짜 갭이라, 새로 설계해야 하는 부분이다.
- 자기 승인 방지는 ADR 3-A 로직을 그대로 재사용(새로 만들 필요 없음).

### Phase C — 비동기 실행 + 일시정지/재개: "HOTL" 문제 해결 (가장 큰 구조 변경)

**정정(사용자 요청, 2026-09-28, "HAIR AI Agent Framework로 CrewAI,
LangGraph 등 다양하게 분석해 최적을 제안해줘" — 프레임워크 비교 리서치
결과)**: 아래 §당시 "CrewAI의 `human_input=True`는 블로킹이라 못 쓰니
HAIR 자체 체크포인트를 새로 설계한다"는 판단은 **`Crew` 레벨의 옛
기능만 맞는 얘기였다**. CrewAI에는 별도 레이어인 **Flows**
(`@start`/`@listen`/`@router` 이벤트 기반 오케스트레이션)가 있고, 여기
`@persist`(재시작 간 상태 자동 영속화)와 `@human_feedback`(실행을
멈추고 상태를 유지한 채 사람 입력을 기다리며, 콘솔 `input()` 대신
Slack/이메일/웹훅/API로 응답받을 수 있는 `provider` 지정 가능)가 이미
있다 — HAIR가 새로 설계하려던 체크포인트를 CrewAI 안에서 그대로 해결할
수 있을 가능성이 크다. **단, 이 리서치는 WebFetch가 막힌 환경에서 검색
스니펫 기반으로 진행돼 `@human_feedback`의 정확한 API/데코레이터
문법은 1차 검증이 안 됐다** — 실제 설계 전에 설치된 `crewai` 패키지
소스나 공식 Flows 문서를 이 프로젝트가 항상 해온 방식대로 직접 읽어
재확인해야 한다.

**프레임워크 자체를 바꾸는 것(LangGraph/AutoGen/OpenAI Agents SDK/
Google ADK로 전환)은 기각한다**:
- LangGraph의 `interrupt()`+체크포인터가 가장 정교하지만, "역할 기반
  Crew 모델은 그래프 노드로 1:1 이식되지 않고, 어느 시점부터는
  그린필드 재작성보다 마이그레이션이 더 비싸진다"는 게 리서치에서
  확인됐다 — HAIR는 이미 `crew_runtime.py`(Agent/Task/Crew 생성,
  Process.sequential/hierarchical, delegation 캡처, MCPServerAdapter,
  native VectorDB/GraphDB Tool)에 깊게 투자돼 있고 129개 테스트가 이를
  검증한다.
- AutoGen은 2025-10-02부로 Microsoft가 유지보수 모드로 전환한
  프레임워크라 후보에서 제외한다(AG2는 별도 커뮤니티 포크).
- OpenAI Agents SDK/Google ADK는 매력적인 개별 기능(`ToolApprovalItem`
  승인, 1급 HITL 그래프 프리미티브)이 있지만 전면 재작성이 필요해
  HAIR의 기존 투자를 버릴 만한 이유가 안 된다.

**설계 방향(재확정 전까지 임시)**: CrewAI Flows로 대체 확인되면 그걸
쓰고, 확인 안 되면 아래 원래 계획대로 자체 체크포인트를 구현한다 —
둘 중 어느 쪽이든 사용자에게 보이는 결과(일시정지→사람 응답→재개)는
동일하다.

- (원래 계획, Flows 검증 실패 시 폴백) "Crew 전체를 한 번에 `kickoff()`"를
  **Task 단위로 쪼개 순차 실행**하는 방식으로 바꾼다 — Task 하나 끝날
  때마다 상태를 커밋하고(`job_items`에 `waiting_for_human` 상태 추가,
  현재 상태 + 다음 Task 입력을 저장할 체크포인트 컬럼 추가), 사람이
  계속 진행/수정 후 진행을 API로 트리거해야 다음 Task가 실행되게 한다.
- 백그라운드 워커 필요(현재 없음, `docs/LIMITS.md` §3이 이미 "단일
  프로세스·순차 요청 전제"라고 인정한 부분) — FastAPI
  `BackgroundTasks`로 시작하고, 필요하면 별도 워커 프로세스로 분리.
- Web UI: 진행 중인 실행의 타임라인(Asana 댓글 스레드 방식 차용),
  "사람 응답 대기 중" 목록, 일시정지된 실행에 대한 승인/재개/재지시
  버튼.
- `task_callback`을 지금처럼 메모리에만 쌓지 않고 **Task 하나 끝날
  때마다 즉시 `audit.record()`**하도록 바꿔 활동 기록도 실시간에
  가깝게 만든다(현재는 Crew 전체 종료 후 일괄 기록).

## 5. 우선순위/난이도

| Phase | 난이도 | 의존성 | 사용자 체감 |
|---|---|---|---|
| A. 결과물 엔티티 | 중 | 없음 | "이제 사람이 만든 걸 Agent가 실제로 읽고 시작한다" |
| B. 산출물 승인 게이트 | 중(A 필요) | Phase A | "AI가 만든 것도 배정처럼 승인/수정 가능" |
| C. 비동기+일시정지 | 상(구조 변경) | 없음(A/B와 독립적으로 시작 가능하나 완성엔 A 필요) | "실행 중에 멈추고 개입 가능" |

Phase A/B는 기존 스키마에 테이블을 더하고 기존 승인 파이프라인을
확장하는 수준이라 상대적으로 안전하다. Phase C는 지금 HAIR의
"단일 프로세스·동기 요청" 전제(`docs/LIMITS.md` §3) 자체를 건드리는
근본적인 아키텍처 변경이라 리스크가 가장 크고, 별도 설계 문서(ADR)가
먼저 필요하다.

## 6. 스코프 밖으로 명시하는 것

- CrewAI 네이티브 `Task.human_input=True`는 그대로 쓰지 않는다(블로킹
  `input()` 문제가 그대로 남음, `docs/LIMITS.md` §17에서 이미 검증·기각).
- 실시간 WebSocket 스트리밍(토큰 단위 실시간 출력)은 1차 범위 밖 —
  폴링 기반 타임라인으로 시작하고, 필요성이 확인되면 그때 검토한다.
- flow.team 벤치마킹은 참고 수준으로만 반영한다 — 실제로 확인된 기능이
  얕아서 구체적으로 베낄 만한 메커니즘이 없었다(§2-1 참고).

## 7. 다음 액션(사용자 결정 필요)

이 문서는 기획안이며 아직 구현하지 않았다. 진행하려면:

1. Phase A부터 시작할지, 세 Phase를 한 번에 설계할지 결정.
2. **프레임워크 자체 전환은 기각(2026-09-28 리서치로 결정)** — CrewAI
   유지, LangGraph/AutoGen/OpenAI Agents SDK/Google ADK로 전환 안 함
   (근거: 위 Phase C 정정 참고). 남은 결정은 "CrewAI Flows
   (`@persist`+`@human_feedback`)로 해결되는지, 아니면 HAIR 자체
   체크포인트를 만들어야 하는지"뿐 — **이건 설치된 `crewai` 패키지
   소스/공식 Flows 문서를 직접 읽어 확인해야 하는 실측 작업**이지 별도
   ADR 토론이 필요한 사안이 아니다.
3. 4-3에서 오픈 이슈로 남긴 "Agent의 skill_tags→Tool 자동 부착을
   Skill Pool 경유로 계속 둘지, Tool Pool 직접 매칭으로 분리할지"도
   별도 ADR 검토 대상 — Phase A 구현 착수 전에 최소한 방향만 정해두는
   것을 권장(안 정해도 4-3의 "LLM으로 도와줘" 기능 자체는 구현 가능하나,
   이후 스키마 재작업 리스크가 있음).
4. 이 문서를 팀 리뷰용으로 공유할 계획이면 Artifact(웹 페이지)로도
   발행할 수 있다 — 요청하면 바로 만들어준다.
