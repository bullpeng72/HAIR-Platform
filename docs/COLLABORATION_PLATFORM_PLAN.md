# 사람-AI 협업 플랫폼 기획안 — HAIR-Platform 다음 단계

사용자 요청(2026-09-28): "HAIR의 핵심은 사람과 AI Agent가 협업하여 일하는
구조야. 사람이 한 결과물을 AI Agent에게 전달, 사람이 HITL(Human-in-the-
loop), HOTL(Human-on-the-loop)로 AI Agent 업무 감독 등이 가능해야해" →
"HAIR 관련으로 외부 리서치 및 [flow.team 등] 유사 서비스를 분석해 사람과
AI가 협업하는 플랫폼을 기획해줘".

이 문서는 두 단계로 구성된다: (1) 현재 HAIR-Platform 실측 갭 분석(직전
세션에서 코드를 직접 읽어 확인), (2) 외부 서비스 6곳 리서치로 뽑아낸
공통 패턴을 근거로 한 3단계 개선 로드맵. **추정이나 마케팅 문구가 아니라
실제 코드 인용·실제 제품 기능 설명에 근거한다.**

## 1. 현재 HAIR-Platform의 실측 갭

직전 세션에서 코드베이스를 직접 조사해 확인한 사실(파일:라인 근거는
대화 기록 참고, 핵심만 요약):

| 패턴 | 현재 상태 | 근거 |
|---|---|---|
| 사람→AI 결과물 전달 | **없음** | `human_pool` 테이블에 산출물 저장 필드 자체가 없음(`db.py:44-55`). `run_crew()`의 `Task.context` 체이닝(`crew_runtime.py:274-284`)은 Agent 산출물→Agent 입력만 연결. 업로드/첨부/문서 개념 전체 코드베이스에 없음 |
| HITL(산출물 승인) | **배정 승인만 있음, 산출물 승인 없음** | `approvals.subject_type`은 `"assignment"`(F6 배정)·`"brief"`(F1 브리프) 둘뿐(`app.py:1223`이 다른 값을 명시적으로 거부). Agent가 만든 결과물은 생성 즉시 저장되고 승인/반려/수정 게이트가 전혀 없음. CrewAI의 `Task.human_input=True`를 실제로 검토했으나 블로킹 `input()`이라 웹서버와 비호환이라 의도적으로 보류함(`docs/LIMITS.md` §17) |
| HOTL(실행 중 감독) | **완전 동기 블로킹, 개입 지점 없음** | `crew.kickoff()`(`crew_runtime.py:158,359`), LLM 호출 전부 스트리밍 없는 단일 블로킹 호출. `/api/crew/run` 등은 HTTP 요청 안에서 끝까지 실행 후 반환(job ID 폴링 구조 아님, `docs/LIMITS.md` §3). `task_callback`은 메모리에만 쌓고 감사로그는 Crew 전체 종료 후 일괄 기록(`crew_runtime.py:317,385-421`). 일시정지/취소/재지시 엔드포인트 없음 |

**결론**: F5~F7(누구를 배정할지 승인)은 잘 갖춰져 있지만, "업무 내용
자체"에 대한 사람-AI 협업(결과물 릴레이, 산출물 리뷰, 실행 중 개입)은
설계에 없다.

## 2. 외부 서비스 리서치

### 2-1. flow.team (사용자가 지목한 서비스)

한국 팀 협업/메신저+업무관리 SaaS. AI 기능은 확인됐으나 **HITL/HOTL
관점에서는 얕다** — AI 프로젝트 템플릿 생성, 채팅 명령/엑셀→업무 변환,
반복업무 챗봇, 문서 초안, 일일 요약, 권한 준수 통합검색 정도이고
월 50회 사용량 제한이 있다. **AI 산출물에 대한 별도 승인/편집 게이트나
실시간 가시성 기능은 찾지 못했다** — 구조상 AI 산출물이 그냥 일반
"게시물/업무"로 바로 등록되고, 사람이 그걸 다른 게시물처럼 나중에 보고
고치는 방식으로 보인다(전용 리뷰 메커니즘이 따로 없다는 뜻). 1차 리서치
수준(검색 스니펫 기반)이라 신뢰도는 아래 항목들보다 낮게 잡아야 한다.

### 2-2. GitHub Copilot Coding Agent — 가장 근접한 사례

- **핸드오프**: 사람이 이미 만든 GitHub 이슈를 그대로 Copilot에게
  할당(이슈 = 사람이 만든 작업물이 AI 입력이 되는 실제 사례).
- **HOTL**: GitHub Actions 워크스페이스에서 저장소를 탐색·계획하고,
  **draft PR에 커밋을 순차적으로 실시간으로 푸시** — "작업이 실시간으로
  일어나는 걸 보고, 이상하면 언제든 개입할 수 있다."
- **HITL(산출물 승인)**: 작업은 draft PR 형태로만 존재하고, **머지 전
  사람 리뷰가 필수**다. 여러 차례 리뷰/수정 사이클이 일반적.
- **자기 승인 방지**: "Copilot에게 작업을 할당한 사람은 그 결과 PR을
  본인이 승인할 수 없다" — **HAIR의 ADR 결정 3-A(self-approval 방지)와
  원리가 완전히 같다.**

### 2-3. Relay.app — 가장 깔끔한 선언적 패턴

- AI 스텝마다 "사람이 이 AI 출력을 리뷰해야 하나?" **토글이 스텝 단위로
  붙어 있다** — 별도의 전역 승인 시스템이 아니라 스텝에 부착 가능한
  속성.
- 트리거되면 **워크플로가 멈추고**, 리뷰어에게 맥락과 함께 결과물을
  전달(이메일/Slack)하며 **승인/반려/수정** 버튼을 준다. 클릭하면 워크플로가
  재개되거나 중단된다.
- 같은 메커니즘을 "실행 전 승인"·"누락 데이터 수집"·"작업 배정"·"발송 전
  리뷰/수정"에 재사용한다 — **승인/편집이 "1급 워크플로 노드 타입"**이다.

### 2-4. Lindy.ai

- 액션 단위 "확인 요청" — 에이전트가 그 지점까지 실행하고 멈춰서
  기다림(이메일/인앱 알림으로 승인).
- 조건부 에스컬레이션 규칙(사용자가 "사람"을 요청, 반복 실패, 금지
  주제)으로 라이브 대화를 사람에게 넘김.
- 실시간 활동 피드는 확인 못 했다(사후 리포팅만 확인).

### 2-5. LangGraph `interrupt` — 실제 엔지니어링 메커니즘

- 노드가 `interrupt(value)`를 호출하면 `GraphInterrupt`가 발생해 실행이
  멈추고, 그 값이 클라이언트로 전달된다.
- **체크포인터가 그래프의 전체 상태(어느 노드, 모든 상태값, 정확한 실행
  지점)를 영속화**해서 실행을 무기한 중단해둘 수 있다.
- 사람이 `Command` 객체로 응답하면, **같은 노드를 처음부터 재진입해
  interrupt 지점까지 재생(replay)한 뒤** 사람의 입력으로 교체해 이어간다.
- **"평소엔 동기적인 에이전트 루프를, HTTP 요청을 계속 열어두지 않고도
  멈출 수 있게 만드는" 방법에 대한 구체적 답**이다: 상태를 외부에
  영속화하고, 재진입/재생으로 중단 지점까지 도달한 뒤, 주입된 입력으로
  재개한다.

### 2-6. Asana AI Teammates

- **AI가 사람과 똑같은 방식으로 업무에 배정된다**("팀원에게 업무를
  맡기듯 AI Teammate에게 배정") — **HAIR가 이미 가진
  `resource_type: human|agent` 다형성과 원리가 완전히 같다.**
- AI가 작업을 하위작업으로 쪼개고, **사람이 쓰는 것과 같은 업무 댓글
  스레드에 진행상황을 남긴다** — "팀이 언제든 초안을 리뷰하거나 수정을
  요청할 수 있다."
- "AI Studio"(반복작업 완전자동화)와 "AI Teammates"(판단이 필요한
  협업작업, 사람이 결과를 리뷰·가이드·의사결정을 직접 가져올 수 있음)를
  명확히 구분한다. 복잡/모호한 요청은 자동으로 사람 리뷰 플래그가
  붙는다.

### 2-7. 공통 패턴 (가장 중요한 발견)

**여기서 조사한 어떤 제품도 "단일 동기 RPC 호출이 끝난 결과물을
반환"하는 방식으로 이 문제를 풀지 않는다.** 잘 되는 제품은 다음 두
형태 중 하나(또는 둘 다)를 쓴다:

1. **공유 스레드/피드 모델** (GitHub PR 커밋, Asana 업무 댓글, Flow
   게시물): AI의 작업을 사람이 이미 보고 있는 **같은 객체에 점진적인
   post/commit/comment로 쪼개 넣는다** — "실시간 가시성"과 "언제든
   개입"이 별도 모니터링 기능이 아니라 사람과 협업할 때 쓰는 것과 같은
   UI 표면이라서 저절로 따라온다.
2. **명시적 일시정지-스텝 모델** (Relay의 스텝별 리뷰 토글, Lindy의
   "확인 요청", LangGraph의 `interrupt`+체크포인트): 워크플로/그래프를
   상태가 영속화되는 스텝의 나열로 모델링하고, 어떤 스텝이든 "여기서
   사람 응답 전까지 멈춰라"를 선언할 수 있다 — 이건 AI 실행 자체가
   태생적으로 재개 가능(resumable)/비동기여야 가능하지, 단일 블로킹
   함수 호출 위에 나중에 덧붙일 수 있는 게 아니다.

두 패턴 모두 "AI의 작업 단위"를 **상태를 가지고 점진적으로 보이며
승인/편집 게이트를 붙일 수 있는 객체**로 다뤄야 한다는 공통 요구를
갖는다 — 지금 HAIR처럼 "실행이 끝나야 문자열 하나가 한 번 나오는 불투명한
블로킹 호출"로는 안 된다.

## 3. HAIR-Platform이 이미 가진, 재사용 가능한 기반

다행히 완전히 새로 설계할 필요는 없다 — 조사해보니 HAIR는 이미 위
패턴들의 핵심 전제 두 가지를 갖고 있다:

1. **`assignments.resource_type: 'human' | 'agent'` 다형성** — Asana
   "AI를 사람처럼 배정"과 원리가 동일하다. F6/F7이 이미 사람이든
   Agent든 같은 배정·승인 파이프라인을 태운다.
2. **ADR 결정 3-A(자기 승인 방지)** — GitHub Copilot의 "할당자는 본인
   결과물을 승인 못 함"과 원리가 동일하다. 이미 검증된 코드(`app.py`
   self-approval 체크)가 있으니 산출물 승인에도 그대로 확장하면 된다.

부족한 건 "산출물을 담을 그릇"(공유 스레드/피드에 해당하는 엔티티)과
"실행을 멈췄다 재개할 수 있는 상태 저장 구조"(LangGraph의 체크포인트에
해당) 두 가지다.

## 4. 제안 로드맵 — 3단계

### Phase A — 결과물(Deliverable) 엔티티: "결과물 전달" 문제 해결

- 신규 테이블 `deliverables`: `id, task_id, author_type(human|agent),
  author_id, content, kind(draft|final), created_at`.
- 신규 테이블 `deliverable_comments`(공유 스레드/피드 모델 차용): 같은
  `task_id` 위에서 사람과 Agent가 번갈아 post를 남기는 타임라인.
- `crewai_agent_generator()`/`run_crew()`가 Task description을 조립할 때,
  그 task에 이미 있는 사람 작성 deliverable을 **자동으로 프롬프트
  컨텍스트에 포함**시킨다(현재는 이 연결이 전혀 없음, `crew_runtime.py`
  수정 필요).
- Web UI: "업무 요청" 상세 화면에 "결과물 타임라인" 탭 추가(할 일마다
  사람/Agent 산출물이 시간순으로 보임).

### Phase B — 산출물 단위 승인 게이트: "HITL" 문제 해결 (Phase A 의존)

- `approvals.subject_type`에 `"deliverable"` 추가(현재 `app.py:1223`이
  하드코딩으로 막고 있는 지점을 확장).
- Agent 실행 완료 시 `deliverables`가 기본 `draft` 상태로 생기고, Relay
  패턴처럼 "이 스킬/이 Task는 리뷰 필요?" 설정(스킬 단위 또는 Task
  단위, `skill_pool`처럼 데이터로 관리)이 켜져 있으면 자동으로 승인
  요청이 걸린다.
- 승인 화면에서 **승인/반려**뿐 아니라 **수정(edit)**까지 가능해야
  한다 — 지금 HAIR엔 "산출물을 사람이 고친다"는 개념 자체가 없다는 게
  이번 조사에서 드러난 진짜 갭이라, 새로 설계해야 하는 부분이다.
- 자기 승인 방지는 ADR 3-A 로직을 그대로 재사용(새로 만들 필요 없음).

### Phase C — 비동기 실행 + 일시정지/재개: "HOTL" 문제 해결 (가장 큰 구조 변경)

- 현재의 "Crew 전체를 한 번에 `kickoff()`"를 **Task 단위로 쪼개 순차
  실행**하는 방식으로 바꾼다 — Task 하나 끝날 때마다 상태를 커밋하고
  (`job_items`에 `waiting_for_human` 상태 추가, 현재 상태 + 다음 Task
  입력을 저장할 체크포인트 컬럼 추가), 사람이 계속 진행/수정 후 진행을
  API로 트리거해야 다음 Task가 실행되게 한다 — CrewAI 자체의
  `human_input=True`(블로킹 `input()`)는 여전히 안 쓰고, HAIR 자체
  체크포인트로 LangGraph의 interrupt/resume 아이디어만 차용한다.
- 백그라운드 워커 필요(현재 없음, `docs/LIMITS.md` §3이 이미 "단일
  프로세스·순차 요청 전제"라고 인정한 부분) — FastAPI
  `BackgroundTasks`로 시작하고, 필요하면 별도 워커 프로세스로 분리.
- Web UI: 진행 중인 실행의 타임라인(Asana 댓글 스레드 방식 차용),
  "사람 응답 대기 중" 목록, 일시정지된 실행에 대한 승인/재개/재지시
  버튼.
- `task_callback`을 지금처럼 메모리에만 쌓지 않고 **Task 하나 끝날
  때마다 즉시 `audit.record()`**하도록 바꿔 활동 기록도 실시간에
  가깝게 만든다(현재는 Crew 전체 종료 후 일괄 기록).

## 5. 우선순위/난이도

| Phase | 난이도 | 의존성 | 사용자 체감 |
|---|---|---|---|
| A. 결과물 엔티티 | 중 | 없음 | "이제 사람이 만든 걸 Agent가 실제로 읽고 시작한다" |
| B. 산출물 승인 게이트 | 중(A 필요) | Phase A | "AI가 만든 것도 배정처럼 승인/수정 가능" |
| C. 비동기+일시정지 | 상(구조 변경) | 없음(A/B와 독립적으로 시작 가능하나 완성엔 A 필요) | "실행 중에 멈추고 개입 가능" |

Phase A/B는 기존 스키마에 테이블을 더하고 기존 승인 파이프라인을
확장하는 수준이라 상대적으로 안전하다. Phase C는 지금 HAIR의
"단일 프로세스·동기 요청" 전제(`docs/LIMITS.md` §3) 자체를 건드리는
근본적인 아키텍처 변경이라 리스크가 가장 크고, 별도 설계 문서(ADR)가
먼저 필요하다.

## 6. 스코프 밖으로 명시하는 것

- CrewAI 네이티브 `Task.human_input=True`는 그대로 쓰지 않는다(블로킹
  `input()` 문제가 그대로 남음, `docs/LIMITS.md` §17에서 이미 검증·기각).
- 실시간 WebSocket 스트리밍(토큰 단위 실시간 출력)은 1차 범위 밖 —
  폴링 기반 타임라인으로 시작하고, 필요성이 확인되면 그때 검토한다.
- flow.team 벤치마킹은 참고 수준으로만 반영한다 — 실제로 확인된 기능이
  얕아서 구체적으로 베낄 만한 메커니즘이 없었다(§2-1 참고).

## 7. 다음 액션(사용자 결정 필요)

이 문서는 기획안이며 아직 구현하지 않았다. 진행하려면:

1. Phase A부터 시작할지, 세 Phase를 한 번에 설계할지 결정.
2. Phase C의 "Task 단위 쪼개 실행" 방식이 CrewAI의 설계 철학(Crew가
   전체를 관장)과 다소 어긋나므로, CrewAI를 계속 쓸지 자체 오케스트레이션
   레이어로 일부 전환할지 별도 ADR 검토가 필요.
3. 이 문서를 팀 리뷰용으로 공유할 계획이면 Artifact(웹 페이지)로도
   발행할 수 있다 — 요청하면 바로 만들어준다.
