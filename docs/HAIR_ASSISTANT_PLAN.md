# HAIR 매뉴얼 기반 챗봇 도우미 기획안

사용자 요청(2026-09-28): "HAIR 메뉴얼 기반으로 동작하는 챗봇 형태의
도우미를 기획해줘". 이 문서는 `COLLABORATION_PLATFORM_PLAN.md`·
`HAIR_MASTER_PLAN.md`와 같은 성격의 **기획 문서**다 — 코드 변경 없음,
실측 사실과 기존 아키텍처(§3-1 지식 그라운딩)에 근거해 설계만 제시한다.

## 1. "HAIR 매뉴얼"의 실체 — 현재 상태 실측

챗봇을 설계하기 전에 먼저 확인해야 할 것: **"HAIR 매뉴얼"이라고 부를
만한, 최종 사용자(Admin/Manager/Member/Viewer로 로그인해 웹 UI를 쓰는
사람)를 대상으로 한 문서가 지금 존재하는가?** 답은 "없다"다.

| 문서 | 실제 대상 독자 | 최종 사용자용으로 그대로 쓰면 안 되는 이유 |
|---|---|---|
| `README.md` | 개발자(설치·실행) | 설치/테스트 명령 중심, 화면 사용법 없음 |
| `docs/SPEC.md` | 개발자/기획자 | F1-F13·Gate A-G 정의는 정확하지만 내부 용어(승인 큐 스키마 등)가 섞여 있음 |
| `docs/ADR.md` | 개발자(의사결정 기록) | "왜 이렇게 결정했는가" 논의 과정이 핵심 — 사용자는 "어떻게 쓰는가"만 필요 |
| `docs/HAIR_MASTER_PLAN.md`, `COLLABORATION_PLATFORM_PLAN.md` | 기획자/개발자 | 미구현 항목·설계 초안이 섞여 있어 그대로 노출하면 "안 되는 기능을 된다"고 오인시킬 위험 |
| `docs/LIMITS.md` | 개발자(알려진 갭·한계) | 보안/데이터 취약점 성격의 내용도 있어 **일반 사용자에게 노출하면 안 됨** |
| `docs/RETROSPECTIVE.md` | 개발자(스냅샷 회고) | 이미 문서 자체에 "현재 상태 아님" 경고가 붙어 있음(이번 세션 초반에 추가) |

**결론**: 기존 문서를 그대로 "매뉴얼"로 삼을 수 없다. 최종 사용자
대상으로 새로 쓰는 `docs/USER_MANUAL.md`를 만들고, 그 문서만 챗봇의
지식 소스로 쓴다. 개발자 문서(ADR/LIMITS/RETROSPECTIVE)는 소스에서
**원천 제외** — RBAC로 가리는 게 아니라 애초에 임베딩 대상에 넣지
않는다(Admin이라고 해서 LIMITS.md의 보안 갭을 챗봇이 요약해 알려줄
이유가 없다 — 그건 개발자가 코드로 직접 확인할 사안이다).

## 2. `docs/USER_MANUAL.md`(신규) — 콘텐츠 범위

메뉴/탭 단위로 "무엇을, 왜, 어떻게" 구조로 작성한다(SPEC.md의 F1-F13
정의·HAIR_MASTER_PLAN.md §1 프로세스 표에서 사용자 행동 부분만 발췌·
평이한 말로 재작성):

- 브리프 제출(F1)과 할 일 분해 — 브리프는 무엇이고 왜 필요한가
- 배정 요청과 승인(F5-F7) — 왜 승인이 필요한가, 누가 승인자인가(ADR
  3-A 자기승인 방지는 "본인 요청은 본인이 승인 못 한다"로 순화해 설명)
- 협업 워크스페이스 — 사람 입력 작성, "LLM으로 도와줘", AI 실행 트리거,
  산출물 승인/반려
- Gate A-G 자동 평가 — "이 점수가 뭘 의미하는가"(SPEC.md §5 정의를
  사용자 언어로: "G는 Grounding, 근거 없는 답변인지 확인" 등), 배지
  색(초록/노랑)이 뭘 뜻하는지
- 인박스·대시보드(Phase 5) — 각 항목 유형(승인 대기/실행 실패/낮은
  Gate 점수)이 뜨는 조건
- Human/Agent Pool, 검색·필터 — 가용성 필터, 스킬 매칭
- 역할별로 왜 화면이 다르게 보이는지(RBAC 4종 — "왜 이 버튼이 안
  보이나요"에 답할 수 있어야 함)

**제외**: 내부 테이블/함수명, ADR 의사결정 과정, `LIMITS.md`의 미해결
갭, 비용/구현 세부사항. "안 되는 것"을 설명할 때도 "왜 이 프로젝트가
이렇게 결정했는지"가 아니라 "지금은 이렇게 동작한다"까지만 말한다.

콘텐츠 저작 자체는 상당한 작업이라 이 기획 문서와 별도로 진행 여부를
사용자에게 확인한다(§7 열린 질문 참고) — 이 문서는 챗봇 **아키텍처**를
설계하는 것이 우선이다.

## 3. 챗봇이 답해야 할 질문 범위

### 포함(v1)

- `USER_MANUAL.md`에 근거해 "어떻게/왜/무엇" 질문에 답한다.
- 답변에 근거가 된 매뉴얼 섹션 제목을 함께 제시한다(출처 표시 —
  Gate A-G의 "Grounding" 개념을 챗봇 자신에게도 적용하는 셈이다).
- 검색된 청크의 유사도가 낮으면(임계값 미달) "매뉴얼에서 관련 내용을
  찾지 못했습니다"라고 답하고 **지어내지 않는다** — 이게 v1에서 가장
  중요한 요구사항이다.

### 명시적으로 제외(v1, 이후 별도 검토)

- **사용자 대신 행동을 실행하지 않는다**(브리프 제출·승인 처리·Agent
  실행 트리거를 챗봇이 API를 호출해 대신 수행하는 것 금지). 근거:
  이 프로젝트 전체에 걸쳐 확립된 원칙 — 모든 상태 변경은 승인
  체인·`audit_log`(actor_id 귀속)를 거쳐야 한다(ADR 3-A, NF10). 챗봇이
  대신 실행하면 "누가 한 행동인가"가 애매해지고, 자기승인 방지 같은
  기존 안전장치를 우회하는 새 경로가 생긴다. 순수 정보 제공(Q&A)만
  한다.
- Admin 전용 내부 정책의 심층 설명(왜 이 RBAC 매트릭스로 결정했는지
  등) — ADR 근거이므로 매뉴얼 소스 자체에서 제외했으니 자연히 답 못 함.
- 여러 턴에 걸친 대화 맥락 유지(멀티턴 대화 상태 관리)는 v1 범위 밖 —
  질문 1건마다 독립적으로 검색+답변(단일 요청-응답, 기존
  `system_prompt_for_human_assist()`류 1회 호출 패턴과 동일한 복잡도로
  시작).

## 4. 아키텍처 — 기존 그라운딩 인프라 재사용

`HAIR_MASTER_PLAN.md` §3-1이 이미 이 방향을 예고해뒀다: "같은
`vectorstore.search()`를 사람의 LLM 보조 호출에도 재사용할 수 있다."
매뉴얼 챗봇은 그 아이디어의 세 번째 사용처다(Agent 전용 → 사람의
"LLM으로 도와줘" → **플랫폼 전체 사용자 대상 매뉴얼 Q&A**).

### 4-1. 저장 — 새 테이블 `manual_chunks`(신규 제안)

`knowledge_chunks`(현재 스키마: `source_agent_id`가 필수 성격의 참조,
`vectorstore.py:48` `index_text()`)를 그대로 재사용하지 않고 별도
테이블을 제안한다 — Skill Pool의 지식 그라운딩(Agent별 근거 문서)과
매뉴얼 그라운딩(플랫폼 공통 사용법)은 목적이 다르고, `source_agent_id`
같은 Agent 종속 컬럼을 억지로 NULL 허용시키는 것보다 스키마 의도가
명확하다:

```
CREATE TABLE manual_chunks (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    section_title TEXT NOT NULL,
    text TEXT NOT NULL,
    embedding TEXT NOT NULL,
    embedding_provider TEXT NOT NULL,
    embedding_model TEXT NOT NULL,
    created_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```

검색 로직(코사인 유사도)은 `vectorstore.py`의 `_cosine_similarity()`를
그대로 가져다 쓴다 — **새 유사도 계산 로직을 또 만들지 않는다**
(HAIR_MASTER_PLAN.md §3-2가 이미 강조한 원칙과 동일).

### 4-2. 색인 — 1회성 CLI

`bootstrap.py`(콜드스타트 admin 생성)와 같은 패턴의 운영자 실행
CLI를 제안한다: `python -m hair_platform.manual_index --db-path hair.db`.
`docs/USER_MANUAL.md`를 `##` 헤딩 단위로 분할해 각 섹션을 청크 하나로
임베딩·저장한다. 문서가 바뀌면 재실행(전량 재색인, 증분 갱신은 v1
스코프 밖).

### 4-3. 질의 — 신규 엔드포인트

```
POST /api/assistant/ask   (Depends(get_current_user) — 로그인만 하면 역할 무관, 
                            GET /api/skill-pool/names와 같은 "전 역할 개방" 패턴)
  body: {"question": "브리프는 어떻게 제출하나요?"}
  →
  1. vectorstore.search()와 동일한 코사인 유사도로 manual_chunks 상위 k=3 검색
  2. 최고 유사도가 임계값 미만이면 "매뉴얼에서 못 찾음" 즉시 반환(LLM 호출 없음 — 비용 절감)
  3. system_prompt_for_manual_assistant()(신규, llm.py에
     system_prompt_for_role/system_prompt_for_human_assist와 같은 자리에 추가)로
     프롬프트 구성 — "검색된 매뉴얼 발췌 안에서만 답하라, 모르면 모른다고 하라"를 명시
  4. llm.call_llm() 1회 호출(기존 함수 그대로 재사용)
  5. {"answer": ..., "sources": ["섹션 제목", ...]} 반환
```

### 4-4. 의존성 제약(실측 기반)

`vectorstore.embed_text()`는 **현재 OpenAI 임베딩만 지원**한다
(`vectorstore.py:34-38`, Anthropic은 공개 임베딩 API가 없고 Ollama
로컬 임베딩은 오픈 이슈로 이월돼 있음). 즉 이 챗봇의 검색 단계는
`OPENAI_API_KEY` 없이는 동작하지 않는다 — 답변 생성(`call_llm`)은
provider를 Anthropic/Ollama로 바꿀 수 있어도 검색은 못 바꾼다. 키가
없는 배포 환경을 고려한다면 대안은: (a) 매뉴얼 색인만은 필수
전제조건으로 명시하거나, (b) 키워드 매칭(예: SQLite FTS5) 폴백을
v1.1에서 추가 — 이번 기획에서는 (a)로 시작하고 (b)는 오픈 이슈로
남긴다.

## 5. UI 노출 지점

두 방식을 비교한다:

| 방식 | 장점 | 단점 |
|---|---|---|
| 모든 탭에 떠 있는 플로팅 "도움말" 버튼 | 질문이 보통 "다른 화면을 보다가" 생김 — 탭 이동 없이 바로 물어볼 수 있음 | 기존 `TABS` 배열 기반 렌더링 구조에 전역 오버레이를 추가해야 함(작은 구조 변경) |
| 새 "도움말" 탭(TABS 배열에 추가) | 기존 탭 추가 패턴과 완전히 동일 — 구현 리스크 최소 | 질문이 생긴 화면에서 벗어나야 함(맥락 전환 비용) |

**권장: 플로팅 버튼.** 근거: 이번 세션 UI/UX 리뷰에서 이미 반응형
브레이크포인트(`@media (max-width: 640px)`)를 넣어뒀으므로, 작은
화면에서 겹치지 않는 위치(우하단 고정, 모바일에서는 탭 콘텐츠 영역
스크롤을 가리지 않게 z-index·여백 조정)만 추가 검토하면 된다.

## 6. 안전장치·리스크

- **환각(hallucination) 방지가 최우선 요구사항**이다(§3 참고) — 검색
  근거 없이 답하지 않는다. 이는 이미 이 프로젝트의 Gate G(Grounding)
  개념과 철학이 같다 — 원한다면 나중에 `agent_evaluation.py`의 Gate
  채점 로직을 챗봇 답변에도 적용해 자동 QA를 붙이는 확장을 검토할 수
  있다(v1 스코프 밖, 아이디어로만 기록).
- **비용 무제한 노출 리스크**: 기존 LLM 호출 경로(Agent 실행, "LLM으로
  도와줘")는 Manager 이상이 트리거하는 저빈도 행동이다. 매뉴얼 챗봇은
  **전 역할이 언제든 반복 호출 가능**해 비용 프로파일이 다르다. 현재
  `cost.py`는 `human_pool`/`agent_pool`의 정적 `cost_estimate`를
  집계하는 리포트일 뿐, 개별 LLM 호출의 실비용을 추적하는 메커니즘은
  코드베이스 어디에도 없다(§4-3의 임계값 이하 조기 반환이 유일한
  방어선). 사용자당/일 단위 호출 횟수 제한은 열린 이슈로 남긴다 — v1
  차단 사유는 아니지만 실제 배포 전 반드시 재검토해야 한다.
- **매뉴얼-코드 드리프트**: 이번 세션의 "기획/설계 내용 중... 분석해줘"
  리뷰에서 실제로 `HAIR_MASTER_PLAN.md` 6곳이 실제 코드와 어긋나 있는
  걸 발견했다(§4 데이터 흐름 다이어그램 등, 2026-09-28 수정 이력
  참고). `USER_MANUAL.md`도 똑같은 위험에 노출된다 — 코드가 바뀌어도
  매뉴얼을 안 고치면 챗봇이 틀린 사용법을 "매뉴얼에 있는 사실"이라며
  자신 있게 답하게 된다. 강제 동기화 메커니즘은 없다(알려진 한계로
  명시, `docs/LIMITS.md`에 항목 추가를 권장).

## 7. 로드맵 상 위치 및 열린 질문

Phase 1-5 다음의 **Phase 6**으로 제안한다(`HAIR_MASTER_PLAN.md` §7에
행 추가 예정). Phase 1-5 완료 상태에 종속되지 않음 — 독립적으로 착수
가능. TDD-AI 골든셋을 시작한다면 현재 마지막 번호(GC171) 다음인
GC172부터 이어간다.

**구현 착수 전 사용자 확인이 필요한 열린 질문**:

1. `docs/USER_MANUAL.md` 콘텐츠를 지금 바로 작성할지(저작 자체가 이
   문서와 별개의 상당한 작업), 아니면 1차로 SPEC.md/MASTER_PLAN.md
   발췌본을 임시로 쓰고 이후 다듬을지.
2. 플로팅 버튼 vs 도움말 탭 — §5 권장안(플로팅)에 동의하는지.
3. v1에 역할별 답변 차등(예: Admin에게만 보이는 관리 기능 설명)을
   넣을지, 아니면 완전히 역할 무관 단일 매뉴얼로 시작할지.
4. 비용 제한(§6) 없이 v1을 배포해도 되는지, 아니면 착수 전에 호출
   횟수 제한부터 설계할지.

이 문서는 기획까지다 — 위 열린 질문에 대한 답이 정해지고 "진행해줘"
지시가 있을 때 TDD-AI 사이클(Red-Green-Refactor)로 구현에 들어간다.
