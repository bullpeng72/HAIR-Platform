# HAIR 대표 시나리오 — 개발 업무 / 일반 업무 / 고객 지원

사용자 요청(2026-09-28): "HAIR 대표시나리오 (개발, 일반 업무 등) 몇개를
기획해줘". 이 문서는 실제 구현된 화면·엔드포인트·데이터 흐름만으로
구성한 **워크스루**다 — 아직 없는 기능(예: F1의 AI 기반 자동 분해)은
쓰지 않고, 지금 그대로 실행하면 재현되는 순서를 적는다. 각 시나리오
끝에 "이 시나리오가 보여주는 HAIR의 핵심 가치"와 "현재 구현과의 정합성
갭"을 덧붙인다.

**중요한 실측 전제**: F1(브리프 제출)의 "역할 후보 추출"은 AI 분해가
아니라 **줄바꿈 단위 스텁**이다(`app.py:92-95` `parse_brief_stub` —
브리프 텍스트를 줄 단위로 쪼갠 게 전부, 키워드 인식조차 없음). 실제
Task 분해(F2, `POST /api/briefs/{id}/tasks`)는 Manager/Admin이
`stub_roles`를 참고해 **role_name·required_skills를 직접 입력**하는
수동 폼이다(ADR 결정 1-A — 후보 매칭은 분해에 포함 안 함). 아래
시나리오는 전부 이 실제 흐름을 따른다.

## 시나리오 1 — 소프트웨어 개발: "결제 실패 버그 수정"

**배경**: Manager(`pm_kim`, manager role)가 운영 중 발견한 결제 API
버그를 브리프로 등록하고, 백엔드 수정은 AI Agent에게, 최종 코드 리뷰는
사람에게 맡긴다.

1. **브리프 제출(F1)** — Manager가 로그인해 브리프 폼에 다음을 입력:
   ```
   결제 확정 API에서 특정 카드사 응답 시 500 에러 발생
   재현 로그: POST /payments/confirm, provider=hanacard일 때만 실패
   백엔드에서 원인 분석 및 패치 필요
   QA가 재현 케이스로 회귀 테스트 필요
   ```
   `POST /api/briefs` → `parse_brief_stub()`가 줄 단위로 4개 후보
   문자열을 `stub_roles`에 저장(그 이상의 분석은 없음 — Manager가 직접
   봐야 한다).
2. **Task 분해(F2)** — Manager가 `stub_roles`를 참고해 직접 2개 Task를
   등록: `role_name="백엔드 개발"`(`required_skills=["python","결제 API"]`),
   `role_name="QA"`(`required_skills=["회귀 테스트"]`). `POST
   /api/briefs/{id}/tasks`.
3. **배정 요청·승인(F5-F7)** — "백엔드 개발" Task는 Agent Pool에서
   `role_name` 매칭되는 Agent(예: 이전에 온보딩된 backend Agent)를
   배정 요청, "QA" Task는 Human Pool에서 사람을 배정 요청. 둘 다
   Manager 본인이 아닌 다른 승인자가 승인해야 확정된다(ADR 3-A
   자기승인 방지 — Manager가 요청자면 동일인이 승인 불가).
4. **협업 워크스페이스 진입** — 확정된 "백엔드 개발" Task를 연 QA
   담당자(또는 Manager)가 재현 로그·기대 동작을 사람 입력으로 작성해
   `deliverable(author=human)`로 저장.
5. **AI 실행 트리거(Phase 4)** — `POST /api/tasks/{id}/execute-agent`
   호출 → 사람 입력을 Task context에 포함해 `agent_runtime.
   execute_agent()`가 백그라운드로 LLM을 1회 호출 → 완료되면
   `deliverable(author=agent)`(패치 설명·원인 분석) 생성.
6. **Gate A-G 자동 평가** — Agent 산출물 저장 직후 자동으로 채점되고
   Gate 배지(초록/노랑)가 협업 워크스페이스에 표시된다. Gate 점수가
   낮으면(`인박스`의 "낮은 Gate 점수" 항목으로도 뜸) 사람이 그 근거를
   보고 반려 여부를 판단한다.
7. **승인/반려** — 사람이 Agent 산출물을 검토해 `approved`(다음 QA
   Task로 이어짐) 또는 `rejected`(Agent 재실행 또는 사람이 직접 수정).

**핵심 가치**: HOTL(Agent 실행은 비동기, 사람은 언제든 진행 상태를
`GET /api/tasks/{id}/agent-execution-jobs`로 확인) + Gate A-G로
"AI가 짠 패치를 그냥 믿지 않고 근거로 검증"하는 신뢰성 확보.

**갭**: Agent가 실제로 코드를 수정하거나 테스트를 실행하지는 않는다 —
LLM 호출 1회로 "패치 설명 텍스트"를 만들 뿐이다(코드 저장소 접근·실제
패치 적용·CI 연동은 스코프 밖, `docs/LIMITS.md` 참고).

## 시나리오 2 — 일반 업무: "월간 마케팅 성과 보고서 작성"

**배경**: Manager가 매달 반복하는 보고서 작성을 팀원(Member)에게
배정하고, 팀원은 LLM 보조 초안 작성 기능을 쓴다 — Agent를 전혀 쓰지
않는, 순수 사람 중심 시나리오(HAIR가 "AI 강제"가 아님을 보여준다).

1. **브리프 제출** — Manager가 "9월 마케팅 캠페인 성과 정리, 지난달
   대비 CTR·전환율 비교, 다음 달 제안 포함"을 제출.
2. **Task 분해** — `role_name="마케팅 보고서 작성"`,
   `required_skills=["데이터 요약","보고서 작성"]` 1건 등록.
3. **배정·승인** — Human Pool에서 스킬 태그가 맞는 Member를 검색해
   배정 요청(§검색/필터 스케일 — `GET /api/pool/search?availability=
   available`), Manager 아닌 다른 승인자가 승인.
4. **협업 워크스페이스 — "LLM으로 도와줘"** — Member가 지난달 수치를
   붙여넣고 "LLM으로 도와줘"를 누르면 `system_prompt_for_human_assist()`
   기반 프롬프트로 LLM이 초안을 제안한다("최종 결정과 책임은
   사람에게 있습니다"라는 문구가 시스템 프롬프트에 명시돼 있음 —
   Agent 실행과 달리 이건 **사람이 작성한 것으로 저장**된다).
5. **제출** — Member가 초안을 다듬어 `deliverable(author=human)`로
   제출한다. **실측으로 정정(2026-09-28, 라이브 시나리오 실행)**: 원래
   이 문서는 여기서 "Manager가 검토 후 승인"이라고 적었으나, 실제로는
   **승인이라는 절차 자체가 존재하지 않는다** — `author_type='human'`
   deliverable은 항상 `status='draft'`로 남고(`deliverables.
   create_deliverable()`), Agent 산출물만 받는 결재 체인
   (`approvals.create_approval_chain()`)이 붙지 않는다. Manager는
   `GET /api/tasks/{id}/deliverables`로 **읽기만** 가능하고(admin/매니저는
   감독 목적 조회 허용), 댓글조차 남길 수 없다 —
   `POST /api/deliverables/{id}/comments`는 그 task의 참가자 본인만
   허용하는 "대리 작성 금지" 원칙을 예외 없이 적용해 비참가자 Manager를
   403으로 막는다(직접 호출로 확인: `pm_lee`가 비참가자로 댓글을
   시도 → 403). 즉 순수 사람 Task는 **완성 여부를 판단할 상태 전이
   자체가 없다** — 승인·반려도, 코멘트도 API로는 불가능하다.
6. **대시보드 확인(Phase 5)** — Manager는 `GET /api/dashboard`에서
   이번 달 완료된 보고서 Task와 팀 평균 Gate 점수(Agent 산출물이 있는
   Task만 해당)를 함께 본다.

**핵심 가치**: 협업 워크스페이스가 "Agent 실행"과 "사람 LLM 보조"를
같은 화면에서 다룬다 — 다만 §5에서 실측으로 드러났듯 **승인 게이트는
같지 않다**(Agent 산출물만 결재 체인을 탄다). 어떤 Task는 전부 사람이,
어떤 Task는 사람+Agent 혼합이 되어도 "협업 워크스페이스 화면 자체"는
같지만, 그 화면이 실제로 강제하는 절차는 author_type에 따라 다르다.

**갭(실측으로 재확인·심화, 2026-09-28)**: 원래 이 문서는 "사람 산출물의
품질 검증은 승인자의 수동 판단에 의존한다"고만 적었는데, 라이브로
직접 실행해보니 더 근본적인 갭이었다 — **"수동 판단"을 남길 방법
자체가 API에 없다**(승인/반려 상태 전이 없음, 댓글도 비참가자는
403). 실사용 시 Manager가 사람 산출물의 품질을 확인하려면 플랫폼
밖에서(구두·별도 메신저) 피드백을 주고, 완료 여부는 Task/브리프
상태가 아니라 Manager가 그냥 "안다"고 가정하는 수밖에 없다 — Gate
A-G가 없는 것과는 별개로, **완료 판정 메커니즘 자체가 없다**는 점을
`docs/LIMITS.md` §33에 별도로 남긴다.

## 시나리오 3 — 고객 지원(CS): "반복 문의 응답 초안 + 에스컬레이션"

**배경**: Viewer 권한만 가진 1선 상담원이 문의를 브리프로 못 올리고
(F1은 Admin/Manager 전용, RBAC), Manager가 대신 등록 → Agent가 초안을
만들고 Member가 최종 확인 후 고객에게 보낸다. RBAC 4종 역할이 실제로
갈리는 지점을 보여주는 시나리오.

1. **문의 접수** — 상담원(Viewer)은 문의 내용을 사내 채널로 Manager에게
   전달(HAIR 밖의 일 — 플랫폼은 F1부터 관여).
2. **브리프 제출** — Manager가 "환불 정책 문의 반복 다수, 표준 응답
   템플릿 필요, 애매한 케이스는 에스컬레이션 문구 포함" 제출.
3. **Task 분해·배정** — `role_name="CS 응답 초안"`(Agent Pool 배정,
   `required_skills=["고객 응대"]`)와 `role_name="최종 검수"`(Member
   배정) 2개 Task.
4. **AI 실행** — "CS 응답 초안" Task에서 `execute-agent` 트리거,
   Skill Pool의 "고객 응대" 스킬이 `augmentation_mode`에 따라 정적
   프롬프트로 주입되어(§3-1) 일관된 톤의 초안 생성.
5. **Gate 평가 확인** — Gate 배지가 "측정 없음"(노랑)이면 — 예를 들어
   TCR(Task Completion Rate) 관련 Gate가 채점 불가 상태면 — 검수자가
   이를 신호로 더 꼼꼼히 검토한다(이번 세션 UI 리뷰에서 고친
   "Gate 측정 없음" 오탐 방지 배지가 정확히 이 장면에 쓰인다).
6. **최종 검수·승인** — Member가 초안을 검토해 승인하거나, 애매한
   건은 반려 코멘트로 에스컬레이션 필요성을 남긴다
   (`deliverable_comments`).
7. **인박스로 흐름 확인** — Member는 로그인 시 `GET /api/inbox`에서
   "승인 대기" 항목으로 이 Task를 바로 확인한다(탭을 일일이 돌아다닐
   필요 없음, Phase 5).

**핵심 가치**: RBAC 4종이 실제로 "누가 브리프를 못 올리는지, 누가
검수하는지"를 가르는 걸 보여준다 + 인박스가 "내가 지금 뭘 해야
하는가"를 역할 무관하게 한곳에 모은다.

**갭**: Viewer가 상담원 역할이라는 전제는 시나리오상 설정일 뿐 — 실제
"상담원용 화면"이 따로 있는 건 아니다(Viewer는 읽기 전용, 브리프
제출조차 못 함). 실사용 시 상담원이 Viewer보다 넓은 권한(예:
Member)을 가져야 할 수 있고, 그 경우 역할 매핑을 재검토해야 한다.

## 공통 관찰 — 세 시나리오가 함께 보여주는 것

| 축 | 시나리오 1(개발) | 시나리오 2(일반 업무) | 시나리오 3(CS) |
|---|---|---|---|
| Agent 관여 | O(코드 패치 설명) | X(사람 LLM 보조만) | O(응답 초안) |
| Gate A-G 적용 | O | X(사람 산출물) | O |
| RBAC 경계 노출 | 낮음(Manager/Member만 등장) | 낮음 | **높음**(Viewer 배제가 핵심) |
| 승인 단계 수 | 2단계(백엔드→QA) | 1단계 | 2단계(초안→검수) |

세 시나리오 모두 **F1 브리프 → F2 수동 분해 → F5-F7 배정/승인 →
협업 워크스페이스 → (선택)Gate 평가 → 승인**이라는 동일한 골격을
쓴다 — HAIR의 핵심은 이 골격이 "사람만", "Agent만", "혼합" 어느
조합에도 똑같이 적용된다는 것이다(시나리오 2의 "핵심 가치" 참고).
