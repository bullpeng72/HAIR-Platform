<h2 id="ov">1. 개요</h2>

HAIR(Human-AI Resource Management)는 **사람과 AI Agent를 하나의 조직도 위에 함께 두고, 같은 절차로 일을 배정·승인·실행**하는 협업 플랫폼입니다. 아래 세 가지 원칙만 알면 나머지 기능은 전부 그 응용입니다.

- **배정·결재 절차는 사람과 Agent가 같습니다** — 할 일에 누군가를 배정하고(리소스 매칭/배정), 결재로 확정하고(결재), 조직도에 반영되는 흐름이 사람이든 Agent든 같습니다. 다만 등록 화면은 다릅니다 — 사람은 "사람 인력 관리", Agent는 "AI 에이전트 생성"에서 만듭니다.
- **사람이 승인해야 확정됩니다** — Agent가 만든 결과물은 결재를 거쳐야 "확정된 결과"가 됩니다. 이렇게 사람이 중간에서 확인하는 구조를 **HITL**(Human-In-The-Loop)이라고 부릅니다. 예외는 파이프라인의 자동 진행 단계로, 그 단계에 정한 품질 점검(Gate) 기준을 통과하면 통과 자체가 승인으로 처리돼 사람이 매번 누르지 않아도 됩니다.
- **결과물은 점수로 확인합니다** — Agent 결과물은 저장될 때 **자동 품질 점검**(화면에는 "품질 점검"으로 보입니다. 내부 이름은 **Gate A-G**: A 목표 달성·B 행동 무결성·C 신뢰성·D 응답 시간(성능 계약)·E 보안 경계·F 다중 Agent 협업·G 근거 제시(관측성). 완료율은 TCR)와 내용 검사(수치·인용·용어 등, 4절 "결과물 자동 검증")로 자동 채점되고, 점수가 결과물 카드에 배지로 남습니다.

일을 맡기는 길은 두 가지입니다 — **가벼운 대화**(2절, 결재 없음)와 **정식 업무 절차**(3절, 결재·이력·품질 점검 기록). 두 길은 같은 Agent·팀 등록을 쓰므로, 대화로 시작한 일을 나중에 정식 업무로 옮길 수 있습니다.

### 계정 유형 4가지
로그인 계정에는 유형(역할)이 하나씩 정해져 있고, 유형에 따라 **보이는 메뉴와 누를 수 있는 버튼**이 다릅니다. 내 유형은 화면 위쪽 계정 이름 옆 괄호에 표시됩니다(예: `hong (구성원)` — 관리자=admin, 매니저=manager, 구성원=member, 열람자=viewer). 계정은 admin이 설정 → 운영 관리 → **"사용자 관리"**에서 만들고 유형을 정합니다(첫 admin 계정만 서버 PC에서 `hair bootstrap-admin`으로 만듦).

| 유형 | 이런 사람에게 | 할 수 있는 일 | 할 수 없는 일 |
|---|---|---|---|
| **admin** (관리자) | 플랫폼 운영 책임자 | manager가 할 수 있는 모든 일 + **admin 전용**: 사용자 생성·유형 지정, Agent 온보딩 승인, 업무 요청·할 일·사람·Agent **삭제**, 모델 레지스트리·LLM 설정 최적화, 평가 기준, 조직 정책·기본 구성 점검, 외부 알림·메일 알림·코드 저장소·사내 DB·메일 수신함·캘린더 연결 | 자기가 올린 배정 요청을 자기가 승인(다른 admin·manager가 승인) |
| **manager** (업무 관리자) | 팀장·PM처럼 일을 나누고 배정하는 사람 | 업무 요청을 할 일로 나누기, 배정 요청과 **결재 처리**, Agent 만들기·실행, 팀·파이프라인 실행, 사람 인력·팀·파이프라인·도구/스킬·지식 베이스 관리, 정기 실행·이벤트 트리거, 대시보드·비용·공정성 지표·활동 기록 보기 | 위 admin 전용 기능, 자기 요청 승인 |
| **member** (실무자) | 업무를 요청하고 맡은 일을 하는 사람 | 대화(Agent 멘션 포함), **업무 요청 제출**, 배정 요청 올리기, 맡은 할 일의 협업 워크스페이스에서 결과물 작성·검토 요청·댓글, 내 API 키 발급, 성과 리뷰 보기 | **결재 처리**, 할 일로 나누기, Agent 만들기·실행, 파이프라인 실행, "설정" 메뉴 전체 |
| **viewer** (열람자) | 내용을 보기만 하면 되는 사람(임원·외부 검토자 등) | 홈·인박스·내 업무·업무 요청·결재(목록)·갤러리·할 일 보드·인력 검색·조직도·이용 가이드 **열람**, **대화**(AI 답변 포함) | 업무 요청 제출, 배정 요청, 결재 처리, 결과물 작성, API 키, 홈의 "AI에게 일 맡기기", 성과 리뷰·⚙ 내 설정(연동 설정), "설정" 메뉴 |

> 💡 **알아 두면 좋은 점**
>
> - 버튼이 안 보이거나 "권한이 없습니다"가 나오면 대부분 계정 유형 때문입니다. 필요한 작업을 할 수 있는 유형의 사람에게 요청하거나, admin에게 유형 변경을 요청하세요.
> - 결과물 작성·댓글은 유형과 함께 **그 할 일에 참여하고 있는지**도 봅니다. admin이라도 참여하지 않은 할 일의 워크스페이스에는 결과물을 쓸 수 없습니다.
> - viewer도 대화에서 기본 AI나 Agent를 부를 수 있어 **AI 호출 비용이 발생**합니다.
> - 유형별로 보이는 메뉴 전체는 [7절](#menu) 표를 보세요.
> - 모든 유형이 헤더의 내 계정 이름을 눌러 **자기 비밀번호를 바꿀 수 있습니다**(아래 "내 계정").

- 목록이 비어 있으면 무엇이 그 목록에 모이는지와 다음에 할 일(예: "홈에서 AI에게 일 맡기기" 버튼)이 보입니다.

### 내 계정 — 비밀번호 바꾸기

1. 헤더 오른쪽의 **내 계정 이름**(예: `hong (구성원)`)을 누릅니다.
2. **지금 비밀번호**, **새 비밀번호**(8자 이상), **새 비밀번호 확인**을 넣고 **"바꾸기"**를 누릅니다.
3. 바꾸면 **다른 브라우저·탭·PC에서 로그인한 곳은 모두 로그아웃**됩니다(지금 탭은 그대로). 비밀번호가 새어 나간 것 같을 때도 이렇게 바꾸세요.

- 비밀번호를 잊었으면 admin에게 **재설정**을 부탁합니다(13절). 재설정해도 그 계정의 다른 로그인은 모두 끊깁니다.
- 같은 아이디로 비밀번호를 **5번 틀리면 15분 동안** 로그인이 막힙니다(8절 "로그인과 계정").

<h2 id="chat">2. 가장 빠른 시작 — 홈과 대화</h2>

📍 **메뉴**: 홈 · 대화

### 0단계 — 어디서 시작할지 모르겠다면: 홈의 "AI에게 일 맡기기"
로그인하면 **"홈"**이 열립니다("AI에게 일 맡기기" 칸은 viewer에게는 보이지 않습니다).

1. **"AI에게 일 맡기기"** 입력창에 할 일을 한두 문장으로 적습니다(예: "3분기 부서 예산 집행 실적을 분석해 경영진 보고서를 써 줘").
2. **"추천 받기"**를 누르거나 Ctrl(⌘)+Enter를 누릅니다. 빠른 질문(대화)·특정 Agent·여러 단계 파이프라인·정기 실행 중 어느 방법이 맞는지 **이유와 함께** 추천합니다. 추천은 키워드 규칙으로 하므로 AI를 호출하지 않고 비용도 없습니다.
3. 추천 카드의 버튼을 누르면 그 방법으로 이어집니다.
   - **"대화 열기"·"이 Agent와 대화 열기"** — 새 대화를 만들고(Agent면 초대까지) 입력창에 글을 채워 둡니다. **보내기는 직접 확인하고 누릅니다.**
   - **"업무로 만들고 바로 실행"**(admin·manager, 비용 발생) — 업무 요청과 할 일을 만들고 추천된 파이프라인을 바로 시작한 뒤 "내 업무"로 이동합니다. 1단계 계획 승인은 "결재"에서 처리합니다.
   - **"업무 요청으로 올리기"**(member) — 추천된 실행 방식을 적은 업무 요청을 올리고 **그 업무의 진행 화면**(3절 "진행 한눈에 보기")을 바로 엽니다. 할 일로 나눠 실행하는 것은 manager가 합니다.
   - **"정기 실행 설정으로"** — 헤더 ⚙ 내 설정(연동 설정)의 정기 실행 칸에 업무 내용을 채워 둡니다. 파이프라인·주기·시각을 골라 추가하세요.

같은 홈 화면에는 **처리할 일**(결재 대기·AI 실행 실패·품질 점검 미달·최근 완료 건수 — 누르면 해당 화면으로 이동)과 **일을 맡기는 방법 4가지** 안내가 있고, admin에게는 **관리 점검**(기본 구성과 다른 곳·외부 알림 미설정·단가 없는 모델·작업 프로세스 상태)이 함께 보입니다.

### 1단계 — 대화 열기
메뉴 **일하기 → "대화"**를 엽니다.

- 새로 시작하려면 **"새 대화 제목(선택)"** 칸에 제목을 적고(비워도 됨) **"새 대화 시작"**을 누릅니다.
- 이어서 하려면 목록에서 대화를 골라 **"열기"**를 누릅니다.

> 💡 **누구를 불러야 할지 모르겠다면** — 기본 등록된 Agent 39개를 바로 부를 수 있습니다. 예: `@코드 검증가 이 함수 리뷰해줘`, `@데이터 분석가 이 숫자들의 증감률을 계산해줘`, `@외부 자료 조사가 ○○ 시장 동향을 조사해줘`. 전체 목록과 역할은 **"인력 검색"** 탭에서 볼 수 있습니다.

### 2단계 — 입력창 주변 컨트롤
화면 아래 입력 영역에는 왼쪽부터 다음 컨트롤이 있습니다.

- **"개발업무 스킬도 보기"** 체크박스(기본 꺼짐) — 옆 스킬 드롭다운에는 평소 **일반업무 스킬**(기획·전략·자료조사·보고서·데이터분석·차트·제안서·실적서 등)만 나옵니다. 코드 작성·Gate 채점 같은 **개발업무 스킬**은 이 체크박스를 켜야 보입니다(삭제된 것이 아니라 숨겨 둔 것). 어떤 스킬이 어느 분류인지는 "도구/스킬 Pool" 화면(admin·manager)에서 보고 바꿀 수 있습니다.
- **스킬 선택 드롭다운**(기본 "스킬 선택 안 함") — 아무도 멘션하지 않고 보낼 때 기본 AI가 어떤 지식·도구를 쓸지 고릅니다.
  - **"실시간웹검색"** — Tavily로 실제 웹을 검색한 뒤 그 결과를 근거로 답합니다(서버에 `TAVILY_API_KEY`가 설정돼 있어야 함 — 없으면 관리자에게 요청).
  - **"내부지식검색"** — 지식 베이스에 등록된 사내 자료를 찾아 답합니다.
    - **공개 범위**: 지식 베이스의 문서마다 공개 범위가 있어, **요청한 사람이 볼 수 있는 문서만** 근거로 씁니다(전체·manager 이상·admin만·특정 팀). 기본은 전체 공개입니다. 설정은 "지식 베이스" 화면의 문서 목록 **"공개 범위"** 칸에서 admin·manager가 바꿉니다("admin만"은 admin만).
  - "일반웹검색"·"최신정보필수확인"·"딥리서치"·"AI업계동향브리핑" 같은 조사형 스킬은 답에 **출처(제목·URL 또는 참고한 과거 결과물 번호)를 반드시 밝히게** 돼 있습니다. 출처 없는 답이 오면 스킬이 제대로 적용됐는지 먼저 확인하세요.
  - 메시지에 **멘션을 하나라도 넣으면 이 선택은 자동으로 비워집니다** — 멘션한 대상이 우선이기 때문입니다.
- **메시지 입력창** — `@`를 치면 사람·Agent·팀 자동완성이 뜹니다. 아직 이 대화에 없는 대상도 검색되며, 목록에서 고르면 **그 자리에서 대화에 초대된 뒤** 멘션이 들어갑니다.
- **📎 자료 버튼** — 로컬 파일(`.md`·`.markdown`·`.txt`·`.html`·`.htm`·`.pdf`·`.csv`·`.xlsx`·`.docx`·`.pptx`)을 고르면 파일명이 표시되고 **대기 상태**가 됩니다("자료 제거"로 취소). **"전송"**을 누르면 적은 메시지가 먼저, 첨부 내용이 이어서 별도 메시지로 올라갑니다(메시지 없이 첨부만 보내도 됨). 첨부는 **이 대화에서 한 번만 쓰이고 저장되지 않습니다** — 계속 참고할 자료는 admin·manager가 "지식 베이스"에 올려야 합니다.

### 3단계 — 누구를 부를지 정하고 보내기
- **`@역할명` 또는 `@지정한이름`** — 그 Agent 하나만 실행됩니다(예: `@DA 이 기능의 데이터 모델을 설계해줘`).
- **`@팀이름`** — 그 팀의 Agent 멤버 전원이 실행됩니다. 팀에 파이프라인이 연결돼 있으면 그 파이프라인이 단계별로 진행되고, 아니면 멤버가 등록 순서대로 앞 사람 결과를 이어받아 실행됩니다(9절 "방법 A").
- **`@아이디`(사람)** — AI는 끼어들지 않고, 그 사람이 직접 답하는 메시지로 남습니다.
- **아무도 멘션하지 않으면** — 대화 상단의 **"AI 자동응답"** 체크박스가 켜져 있을 때만 기본 AI가 답합니다. 켜 두면 멘션 없는 메시지마다 모델이 호출되므로(비용 발생) 사람끼리 대화할 때는 꺼 두세요.

### 4단계 — (선택) 기본 AI의 모델 정하기
대화 상단의 provider·모델 선택에서 고른 뒤 **"모델 설정 저장"**을 눌러야 반영됩니다.

> ⚠️ **이 설정은 멘션 없이 답하는 기본 AI에만 적용됩니다.** `@Agent`로 부르면 그 Agent에 저장된 모델을 쓰고, `@팀`으로 부르면 팀 전체가 한 모델을 함께 씁니다(매니저가 있는 기존 위임형 팀은 매니저 Agent의 모델, 그 밖에는 아래 ①의 플랫폼 공통 기본 LLM). 단, 대화가 10건을 넘을 때 오래된 메시지를 요약하는 일과 "업무 요청으로 전환"의 AI 정리에는 멘션과 관계없이 이 설정이 쓰입니다. 메시지마다 실제로 쓴 모델이 작성자 줄에 표시됩니다.
>
> provider와 model을 둘 다 **"기본값 사용"**으로 두면 ① admin이 "LLM 설정 최적화" 탭의 **"플랫폼 공통 기본 LLM"** 카드에 지정한 모델 → ② 없으면 서버 환경변수 → ③ 그래도 없으면 설치된 API 키로 자동 판별한 모델 순서로 정해집니다. provider만 고르고 model을 "기본값 사용"으로 두면 ①을 건너뛰고 그 provider의 표준 모델을 씁니다.
>
> 💡 **응답이 느리다면**
>
> - 결과물의 한자·외국 문자 교정과 근거 없는 수치 문장 교정은 **짧은 AI 호출을 한 번 더** 합니다. 로컬 대형 모델 하나가 모든 일을 처리하면 이 짧은 호출도 앞 작업이 끝날 때까지 기다립니다.
> - admin이 "LLM 설정 최적화" 탭의 **"보조 작업 모델"** 카드에 다른 모델을 지정하면 이런 보조 호출만 그 모델로 보냅니다. 결과물 작성은 각 Agent의 모델 그대로입니다.
> - 본 모델과 **동시에 돌 수 있는** 모델(클라우드 소형 모델, 또는 메모리가 넉넉할 때 로컬 소형 모델)이어야 빨라집니다. 메모리가 부족하면 로컬 모델 두 개가 번갈아 올라가 오히려 느려집니다.

### 5단계 — 결과 확인
답은 잠시 뒤 메시지로 도착합니다(그동안 "응답을 기다리는 중…" 표시). 실패하면 원인이 메시지로 안내됩니다.

- **진행 표시** — 메시지 아래 진행 패널에 지금 하는 일(자료 조회 중 → 생각 중 — N자 → 답변 작성 중 → 언어 품질 교정 중)과 경과 시간이 보이고, 답을 쓰기 시작하면 **작성 중인 글이 그대로 미리 보입니다**. 방향이 틀렸으면 끝까지 기다리지 말고 다시 요청하세요. 협업 워크스페이스의 AI 에이전트 실행도 "생성 중…" 카드에 같은 미리보기가 나옵니다.
- **작성자 줄 배지** — 응답이 어떻게 만들어졌는지 보여 줍니다.
  - **"단발 응답"**(기본 AI·Agent 1명 멘션): 수치 계산·차트 같은 등록 도구는 필요하면 직접 호출하지만, 검색(내부지식·웹·뉴스)은 요청 직전에 한 번 조회한 결과만 씁니다.
  - **"위임 N건"**(팀 멘션): 실제 Agent 간 위임이 몇 건 있었는지(0건이면 한 명이 혼자 처리).
  - 두 배지가 모두 없으면 파이프라인 진행 알림처럼 모델 호출이 없는 메시지입니다.
- **메시지 남기기** — 대화 메시지는 자동으로 쌓이지 않습니다. 남길 메시지만 직접 보냅니다.
  - **"갤러리로 보내기"**(참가자 누구나, 비용 없음): 그 메시지를 결과물로 저장해 "갤러리" 탭에서 모아 봅니다.
  - **"지식베이스로 보내기"**(대화 참가자): 지식 등록을 **신청**합니다. admin이 "결재" 탭에서 승인해야 색인되고(이때 임베딩 비용 발생), 버튼 글자가 "지식 결재 대기" → "지식 등록 중" → "지식 등록됨 · 갱신 요청"으로 바뀝니다(반려되면 "지식베이스로 보내기(반려됨)"). 등록된 내용은 "내부지식검색" 스킬이나 그 스킬을 가진 Agent가 찾아 씁니다.

### 6단계 — (선택) 정식 업무로 넘기기
결재·Gate 기록이 필요해지면 대화 상단의 **"📋 업무 요청으로 전환"**을 펼칩니다.

1. **"초안 만들기"**(무료) — 이 대화의 사람 메시지를 요청 내용으로, 마지막 AI 답을 참고 발췌로 묶은 초안을 만듭니다. "AI로 목표·요구사항·완료 기준 정리"를 켜면 대화 기본 모델이 목표·요구사항·산출물·완료 기준·확인 필요 항목으로 정리합니다(비용 발생).
2. 초안을 고친 뒤 **"업무 요청 제출"** — 업무 요청(3절)이 만들어지고 대화에 "업무 요청 #N으로 전환했습니다"가 남습니다. 이후는 3절 절차 그대로입니다.

> ⚠️ **멘션했는데 반응이 없다면** — 그 Agent·팀이 아직 이 대화 참가자가 아닐 가능성이 가장 큽니다. `@`를 다시 쳐서 자동완성 목록에서 골라 초대되게 하세요(8절).

<h2 id="task">3. 정식 업무 — 요청부터 결재까지</h2>

승인 이력·품질 점검 점수·결과물 타임라인이 모두 남아야 하는 업무는 이 경로를 씁니다. 대화보다 단계가 많지만, 한 할 일에 사람·Agent·팀을 몇이든 붙일 수 있고 모든 이력이 남습니다.

### 1단계 — 업무 요청 제출(비용 없음)

📍 **메뉴**: 홈 → AI에게 일 맡기기 (또는 일하기 → 업무 요청)

1. **홈의 "AI에게 일 맡기기"**에 맡길 일을 한두 문장으로 적고 **"추천 받기"**를 누릅니다(2절 0단계). 정식 업무가 맞으면 추천 카드의 버튼으로 업무 요청이 만들어집니다 — admin·manager는 **"업무로 만들고 바로 실행"**(할 일·파이프라인까지), member는 **"업무 요청으로 올리기"**.
2. 필요한 역할을 이미 안다면 **"업무 요청"** 화면의 **"직접 등록(고급)"**을 펼쳐 내용을 적고 **"등록"**을 눌러도 됩니다(viewer는 조회만 가능).
   - 문장으로 적으면 **내용과 역할·스킬이 맞는 기존 Agent 역할**이 "제안된 역할" 칸에 참고용으로 채워집니다. 규칙 기반이라 AI를 부르지 않고 즉시 끝납니다.
   - 한 줄에 역할 하나씩 적으면(예: "백엔드 개발자 1명" / "UI/UX 디자이너 1명") 그 줄이 그대로 후보가 됩니다.
3. 대화에서 시작한 일은 대화 상단의 **"📋 업무 요청으로 전환"**으로 옮깁니다(2절 6단계).

### 2단계 — 할 일(Task)로 나누기
📍 **메뉴**: 업무 요청(admin·manager)

업무 요청 행의 **"할 일로 나누기"**를 누르고 아래 항목을 채웁니다(제안된 역할 칩을 누르면 입력란에 채워짐).

- **필요한 역할**(필수, 예: "백엔드 개발자") — 기본 Agent 39개와 이름이 같거나 겹치면("백엔드 개발자"·"코드 검증가"·"데이터 분석가" 등) 새로 만들지 않아도 3단계 후보에 그 Agent가 바로 나옵니다.
- **필요 스킬** — 하나씩 입력하고 Enter나 "추가"를 눌러 칩으로 담습니다(×로 제거, 목록에 없는 이름도 입력 가능). **"실시간웹검색"**(Tavily)과 **"일반웹검색"**(Parallel Search, MCP 도구)은 대화와 Crew 실행 양쪽에서 동작합니다. 대화에서 MCP 서버에 연결하지 못해 일반웹검색을 못 쓰면 답 맨 위에 "도구 서버(MCP)에 연결하지 못해…" 경고가 붙습니다.
- **인원 수**(기본 1).

**"할 일 추가"**를 누르면 목록에 바로 반영됩니다. 이후 배정·Agent 생성·실행은 모두 이 할 일 단위로 이뤄지고, 업무 요청의 **"진행 보기"**에서 할 일마다 배정·결과물·결재 진행과 다음에 할 일을 봅니다(아래 "진행 한눈에 보기").

**한 번에 여러 할 일로 쪼개려면**(admin·manager) — **"AI로 분해 제안 받기(복잡한 업무용)"**를 누르면 AI가 업무 요청을 읽고 여러 할 일(역할·필요 스킬)과 **선행 관계**(A가 끝나야 B 시작)를 제안합니다(비용 발생). 표에서 역할·스킬·"선행 업무"를 고친 뒤 **"이 배치로 할 일 추가"**를 누르면 할 일과 선행 관계가 한꺼번에 만들어지고, 할 일 상세의 의존관계 그림에 바로 나타납니다. 서로를 선행으로 거는 순환(A→B→A)은 자동으로 거부됩니다.

### 3단계 — 사람·Agent·팀·파이프라인 붙이기
📍 **메뉴**: 업무 요청(할 일 상세) · 리소스 매칭/배정 · 팀 관리 · 파이프라인 관리

아래 네 방법을 필요한 만큼 섞어 씁니다. **한 할 일에 확정 배정 여러 건이 함께 있을 수 있고**(사람 여러 명 + Agent 여러 개 + 팀), 네 방법 모두 같은 결재(4단계)를 거칩니다.

*(A) 후보를 찾아 배정 요청(사람·Agent)*

1. 업무 요청 **"진행 보기"**의 할 일 행에서 **"배정하기"**(또는 "상세") → **"후보 매칭하기"**(또는 "리소스 매칭/배정" 탭에서 할 일을 고르고 **"찾기"**)를 누릅니다.
2. 후보 상위 3명이 나옵니다. 고르는 기준:
   - 대상: 역할명이 서로 포함되는 후보(부분일치), 또는 역할명이 달라도 **필요 스킬(2개 이상)을 모두 가진** 후보(예: "Backend Engineer"와 "백엔드 개발자").
   - 순서: 역할명이 맞고 필요 스킬도 다 가진 후보가 먼저. 그다음은 **가용성 40%·적합도 35%·비용 25%** 점수순(적합도가 없으면 가용성 60%·비용 40%), 동점이면 필요 스킬을 더 많이 가진 후보가 앞.
   - Agent의 적합도: 관리자가 입력한 성과점수, 없으면 그 Agent 결과물의 Gate A 평균(평가 3건 이상일 때).
   - 후보가 하나도 없으면 **"AI로 추천 받기"**로 AI가 전체 인력에서 뜻이 맞는 후보를 찾습니다(누를 때만 호출, 비용 발생).
3. 원하는 후보의 **"배정 요청"**을 누르면 조직도의 상사 순서대로 결재 단계가 만들어집니다(아직 승인 전).
   - **본인을 배정하는 셀프배정은 결재 없이 그 자리에서 확정**됩니다 — 본인 시간만 쓰는 배정이기 때문입니다. 바로 5단계로 가면 됩니다.

*(B) 쓸 Agent가 없을 때*

admin·manager가 **"AI 에이전트 생성"**에서 이 할 일을 골라 만듭니다(9절).

*(C) 팀에 배정 요청*

할 일 상세의 **"팀에 배정 요청"**을 펼쳐 활성 팀을 고르고 **"이 팀에 배정 요청"**을 누릅니다. 팀이 없으면 "팀 관리"에서 먼저 만들라는 안내가 나옵니다(9절). 팀 배정의 결재자는 **팀 리더**이며, 기본값은 요청한 본인이고 승인 전까지 할 일 상세에서 다른 사용자로 바꿀 수 있습니다.

*(D) 파이프라인에 배정 요청*

할 일 상세의 **"파이프라인에 배정 요청"**을 펼쳐 활성 템플릿을 고르고 **"이 파이프라인에 배정 요청"**을 누릅니다. 결재가 **승인되는 순간 파이프라인 실행이 시작**됩니다(같은 할 일에서 이미 실행 중이면 배정만 확정되고 중복 실행은 하지 않음). 5단계의 "파이프라인 실행" 버튼과 같은 엔진이지만, 이 경로는 누가 승인했는지 결재 이력이 남습니다.

### 4단계 — 결재 처리
📍 **메뉴**: 결재

1. **"결재"** 탭 → **"내 승인 대기함"**에서 내 차례인 요청을 엽니다. 내가 요청한 건은 여기에 나오지 않습니다(자기 승인 금지).
2. 사유(선택)를 적고 **"승인"**하면 배정이 **확정**돼 조직도·비용·성과 리뷰에 반영됩니다. **"반려"**하면 요청이 끝나며, 다시 하려면 3단계부터 새로 요청합니다.
3. 요청자에게 상사가 지정돼 있지 않으면(예: admin 본인의 요청) 승인자가 정해지지 않은 1단계 결재가 만들어지고, admin·manager 누구나 처리할 수 있습니다.

### 5단계 — 협업 워크스페이스에서 실행
📍 **메뉴**: 내 업무(또는 업무 요청 → 진행 보기)

배정이 확정되면 할 일의 **협업 워크스페이스**에서 실행합니다("내 업무"에서 "열기", 또는 업무 요청 "진행 보기"의 "작업 시작(실행)"·"진행 보기" 버튼).

- **"이 업무의 AI 에이전트 실행(비용 발생)"** — Agent 1명에게 맡깁니다. 옆의 **"📎 참고자료"**로 이번 한 번만 쓸 파일을 첨부할 수 있습니다(대화 첨부처럼 저장되지 않음).
- **"팀 Agent 실행(Crew, 비용 발생)"** — 배정된 팀의 Agent 멤버 전원을 함께 실행합니다(9절 "방법 A").
- **"파이프라인 실행(비용 발생)"** — 템플릿을 골라 처음부터 끝까지 단계별로 자동 진행합니다(5절). **"신규 실행엔진(LangGraph) 사용"**을 켜면 서버가 재시작돼도 멈춘 단계부터 이어서 진행합니다(서버에 `graph` 확장 설치 필요).
- **"검토 요청"** — 사람이 직접 쓴 결과물도 이 버튼을 누르면 Agent 결과물과 같은 결재를 거칩니다.
- **"재시도 예산"**(admin·manager) — 이 할 일의 파이프라인·Crew 재시도를 합쳐 최대 몇 번까지 허용할지 정합니다(빈 값 = 제한 없음). 다 쓰면 단계의 재시도 횟수가 남아 있어도 바로 사람 승인으로 넘어가, 같은 일을 반복하며 비용만 쓰는 것을 막습니다.
- **"사람 판단 필수"**(admin·manager) — 켜면 이 할 일은 어떤 파이프라인을 타든 **모든 단계가 품질 점검 점수와 상관없이 결재를 거칩니다**. 협상·대외 커뮤니케이션처럼 사람이 꼭 봐야 하는 일에 씁니다.

### 진행 한눈에 보기 — 업무 요청 "진행 보기"

📍 **메뉴**: 업무 요청 → 행의 **"진행 보기"**

업무 한 건이 지금 어디까지 왔는지 한 화면에서 봅니다(예전에는 업무 요청·리소스 매칭/배정·내 업무·결재 화면을 오가야 했습니다).

- **단계 표시**: **요청 → 할 일 N → 배정 a/N → 결과물 b/N → 결재 c/N**. 다 끝난 단계는 초록 점, 일부만 끝난 단계는 반쪽 점입니다.
- **할 일 표**: 할 일마다 배정(✓ N명 확정 / 결재 대기 / 배정 안 됨)·결과물 상태·최종 결과물(✓ 승인됨)과 **"다음에 할 일"** 버튼이 있습니다.

| 지금 상태 | "다음에 할 일" 버튼 |
|---|---|
| 배정 안 됨 | **배정하기**(admin·manager — 후보 매칭·팀·파이프라인 배정 칸이 열림). 그 밖에는 "배정 전 — 매니저가 배정합니다" |
| 배정 요청이 결재 대기 | **배정 결재 대기** → 결재 화면 |
| 배정 확정, 결과물 없음 | **작업 시작(실행)** → 협업 워크스페이스(5단계) |
| 실행 중 · 파이프라인이 사람 승인 대기 | **진행 보기** · **승인할 단계 보기** |
| 결과물이 검토 대기 | **결과물 검토·결재** |
| 최종 결과물 승인됨 | ✓ 완료 · **결과 보기** |

버튼을 누르면 그 할 일의 협업 워크스페이스가 바로 아래에 열립니다.

### 6단계 — 결과물 결재로 마무리
📍 **메뉴**: 결재

결과물에는 **품질 점검 배지**(예: "품질 점검 4/5 통과 · 완료율 80%")가 붙고, 4단계와 같은 "결재" 탭에서 승인해야 확정됩니다.

> 💡 **노란 배지는 결재 전에 확인하세요** — 배지에 마우스를 올리면 걸린 항목이 보입니다.
>
> - **수치근거**: 퍼센트가 요청·조회·도구 결과의 숫자로 계산되는지
> - **인용근거**: "…라고"·"…에 따르면"처럼 따옴표로 옮긴 문장이 근거 자료에 실제로 있는지
> - **용어확인**: 근거 자료의 낱말이 한 글자 빠지거나 바뀌었는지(예: "1분기 착수"→"1분 착수", "발표 노트"→"발포 노트")
> - **테스트실행**: 코드 결과물의 테스트를 격리 환경에서 실제로 돌린 결과
>
> 회색 배지는 해당 사항이 없어 **재지 않은 항목이며 실패가 아닙니다**. 전체 목록은 4절 "결과물 자동 검증"에 있습니다.

### 7단계 — 결과물 활용·수정·내보내기
📍 **메뉴**: 갤러리 · 내 업무(협업 워크스페이스)

- **갤러리** — 여러 할 일의 결과물을 한 화면에 모아 봅니다. admin·manager는 조직 전체, 그 밖에는 내가 참가한 할 일의 결과물만 보이며, 유형(텍스트·마크다운·HTML·코드)으로 거를 수 있습니다.
- **"새 탭에서 보기"** — 결과물 하나만 담긴 페이지를 새 탭에 엽니다(로그인 필요, 외부 공개 링크 아님). 코드는 문법 강조, HTML은 그대로, 나머지는 마크다운으로 보여 줍니다.
- **"버전 이력"** — 같은 작성자가 이 할 일에 다시 낸 이전 버전(반려 뒤 재실행·파이프라인 재시도)과 사람이 고치기 전 내용을 골라 지금 버전과 줄 단위로 비교합니다(추가 녹색·삭제 빨강). 바뀐 곳을 확인한 뒤 승인·반려하세요.
- **"부분 수정 요청"**(admin·manager, 또는 본인이 쓴 초안) — 다시 쓸 **섹션**(마크다운 제목 단위)을 고르거나 바꿀 **부분을 붙여 넣고**, "3문장으로 줄여 줘"·"표로 바꿔 줘"처럼 요청한 뒤 "수정안 만들기"를 누르면(비용 발생) AI가 **그 부분만** 다시 씁니다.
  - 수정안은 원문과 줄 단위로 비교해 보여 주고, **"수락"**해야 반영됩니다(이전 내용은 버전 이력에 남음). **"거절"**하면 기록만 남습니다.
  - AI가 원문 낱말을 옮기다 깨뜨린 것으로 보이면(예: "순현금흐름"→"순현나름") 수락 버튼 위에 ⚠ 확인 문구가 뜹니다.
  - 수정안을 만든 뒤 결과물이 바뀌었어도 고칠 부분이 그대로 남아 있으면 그 자리에만 반영하고, 없어졌으면 반영하지 않습니다.
- **내보내기**(서버에 `documents` 확장 필요, 코드 결과물 제외)
  - **"Word로 내보내기"**: 마크다운의 제목·목록·표·굵게·인용을 Word 서식으로 옮기고, HTML은 보이는 글자만 문단으로, 차트·다이어그램은 "(차트 「제목」 — HAIR 화면에서 확인)" 자리표시로 남깁니다.
  - **"Excel로"**(표가 있을 때): 표마다 시트 하나(시트 이름은 표 바로 위 제목), "1,200"·"−20"은 숫자, "30.0%"는 퍼센트 서식 비율로 넣어 바로 계산할 수 있습니다.
  - **"PowerPoint로"**: 제목(#·##·###)마다 슬라이드 한 장, 목록·문단은 본문, 표는 표로 옮깁니다(HTML 발표자료 덱은 슬라이드마다 한 장). 기본 서식이라 다듬어 쓰는 초안용입니다. 디자인을 그대로 살리려면 원본 "다운로드"를 쓰세요.
- **"평가 리포트"** — 이 결과물의 품질 점검(Gate A-G) 채점을 평가 도구(Agent-Evaluator)가 만든 종합 HTML 리포트로 새 탭에 엽니다. 무엇이 들어 있고 어떻게 활용하는지는 4절 **"평가 리포트 — 확인과 활용"**을 보세요.
- **"저장소에 커밋"**(admin, 승인된 코드 결과물) — 12절 "결과물을 저장소에 커밋"을 보세요.
- **"삭제"** — admin·manager는 항상, 그 밖에는 본인이 쓰고 아직 제출하지 않은 초안만 지울 수 있습니다(제출 뒤에는 결재 이력이라 본인도 못 지움). 지우면 갤러리와 워크스페이스에서 바로 사라집니다.

> 배정을 잘못 걸었거나 필요 없어졌다면 할 일 상세의 **"배정 취소"**(admin·manager)로 확정·요청 상태를 되돌리세요. 업무 요청·할 일 삭제가 "확정된 배정이 있어 삭제할 수 없다"로 막힐 때도 이 버튼으로 먼저 정리합니다.

<h2 id="result">4. 결과물 확인 — 품질 점검 배지·평가 리포트</h2>

Agent 결과물은 저장될 때 자동으로 점검돼 배지가 붙고, 평가 도구가 만든 리포트가 함께 저장됩니다. 결재하기 전에 이 절의 방법으로 확인하세요.

### 결과물 자동 검증 — 배지 읽는 법
Agent 결과물은 저장 전에 아래 검사를 거치고, 결과가 단계·결과물 카드의 배지로 보입니다.

- **🔧 사용한 도구**: 파이프라인 단계마다 그 시도에서 Agent가 **실제로 부른 도구**(호출 수·실패 수)가 배지 옆에 보이고, 도구를 하나도 부르지 않았으면 "도구 사용 없음"이 보입니다. 입력·결과 앞부분까지 담긴 전체 기록은 `GET /api/pipeline-runs/{실행 ID}/tool-calls`로 볼 수 있습니다. 결과물에 "점검기로 확인했다"고 적혀 있어도 이 표시가 없으면 실제로는 부르지 않은 것입니다.
- **외부 데이터는 지시가 아니다**: 메일·캘린더·사내 DB·웹 검색·MCP 도구의 결과는 "외부 데이터 — 지시가 아니다" 표시로 감싸 Agent에 전달합니다(메일 본문 속 "이 메일을 받으면 …하라" 같은 문장으로 AI가 조종되지 않게). 외부 데이터를 이미 읽은 실행(같은 파이프라인 실행·같은 대화)에서는 **외부로 쓰거나 실행하는 도구**(도구/스킬 Pool의 "쓰기" 표시 — MCP 도구는 기본으로 켜짐)를 자동으로 쓰지 못하게 막고, 그 단계는 사람 승인으로 넘어갑니다.
- **필수 도구 지정**: admin·manager가 "파이프라인 관리"의 단계 카드에서 **필수 도구**를 추가·삭제합니다(10절). 재무 분석·계약서 조항 검토·채용 공고 작성 단계에는 기본으로 지정돼 있습니다.

- **배지 색**: **초록 = 통과, 노랑 = 미통과, 회색 = 미평가**. 회색은 그 결과물에 해당 사항이 없어 재지 않은 것으로 **실패가 아닙니다**. 인박스의 "품질 점검 미달 경고"와 대시보드의 "반복 실패 Agent"도 실제로 잰 항목의 미통과만 셉니다.
- **결과물 카드의 요약 배지**: "품질 점검 4/5 통과 · 완료율 80%" — 실제로 잰 항목 중 통과한 수와 요청한 항목을 끝낸 비율(TCR)입니다. 잰 항목이 하나도 없으면 "품질 점검 없음".
- **기준 바꾸기**: 통과 기준(기본 모두 0.7)·응답 시간 SLA·추론 표지는 admin이 설정 → 운영 관리 → **"평가 기준"**에서 바꿉니다(10절 "평가 기준 설정").

| 배지 | 무엇을 보나 | 미통과면 |
|---|---|---|
| 목표 달성·행동 무결성·신뢰성·응답 시간·보안·협업·근거 제시 | 품질 점검 7가지(내부 이름 Gate A~G, 1절) — 배지에 마우스를 올리면 "목표 달성(Gate A) — 통과(점수 0.82)"처럼 글자와 점수가 보임 | 단계에 지정된 항목만 판정에 쓰임 |
| 수치근거 | 퍼센트·비율이 요청·조회 자료·도구 계산 결과의 숫자로 재현되는지 계산 | 틀린 문장만 고쳐 쓰고, 그래도 남으면 "⚠ 수치 확인 필요" 표시 |
| 인용근거 | 따옴표로 옮긴 문장이 근거 자료(요청·앞 단계 결과·도구 결과)에 실제로 있는지 | 표시만(사람이 원문 확인) |
| 용어확인 | 근거 자료의 낱말에서 한 글자가 빠지거나 바뀐 용어("1분기"→"1분")가 있는지 | 표시만 |
| 구문·실행가능·테스트실행 | (개발 결과물) 코드 문법, 그대로 실행되는 완성본인지, Python·JavaScript 코드+테스트를 네트워크를 막은 Docker에서 실제 실행(Jest 형식·`node:test` 모두, 배지에 언어별 통과 수) | 구현 단계 재시도 |
| 화면실행 | (HTML 결과물) 문서를 실제 브라우저(Chromium, 샌드박스·네트워크 차단)로 열어 스크립트 오류·빈 화면을 보고, 보이는 버튼을 눌러 본 뒤 난 오류까지 기록. Playwright가 설치돼 있어야 함(없으면 미평가) | 기본은 기록만 — 단계 Gate에 `browser_execution`을 넣으면 통과 조건 |
| 추적성 | 1단계 요구사항을 빠짐없이 반영했는지(AI 판정, 짧은 답이라 출력 상한 4,096토큰) | 작성 단계로 되돌림 |
| 판정 | 검토자가 쓴 `## 판정`이 승인인지 보완 요청인지 | 작성 단계로 되돌림 |
| 조건부 승인 | 검토자가 승인하면서 고칠 곳을 요구했는지(판정 문단의 "수정하면·고쳐야·통일해야·오타가 남아 있음" 등) | 기본은 통과 + 노란 배지(검토자가 짚은 문장 표시). 단계의 "엄격 검토"를 켜면 작성 단계로 되돌림 |
| 점검대조 | 검토가 승인한 최종본을 규칙 기반 점검기에 다시 넣었을 때 문제가 나오는지 | 참고용(통과 판정은 그대로). 점검기가 문제를 찾으면 사람 결재 대기로 올림 |
| 배정확인(참고용) | (계획 분담 단계) 리드가 팀원별 하위 작업을 나눌 때 일을 주지 않은 팀원이 있는지 | 통과 판정과 무관. 빠진 팀원은 단계에 적힌 그 역할의 지시로 **자동으로 하위 작업을 받아** 실제로 기여하고, 노란 배지에 "자동 배정한 팀원"으로 표시 |
| 낱말확인(참고용) | 한국어 사전에 없는 낱말 — 모델이 지어낸 낱말(실측: 퍼널 결론의 뜻 없는 "-니즘" 낱말, "분산 처리"가 깨진 낱말 등)을 찾음. 플랫폼 화면·스킬에 쓰는 외래어와 요청·앞 단계 결과에 나온 낱말, 합성어(지식재산·미집행)는 빼고 셈 | 통과 판정·인박스 경고에는 넣지 않고 노란 배지에 낱말 목록만 표시(사전에 없는 실제 낱말 — 예: 당월·별지 — 이 섞일 수 있음). 서버에 `korean` 확장이 있어야 동작 |
| 필수도구 | 단계에 지정한 **필수 도구**(예: 채용 공고 점검기·계약 조항 점검기·재무 지표 계산기)를 이 시도에서 **실제로 불렀는지** — 도구 호출 기록으로 확인(결과물에 "점검했다"고만 적은 경우를 잡음) | 단계 재시도("필수 도구를 실제로 부르지 않았습니다"가 다음 시도 지시에 들어감). 단계 Agent에 그 도구가 연결돼 있지 않으면 막지 않고 회색(측정 안 함)으로 알림 |
| 외부데이터(참고용) | 이 시도에서 읽은 **외부 데이터**(메일·캘린더·사내 DB·웹 검색·MCP)와, 그 뒤 **막힌 쓰기 도구** | 통과 판정과 무관. 쓰기 도구가 막혔으면 노란 배지 + **그 단계는 사람 승인**으로 넘어감 |

**언어 교정**은 배지 없이 저장 전에 자동으로 합니다(조직 결과물 언어가 한국어일 때).

- **작업 독백 지우기**: 로컬 모델이 결과물에 흘린 영어 혼잣말 줄("Now I'll run the checker.", "Let me check…")은 LLM 없이 줄째 지웁니다. 한글이 없는 줄이면서 전형적인 독백 표현으로 시작할 때만 지우고, 코드 블록·표·인용·제목과 일반 영어 문장은 그대로 둡니다. 활동 기록에 `language_qa_narration_removed`로 남습니다.

- **고치는 것**: 한국어 결과물에 섞인 한자·일본어·베트남어 문자·깨진 글자를 문맥에 맞는 한국어로 바꿉니다. 문장 전체 교정으로 안 고쳐진 줄은 **문제 글자 부분만 앞뒤 문맥과 함께 다시 교정**합니다(긴 문장 속 "全覆盖"·"出具" 같은 짧은 한자도 잡힘).
- **기록**: 고친 내용은 "활동 기록"에 `language_qa_repaired`로 남습니다.
- **고치지 않는 것**: **한국어 글자로 된 뜻 없는 낱말**(모델이 지어낸 단어)은 자동으로 고치지 않고 위 **낱말확인** 배지로 알려 줍니다(서버에 `korean` 확장 설치 시). 다른 실제 낱말로 바뀐 오타("발표"→"발포")는 용어확인이 근거와 대조해 일부만 잡으므로, **최종 결과물은 사람이 한 번 읽어 보세요**.

### 평가 리포트 — 확인과 활용
📍 **메뉴**: 내 업무(협업 워크스페이스의 결과물 카드) · 대화(AI 응답)

Agent가 일을 마칠 때마다 HAIR는 평가 도구(**Agent-Evaluator**)로 Gate A-G를 채점하고, 같은 자리에서 평가 도구가 만든 **종합 HTML 리포트**를 함께 저장합니다. 배지가 "몇 점인가"를 알려 준다면, 리포트는 "왜 그 점수인가·무엇을 고치면 오르는가"를 보여 줍니다.

**어디서 여나**

| 위치 | 여는 곳 | 볼 수 있는 사람 |
|---|---|---|
| 결과물 | 협업 워크스페이스의 결과물 카드 버튼 줄 **"평가 리포트"** | 그 업무 참여자, admin·manager |
| 대화 | AI 응답 작성자 줄의 품질 점검 배지 옆 **"평가 리포트"** 링크(기본 AI·@Agent·@팀 응답 모두) | 그 대화의 참가자 |

- 누르면 **새 탭**에서 열립니다. 리포트는 HAIR 로그인 세션과 분리된 격리 페이지라 그 안의 스크립트가 HAIR에 접근하지 못합니다.
- 리포트는 운영 DB 안에 압축해 저장되며 폴더에 파일로 만들지 않습니다. 파일로 남기려면 리포트 탭에서 브라우저의 **"페이지를 다른 이름으로 저장"**을 쓰세요(외부 자료 없는 HTML 한 장이라 혼자서도 열림).
- 기능 도입(2026-11-25) 전에 만들어진 결과물·응답에는 리포트가 없어 버튼·링크가 보이지 않습니다. 결과물을 지우거나 대화·메시지를 지우면 리포트도 함께 지워집니다.

**리포트에 들어 있는 것**(평가 도구가 만든 영어 리포트입니다)

| 부분 | 무엇을 보나 |
|---|---|
| Executive Summary | 전체 판정(바로 써도 되는지)과 가장 먼저 볼 문제 |
| Path to Green | 미달 Gate(Gate gaps)와 점수를 가장 많이 올릴 개선 순서(Fix plan) |
| Gate A ~ G | Gate별 판정과 세부 지표 — A 응답 품질 5개 차원, B 도구 사용, C 재시도·환각, D 응답 시간·토큰·비용, E 보안 경계, F 협업 구조, G 추론 노출 |
| Lowest-scoring Cases · Failure Taxonomy | 가장 낮게 채점된 응답과 실패 유형 분류 |
| Threshold Sensitivity | 통과 기준을 바꾸면 통과율이 어떻게 달라지는지(아래 "평가 기준 설정"을 정할 때 참고) |
| Recommendations · Gate Failure Diagnosis | 낮은 Gate의 원인 진단과 구체적 개선 제안 |

**활용하는 법**

1. **결재 전 확인** — 결과물 배지가 노랗거나 Gate 점수가 낮으면 리포트의 Gate Failure Diagnosis와 Recommendations부터 봅니다. 예: Gate A가 낮고 "요구사항 일부 누락"으로 나오면 반려 사유에 그 항목을 적어 다시 쓰게 합니다.
2. **Agent 튜닝 근거** — 같은 Agent의 리포트에서 같은 문제가 반복되면(예: Gate G 낮음 = 근거를 밝히지 않음), "AI 에이전트 관리"에서 그 Agent의 스킬(지침·제약사항)이나 모델·파인튜닝을 바꾸고, 다음 결과물의 리포트와 비교합니다.
3. **기준 조정 근거** — Threshold Sensitivity와 실제 결과물 품질을 보고 통과 기준이 너무 빡빡하거나 느슨하다고 판단되면 admin이 10절 "평가 기준 설정"에서 바꿉니다.
4. **공유** — 탭을 파일로 저장해 업무 보고·회의 자료에 붙일 수 있습니다.

> ⚠️ **배지와 리포트의 판정이 다를 수 있습니다.** HAIR의 배지는 10절 "평가 기준"(Gate별 통과 기준)을 따르고, 여러 AI 호출로 이루어진 실행(파이프라인 단계·Crew)에서는 C·D(응답 시간)와 Agent가 1명일 때 F(협업 구조)를 **재지 않음**(회색)으로 처리합니다. 리포트의 PASS/FAIL은 평가 도구 자체 기준으로 매겨져 이런 항목도 값이 보일 수 있습니다 — **결재 판단은 HAIR 배지를 기준**으로 하고, 리포트는 원인과 개선 방향을 보는 용도로 쓰세요. 응답 시간 SLA·추론 표지 설정은 채점에 쓰여 리포트의 지표에도 반영됩니다.

리포트는 평가 1건당 약 0.5초·압축 저장 십수 KB가 듭니다. 끄려면 admin이 서버를 `HAIR_EVAL_HTML_REPORT=0`으로 띄웁니다(채점과 배지는 그대로, 13절).

<h2 id="pipeline">5. 파이프라인으로 자동 진행 — 기본 제공 템플릿</h2>

파이프라인은 여러 Agent가 **정해진 단계 순서대로** 일하게 하는 엔진입니다. 사람은 보통 **1단계(요구사항·계획 확정)에서 한 번만 승인**하고, 그 뒤 단계는 Gate 기준을 통과할 때까지 자동으로 재시도하며, 끝내 통과하지 못한 단계만 다시 사람에게 올라옵니다. 개발뿐 아니라 보고서·제안서·계약 검토 같은 사무 업무에도 같은 엔진을 씁니다.

### 개념
파이프라인은 **단계(stage)의 순서 있는 목록**이고, 각 단계는 넷 중 하나로 동작합니다.

| 모드 | 동작 | 예 |
|---|---|---|
| 단독(single) | Agent 1명이 혼자 처리 | 요구사항 분석가 1명 |
| 순차 릴레이(sequential_relay) | N명이 순서대로 앞 사람 결과를 이어받음 | AA → DA → UI 기획자 |
| 계획 분담(plan_merge) | 리드(첫 번째 역할)가 팀원별 하위 작업을 정함 → 팀원이 각자 수행 → 리드가 하나로 합침. 나누기를 모델의 즉흥적 위임에 맡기지 않고 플랫폼이 세 단계로 직접 진행 | 시장 조사가·재무 분석가가 나눠 쓰고 편집장이 합치는 보고서 |

**판정과 재시도** — 단계마다 **판정에 쓸 품질 점검 항목(Gate)·통과 비율·최대 재시도 횟수·"사람 승인 필요" 여부**가 정해져 있습니다(바꾸는 방법은 10절).

- 판정은 그 단계에 지정한 Gate로만 합니다. 기본 템플릿의 검토 단계는 **Gate A(목표 달성)와 요구사항 추적성**(1단계에서 정리한 요구사항을 빠짐없이 반영했는지 AI가 판정)을 **둘 다** 통과해야 하고, 개발의 구현 단계는 **실행 가능성**(그대로 실행되는 완성본인지)을 봅니다. 나머지 Gate(C 신뢰성·D 응답시간·F 협업 구조·G 관측성)는 내용과 무관하게 비슷한 값이 나와 기록·표시만 합니다.
- 기준을 통과하면 사람 승인이 필요 없는 단계는 바로 다음 단계로 넘어갑니다. 미달이면 "어떤 Gate가 왜 부족한지"를 반영해 자동으로 다시 시도합니다.
- 검토 단계에 **"검토 실패 시 되돌릴 단계"**를 정해 두면 같은 검토를 반복하지 않고 그 단계(보통 작성·구현)로 돌아가 **검토 의견을 반영해 다시 씁니다**(기본 템플릿 8종 모두 이렇게 설정).
- 되돌릴 단계가 있는 검토 단계는 **검토자가 쓴 판정도 따릅니다** — 검토 결과의 `## 판정` 첫머리가 **"보완 요청"**(또는 반려·재작성·수정 요청)이면 Gate 점수가 모두 통과여도 미통과로 보고 작성 단계로 돌려보내고, "승인"이면 통과합니다. 판정 문단을 찾지 못하면 막지 않습니다(Gate 목록에 "판정" 배지로 기록).
- **조건부 승인**: 검토자가 "승인"이라고 쓰면서 같은 판정 문단에 고칠 곳을 요구하면(예: "단, 오타 2곳을 **수정하면** 완성도가 높아집니다", "표기를 **통일해야** 합니다", "오타가 **남아 있습니다**") **노란 "조건부 승인" 배지**가 붙습니다. 배지에 마우스를 올리면 검토자가 짚은 문장이 보입니다. 이미 고친 내용을 설명하는 문장("오타 → 수정 … 반영되었고")은 해당하지 않습니다.
  - **기본(엄격 검토 끔)**: 통과로 처리합니다(다시 쓰는 시간이 들지 않음). **결재 전에 배지의 문장을 확인하세요.**
  - **엄격 검토 켬**: 파이프라인 관리의 단계 카드에서 **"엄격 검토 켜기"**를 누르면, 조건부 승인도 보완 요청처럼 작성 단계로 되돌려 짚은 곳을 고치게 합니다(재시도 상한 안에서). 품질은 올라가지만 다시 쓰는 만큼 시간이 더 듭니다(로컬 모델 실측: 보완 요청 한 번에 영업 메일 15분 → 71분). 버튼은 "검토 실패 시 되돌릴 단계"가 정해진 검토 단계에만 보입니다.
- **점검기와 검토 판정이 다를 때 — 사람이 결정**: 작성 단계에 규칙 기반 점검기(예: 채용 공고 점검기)가 필수 도구로 지정돼 있으면, 검토 단계가 "승인"한 뒤 플랫폼이 **최종본의 해당 부분(예: `## 채용 공고`)을 점검기에 다시 넣어** 확인합니다. 점검기가 차별 소지 문구나 빠진 필수 항목을 찾으면 둘 중 하나가 틀린 것이라, 자동으로 끝내지 않고 **사람 결재 대기**로 올립니다("점검대조" 노란 배지에 찾은 문구 표시). 결재자가 문구를 보고 승인하거나 반려하세요. 둘 다 문제가 없으면 초록 배지로 그대로 진행합니다. 검토가 "보완 요청"이면 어차피 다시 쓰므로 대조하지 않습니다.
- Agent 출력에 섞인 내부 추론·작업 메모·같은 문장 반복·중간에 잘린 HTML은 저장 전에 걷어 내고, 걷어 낼 수 없으면 결과물만 다시 쓰게 합니다(마지막 시도는 그대로 받아 Gate·사람이 판단).
- 재시도를 다 써도 통과하지 못한 단계만 결재함으로 올라옵니다.

**실행 중단** — 방향이 틀렸거나 필요 없어진 실행은 협업 워크스페이스의 **"실행 중단 요청"**으로 멈춥니다. 지금 진행 중인 모델 호출이 끝나는 다음 안전한 지점에서 멈추며, 이미 "사람 승인 대기" 상태라면 바로 멈춥니다.

**진행 표시** — 단계별 배지(대기·진행중·통과·재시도N·승인대기·반려)가 실시간으로 바뀌고, 실행 중인 단계는 카드 위에 **"▶ 2/5 단계 · 작성 — 기획서 작성자 작업 중 · 이 단계 3분 12초 경과"**처럼 몇 번째 단계인지, 어느 Agent가 무엇을 하는지(작업 시작·도구 실행·위임), 경과 시간과 진행 막대가 5초마다 갱신됩니다. 계획 분담 단계처럼 Agent가 직접 글을 쓰는 동안은 **작성 중인 글**도 미리 보입니다. 대화에서 시작한 실행은 같은 정보가 진행 메시지로 대화에도 올라옵니다.
- **예상 남은 시간** — 같은 파이프라인을 전에 돌린 기록이 있으면 진행 막대 아래에 **"⏱ 예상 남은 시간 약 N분"**이 보입니다. 단계마다 최근 실행(최대 5회)의 평균 소요 시간으로 계산하고, 지금 단계는 이미 지난 시간을 뺍니다. 사람 승인을 기다린 시간은 넣지 않습니다. 처음 돌리는 파이프라인이나 기록이 없는 단계는 "+ 기록 없는 단계 N개"로 따로 표시합니다. 보완 요청으로 다시 쓰게 되면 예상보다 더 걸립니다.

### 실행·중단·이어서 실행

- **실행**: 할 일의 협업 워크스페이스에서 템플릿을 고르고 **"파이프라인 실행(비용 발생)"**(admin·manager)을 누르거나, 그 파이프라인을 연결한 팀을 대화에서 `@팀이름`으로 멘션합니다. 홈의 "업무로 만들고 바로 실행"도 같은 실행입니다.
- **사람 승인**: 보통 1단계(요구사항·계획 확정)에서 한 번 결재 화면으로 올라옵니다. 인박스·브라우저 알림·업무 요청의 "승인할 단계 보기"로도 알 수 있습니다.
- **중단**: 협업 워크스페이스의 **"실행 중단 요청"** — 진행 중인 모델 호출이 끝나는 다음 안전한 지점에서 멈춥니다.
- **이어서 실행**: 서버 재시작·멈춤 감지로 멈춘 실행은 협업 워크스페이스에서 **"이어서 실행"**(admin·manager)을 누르면 끝난 단계는 건너뛰고 멈춘 단계부터 다시 돕니다(8절).

### 바로 써보기 — 기본 제공 "소프트웨어 개발 파이프라인"
📍 **메뉴**: 내 업무(할 일의 협업 워크스페이스) 또는 대화

아래 7단계가 등록돼 있어 바로 실행할 수 있습니다.

| # | 단계 | 모드 | 참여 | 판정·사람 승인 |
|---|---|---|---|---|
| 1 | 요구분석/계획 확정 | 단독 | 요구사항 분석가 | **사람 승인 필요**(사람이 개입하는 유일한 단계) |
| 2 | 설계 | 순차 릴레이 | AA → DA → UI 기획자 | 기록만, 자동 통과 |
| 3 | 개발 계획 수립 | 단독 | 개발 계획 수립가 | 기록만, 자동 통과 |
| 4 | 구현 | 단독 | 풀스택 개발자(완성본을 한 번에 작성) | 실행 가능성 필수 |
| 5 | 코드 검증 | 단독 | 코드 검증가 | A + 요구사항 추적성 필수, 미달·보완 요청이면 4단계로 되돌림 |
| 6 | QA 기능테스트 | 순차 릴레이 | 테스트 계획 수립가 → QA 기능테스터 | Gate A |
| 7 | 품질 관리 최종 판정 | 단독 | 품질 관리자 | Gate A(반복 실패 시에만 사람에게) |

미달인 단계는 사유를 반영해 자동 재시도하고, **마지막 자동 재시도에서는 자가검토가 자동으로 켜져** Agent가 초안을 원 요구사항과 대조해 한 번 더 고친 뒤 제출합니다. 그래도 통과하지 못하면 그때 사람 승인으로 올라갑니다.

**시작하는 법** — 할 일의 협업 워크스페이스에서 이 템플릿을 고르고 **"파이프라인 실행(비용 발생)"**을 누르거나, 이 파이프라인을 연결한 팀을 대화에서 `@팀이름`으로 멘션합니다(기본 제공 팀은 없으므로 연결하려면 팀을 직접 만들어야 함 — 9절 "방법 A" 6번).

### 바로 써보기 — 기본 제공 "사업/기획 업무 처리 파이프라인"
개발이 아닌 업무에도 같은 엔진을 쓰는 예입니다. 규칙(1단계만 사람 승인, Gate 판정, 되돌림)은 개발 파이프라인과 같고 역할만 다릅니다.

| # | 단계 | 모드 | 참여 | 판정·사람 승인 |
|---|---|---|---|---|
| 1 | 요구사항 분석/계획 확정 | 단독 | 업무 요구사항 분석가 | **사람 승인 필요** |
| 2 | 자료 조사·분석 | **계획 분담** | PM(리드) → 외부 자료 조사가·데이터 분석가·3C4P SWOT 분석가 | 기록만 |
| 3 | 기획 계획 수립 | 단독 | PM | 기록만 |
| 4 | 작성 | 순차 릴레이 | 기획서 작성자 → 사업전략 수립가 → C-level 보고서 작성자 → 프레젠테이션 자료 작성자(최종 통합, 발표자료 덱) | 기록만 |
| 5 | 내용 검증 | 단독 | 문서 검토자 | A + 요구사항 추적성 필수, 미달·보완 요청이면 4단계로 되돌림 |
| 6 | 표현 검토 | 순차 릴레이 | 문서 교정자 | Gate A |
| 7 | 최종 승인 판정 | 단독 | PM | Gate A(반복 실패 시에만 사람에게) |

**2단계 "자료 조사·분석"은 계획 분담**입니다 — PM이 요청을 팀원별 하위 작업으로 나누고, 팀원이 각자 맡은 부분을 한 뒤, PM이 하나의 보고서로 합칩니다. 실측(로컬 35B, 같은 요청): 순차 릴레이 24.2분·세 사람 보고서를 이어 붙인 8,464자 → 계획 분담 17.1분·결론부터 정리된 한 편 3,267자(수치는 둘 다 정확). PM이 팀원에게 일을 주지 않으면 그 팀원은 단계 지시로 **자동으로 하위 작업을 받고**, 단계의 **"배정확인"** 배지가 노랗게 바뀌어 자동 배정한 팀원이 표시됩니다(팀원 한 명분 시간이 더 듦). 예전 버전에서 올라온 설치본은 admin이 "기본 구성 점검"에서 반영할 수 있습니다(14절).

**"데이터 분석가"**(이 파이프라인과 제안서 파이프라인의 자료 조사·분석 단계, 실적 보고 파이프라인의 데이터 분석 단계)는 `데이터분석` 스킬의 "수치 데이터 분석기" 도구로 합계·평균·증감률·표준편차를 **코드로 계산**합니다. 값이 부족하면(표준편차는 2개 미만, 증감률은 기준값 0) 추측하지 않고 계산할 수 없다고 알립니다.

### 기본 제공 "제안서 작성 파이프라인"·"실적 보고 파이프라인"
사업/기획 파이프라인의 "작성" 단계는 기획서·전략·경영진 요약·발표자료 4종을 한꺼번에 만듭니다. 제안서나 실적서 하나만 필요할 때 나머지까지 만드는 낭비를 줄이려고 두 업무는 따로 템플릿을 두었습니다.

| # | 제안서 작성 파이프라인 | 실적 보고 파이프라인 |
|---|---|---|
| 1 | 요구사항 분석/계획 확정(업무 요구사항 분석가, 사람 승인 필요) | 요구사항 분석/계획 확정(업무 요구사항 분석가, 사람 승인 필요) |

| 5 | 표현 검토(문서 교정자, Gate A) | — |
| 6 | 최종 승인 판정(PM, Gate A) | — |

제안서는 발주처 평가 기준(배점표) 대응과 경쟁사 대비 차별화가 중요해 표현 검토까지 두었고, 실적서는 정기·정형 문서라 그 단계를 빼 가볍게 구성했습니다.

### 업무 영역 템플릿 — 재무·영업/고객지원·법무·인사
부서 업무를 처음부터 구성하지 않도록 영역별 도구·스킬·Agent·파이프라인을 기본으로 넣어 두었습니다. 계산과 조항 점검은 **모델이 아니라 도구(코드)가 합니다** — 모델이 직접 계산한 비율·NPV가 틀리는 문제를 줄이기 위해서입니다.

| 영역 | 도구 | 스킬 | Agent | 파이프라인(단계 — 담당) |
|---|---|---|---|---|
| 재무 | 재무 지표 계산기(예산 대비 실적 차이·집행률, NPV·IRR·회수기간) | 예산실적차이분석·투자타당성검토·비용절감검토 | 재무 분석가·재무 검토자 | 재무 분석 보고: 요구사항 분석/계획 확정[사람 승인] → 재무 분석(재무 분석가) → 작성(C-level 보고서 작성자) → 최종 검토 판정(재무 검토자) |
| 영업/고객지원 | 영업 퍼널 계산기(단계별 전환율·가중 파이프라인 금액) | 영업제안메일작성·고객문의응대·영업실적분석 | 영업 분석가·영업 제안 작성자·고객지원 상담원 | 영업 제안 메일: 요구사항 분석/계획 확정[사람 승인] → 고객·실적 분석(영업 분석가) → 작성(영업 제안 작성자) → 최종 검토 판정(문서 검토자) |
| 법무 | 계약 조항 점검기(표준 조항 유무·주의 문구) | 계약서검토·규정요약·개인정보처리점검 | 계약서 검토자·규정 요약가 | 계약서 1차 검토: 검토 요청 정리[사람 승인] → 조항 검토(계약서 검토자) → 최종 검토 판정(문서 검토자) |
| 인사 | 인사 지표 계산기(이직률·입사율, 채용 퍼널 전환율, 채용 소요일, 연차 발생 일수 — 근로기준법 제60조), 채용 공고 점검기(차별 소지 문구·빠진 필수 항목) | 채용공고작성·면접평가설계·인사지표분석·온보딩계획수립 | 채용 담당자·인사 분석가·온보딩 플래너 | 채용 공고·면접 설계: 채용 요구사항 확정[사람 승인] → 공고·면접 설계(채용 담당자) → 최종 검토 판정(문서 검토자) |

- "최종 검토 판정" 단계는 **Gate A와 요구사항 추적성이 둘 다 통과**해야 하고, 미달이거나 검토자가 "보완 요청"으로 판정하면 작성(법무는 조항 검토) 단계로 되돌려 다시 씁니다.
- **고객지원 상담원**·**규정 요약가**는 파이프라인 없이 대화에서 `@고객지원 상담원`처럼 부릅니다. 지식 베이스에 응대 정책·사내 규정을 등록해 두면 그 내용을 근거로 답합니다.
- 법무 결과물은 **1차 검토용이며 법률 자문이 아닙니다** — 결과물 끝에 이 문구가 붙습니다. 계약 조항 점검기는 키워드 기반이라 다른 표현으로 쓴 조항을 "찾지 못함"으로 낼 수 있습니다.
- **인사**: 채용 공고는 **채용 공고 점검기**가 성별·연령·용모·키·체중·혼인·임신·출신 지역·가족의 직업·재산·종교·사진 요구 같은 차별 소지 문구(남녀고용평등법·연령차별금지법·채용절차법 제4조의3 기준)와 빠진 필수 항목(담당 업무·자격·고용 형태·근무지·근무 시간·급여·전형·지원 방법·마감일)을 찾고, 주의 문구가 0건이 될 때까지 고칩니다. 면접 설계는 모든 지원자에게 같은 질문·같은 행동 기준 평가표를 쓰고, 묻지 말아야 할 질문을 함께 적습니다. 키워드 기반 1차 점검이라 표현을 바꾼 문구는 놓칠 수 있습니다 — 법률 자문이 아닙니다.
- **인사 분석가**(이직률·채용 퍼널 — 사내DB조회로 인사 DB를 직접 조회 가능)·**온보딩 플래너**(입사 전~90일 계획 — 캘린더조회로 팀 일정 확인)는 대화에서 `@인사 분석가`처럼 부릅니다. 연차 일수는 입사일 기준·출근율 80% 이상 가정이며, 회계연도 기준·단체협약이 있으면 그 기준을 따르세요. 지원자·직원 개인정보는 결과물에 옮기지 않도록 스킬에 정해 두었습니다.
- 실측(로컬 35B 모델, 2026-11-25): 계약서 1차 검토는 일방적 조항(손해배상 무제한·한쪽만 해지·자동 갱신)을 모두 위험으로 잡고 인용 문구가 원문과 일치했으며(약 28분), 영업 제안 메일은 퍼널 전환율 8개가 모두 정확했습니다(약 15분).
- 이미 설치된 플랫폼에도 다음 서버 기동 때 자동으로 추가됩니다(같은 이름이 있으면 건드리지 않음).

<h2 id="scenario">6. 실전 시나리오 5가지</h2>

### 시나리오 A — 가벼운 질문 하나
📍 **메뉴**: 대화

대화에서 `@코드 검증가 이 함수 리뷰해줘`처럼 바로 멘션합니다. 결재·Gate 없이 가장 빨리 답을 받습니다. 누구를 부를지 모르겠으면 홈의 "AI에게 일 맡기기"에 할 일을 적고 추천을 받으세요.

### 시나리오 B — 작은 기능 하나 개발
📍 **메뉴**: 홈(또는 업무 요청) → AI 에이전트 생성 → AI 에이전트 관리 → 내 업무 → 결재

업무 요청 → 할 일로 나누기 → (맞는 기본 Agent가 없으면) "AI 에이전트 생성"(crewai) → 온보딩 승인 → 협업 워크스페이스의 "이 업무의 AI 에이전트 실행" → 결과물 결재.

### 시나리오 C — 복잡한 신규 기능·게임 개발(여러 역할 협업)
📍 **메뉴**: 업무 요청 → 내 업무(또는 Crew 빌더)

- **품질·추적성이 중요하면**: 정식 업무로 만들고 할 일의 워크스페이스에서 **"소프트웨어 개발 파이프라인"**을 실행합니다. 1단계 계획만 승인하면 요구분석부터 품질 판정까지 Gate 기준으로 자동 진행됩니다.
- **빨리 결과를 보고 싶으면**: Crew 빌더에서 개발 Agent 여러 개를 골라 바로 실행합니다.

### 시나리오 D — 시장조사·전략 보고서
📍 **메뉴**: 업무 요청 → 내 업무

홈에서 "추천 받기" → "업무로 만들고 바로 실행"을 누르거나, 업무 요청을 올리고 할 일의 워크스페이스에서 **"사업/기획 업무 처리 파이프라인"**(조사·분석 → 기획 → 작성 → 검증)을 실행합니다. 보고서 하나만 필요하면 "제안서 작성"·"실적 보고" 파이프라인이 더 가볍습니다. 같은 팀으로 자주 돌릴 거라면 외부 자료 조사가·3C4P SWOT 분석가·사업전략 수립가 등을 팀으로 묶어 그 파이프라인을 연결해 두고 대화에서 `@팀이름`으로 부르면 됩니다. 단계 구성을 바꾸려면 "파이프라인 관리"에서 새 템플릿을 만드세요.

### 시나리오 E — 매주 반복되는 보고를 자동으로
📍 **메뉴**: 헤더 ⚙ 내 설정(연동 설정)

"정기 실행"에 매주 월요일 09:00 "실적 보고 파이프라인"을 등록하고, "외부 알림" 또는 "메일 알림"에 "파이프라인 사람 승인 대기·완료"를 켭니다. 월요일마다 실행이 시작되고, 1단계 승인이 필요할 때와 끝났을 때 알림이 옵니다. 보고서가 끝나면 이어서 발표자료를 만들게 하려면 "이벤트 트리거"로 "실적 보고 파이프라인이 끝나면 → 다음 파이프라인 시작"을 추가합니다.

<h2 id="menu">7. 메뉴 전체 지도</h2>

맨 위 메뉴는 두 줄입니다 — 첫 줄은 업무 흐름대로 **일하기 · 검토·결재 · 현황 ▾**(모든 사용자, 현황 안의 화면은 유형별로 다름), 둘째 줄은 **"설정 ▾"**(admin·manager). 이용 가이드는 헤더의 **❓ 도움말**·**🔍 메뉴 찾기**로, 연동 설정(내 API 키 등)은 헤더의 **⚙ 내 설정**으로 엽니다.

> 🔍 **메뉴를 외우지 않아도 됩니다** — 화면 맨 위 **"🔍 메뉴 찾기"**(단축키 **Ctrl+K**, Mac은 **⌘K**)에 화면 이름이나 하고 싶은 일(예: `비용`, `API 키`, `결재`, `환경변수`, `삭제가 안 될 때`)을 적으면 내 계정 유형으로 쓸 수 있는 화면과 이 가이드의 해당 절이 함께 나옵니다. ↑↓로 고르고 Enter로 이동하며, 초성(예: `ㅂㅇ` → 비용)으로도 찾습니다. **"❓ 도움말"**은 지금 보고 있는 화면에 맞는 이 가이드의 절을 바로 엽니다.

**일하기**: 홈(AI에게 일 맡기기·처리할 일·맡기는 방법·admin 관리 점검 — 로그인하면 처음 보이는 화면) · 대화 · 업무 요청 · 내 업무 · 할 일 보드

**검토·결재**: 인박스(결재 대기·실행 실패·파이프라인 실패·중단·품질 점검 미달 경고·완료 — 브라우저 알림을 허용하면 새 항목을 데스크톱 알림으로도 받음) · 결재 · 갤러리(여러 할 일의 결과물)

**현황 ▾**: 대시보드 · 성과 리뷰 · 비용 · 공정성 지표 · 활동 기록 · 조직도 · 인력 검색 — 대시보드·비용·공정성 지표·활동 기록은 admin·manager, 성과 리뷰는 viewer 제외, 조직도·인력 검색은 모두

**헤더**: 🔍 메뉴 찾기 · ❓ 도움말(이 가이드의 해당 절) · 내 계정 이름(비밀번호 바꾸기) · ⚙ 내 설정(연동 설정 — viewer 제외: 내 API 키, 정기 실행·이벤트 트리거는 admin·manager, 외부 알림·메일 알림·코드 저장소는 admin)

**설정**(admin·manager, 🔒 = admin 전용) — 그룹 버튼을 누르면 그 아래에 화면 목록이 작게 열립니다(바깥을 누르거나 Esc로 닫힘). 지금 보고 있는 화면이 속한 그룹 버튼에는 "모델 관리 · 모델 레지스트리"처럼 화면 이름이 함께 표시됩니다.

| 기준 시간 · AI가 맡은 작업량 | 예전 방식(사람이 직접)으로 한 건에 걸리던 시간을 넣으면, 기준 시간 × 완료 건수와 "완료까지 걸린 시간이 기준의 몇 %인지"가 나옵니다. 사람이 결과를 검토한 시간은 빼지 않은 추정입니다 |
| 먼저 손볼 곳 | 완료·종료 3건 이상일 때만, 실패가 잦음·한 번에 완료 50% 미만·재작업 많음·사람 대기가 AI 작업보다 김·기준 시간보다 느림을 근거 숫자와 함께 알려 줍니다 |

파이프라인의 **자세히**를 누르면 **단계별 흐름**이 나옵니다 — 단계마다 지나간 실행·시도 수·처음에 통과한 수·다시 작성한 수·사람 검토(반려·넘어감)·평균 AI 작업과 사람 대기 시간·전체 시간에서 차지하는 비중·지금 진행/대기 중인 건수. 시간 비중이 40% 이상인 단계에는 **병목** 표시가 붙습니다. 이 화면에서 **기준 시간**(분)을 넣거나 지웁니다(활동 기록에 남음). 아래에는 최근 실행과 주별 추이(완료 건수·완료까지 중앙값)가 있습니다.

**배운 점 — 같은 실수를 되풀이하지 않게.** 결재함에서 파이프라인 단계를 반려하며 적은 사유는 그 실행의 재시도뿐 아니라 이 화면의 **개선 제안**으로 모입니다(같은 사유가 또 나오면 횟수만 늘고, "다시" 같은 짧은 말은 버립니다). 한 단계가 같은 품질 기준에서 최근 60일 동안 3번 이상, 시도의 30% 이상 미달해도 그 기준에 맞춘 지시문이 제안됩니다. 제안을 **적용**하면(글을 고쳐도 됨) 다음 실행부터 그 단계 지시문 끝에 "이전 실행에서 배운 점"으로 들어갑니다. **무시**한 제안은 다시 만들어지지 않고, 적용 중인 것은 **끄기**로 뺍니다. **직접 추가**로 바로 적용할 수도 있습니다. 단계마다 8개까지이며, 자동으로 적용되지는 않습니다 — 사람이 확인한 것만 들어갑니다.

**변경 기록과 효과.** 파이프라인 관리에서 단계 설정을 바꾸거나(실제로 바뀐 값만) 단계를 추가·삭제·이동하거나, 배운 점을 켜고 끄면 기록이 남습니다. 변경마다 **그 전 30일**과 **그 뒤(다음 변경 전까지, 최대 30일)** 에 시작한 실행의 한 번에 완료 비율·완료까지 시간·그 단계의 다시 작성 비율을 나란히 보여 주고, 양쪽 모두 끝난 실행이 3건 이상이면 **좋아짐·나빠짐·비슷함**을 판정합니다(다른 요인도 섞이는 참고값). 단계 설정 변경과 배운 점 적용은 **되돌리기**(두 번 눌러 확정)로 원래대로 돌릴 수 있고, 그 뒤 같은 값이 다시 바뀌었으면 되돌리지 않습니다.

> 개선 효과를 보려면: 한 번에 한 가지만 바꾸고(배운 점 하나 적용, 또는 단계 설정 하나 변경), 1~2주 실행이 쌓인 뒤 변경 기록의 판정을 확인하세요. 나빠졌으면 되돌리기로 원래대로 돌립니다.

<h2 id="trouble">8. 자주 겪는 문제 — 이용자</h2>

증상별로 묶었습니다. 각 항목은 **원인 → 해결** 순서로 적었고, 화면 이름은 메뉴에 보이는 그대로입니다. 서버·설정 쪽 문제는 14절(운영자)에 있습니다.

### 로그인과 계정

**로그인하면 "로그인 시도가 너무 많아 잠시 막았습니다"가 뜬다**

- **원인**: 같은 아이디로 비밀번호를 5번 틀렸거나, 같은 PC(접속 주소)에서 여러 아이디로 20번 틀렸습니다. 비밀번호를 맞혀 보는 공격을 막기 위해 15분 동안 막습니다(막힌 동안은 맞는 비밀번호도 거절).
- **해결**: 15분 뒤 다시 시도하거나, admin에게 비밀번호 재설정을 부탁하세요(사용자 관리 → 비밀번호 재설정 — 재설정하면 잠금도 풀립니다). 로그인한 뒤에는 헤더의 **내 계정 이름**을 눌러 비밀번호를 바꿀 수 있습니다.

**비밀번호를 바꿨더니(또는 관리자가 재설정했더니) 다른 PC에서 로그아웃됐다**

- **원인**: 비밀번호가 바뀌면 그 전에 로그인한 곳은 모두 끊기게 돼 있습니다(새어 나간 비밀번호로 계속 쓰지 못하게).
- **해결**: 새 비밀번호로 다시 로그인하세요.

### 대화와 멘션

**`@멘션`했는데 아무 반응이 없다**

- **원인**: 부른 Agent·팀·사람이 아직 이 대화의 참가자가 아닙니다(가장 흔한 경우).
- **해결**: 입력창에 `@`를 다시 쳐서 자동완성 목록에서 고르세요. 목록에서 고르면 그 자리에서 대화에 초대된 뒤 멘션이 들어갑니다.

### 실행과 진행

**실행이 오래 걸린다**

- **원인**: 참여 Agent가 많을수록, 로컬(Ollama) 대형 모델일수록 오래 걸립니다(호출 한 번에 수십 초~몇 분). 같은 모델을 쓰는 다른 실행이 있으면 진행 표시에 "모델 대기 — 앞에 N건"이 보입니다.
- **해결**: 진행 표시의 단계·경과 시간·⏱ 예상 남은 시간을 확인하세요. 방향이 틀렸으면 "실행 중단 요청"으로 멈추고 다시 요청합니다. 늘 느리면 admin에게 알려 주세요(14절 — 모델·추론 모드 조정).

**서버를 다시 시작했더니 실행이 "중단됨"·"서버 재시작으로 중단됨"이 됐다**

- **원인**: 실행은 서버 프로그램 안에서 돌기 때문에, 서버가 꺼지면(재시작·PC 재부팅·잠자기 후 종료) 진행 중이던 실행이 함께 멈춥니다. 다시 켤 때 이런 실행은 **"서버 재시작으로 중단됨"**으로 표시됩니다.
- **해결**: 그 업무의 협업 워크스페이스 → "파이프라인 실행"의 **"이어서 실행"**(admin·manager)을 누릅니다.
  - 이미 끝난 단계는 다시 하지 않고, **진행 중이던 단계부터** 다시 실행합니다(그래프 엔진은 마지막 체크포인트부터). 그 단계의 AI 호출 비용은 다시 듭니다.
  - 자동으로 이어 가지는 않습니다 — 멈춘 원인이 실행 자체(무한 반복 등)였다면 재시작할 때마다 같은 비용이 반복될 수 있어, 사람이 확인하고 누르게 했습니다.
- **예방**: 긴 실행 중에는 서버를 끄거나 재시작하지 마세요. 대화 응답·단일 Agent 실행처럼 짧은 작업은 이어서 실행이 없으니 다시 요청하세요. admin이 작업 프로세스(`HAIR_WORKER_MODE=external`, 13절)를 쓰면 웹 서버를 재시작해도 실행이 계속됩니다.

**파이프라인이 "멈춤 감지 — N분 동안 진척이 없어 중단했습니다"로 멈췄다**

- **원인**: 단계가 45분 동안 진행 표시·작성 중 미리보기 없이 멈춰 있어 플랫폼이 정리했습니다(드물게 실행이 내부에서 대기 상태로 멈추는 경우가 있어 무한정 묶이지 않게 둔 안전장치).
- **해결**: 그 업무의 협업 워크스페이스에서 **"이어서 실행"**을 누르면 멈춘 단계부터 다시 돌립니다(끝난 단계는 다시 하지 않음).
- **참고**: 정리할 때 내부 상태(모든 스레드의 스택)를 "활동 기록"의 `pipeline_stage_stalled`에 남깁니다 — 반복되면 관리자(개발 담당)에게 알려 주세요. 로컬 대형 모델이라 한 번의 생성이 원래 45분을 넘는다면 서버의 `HAIR_STAGE_STALL_SECONDS`를 늘립니다(`0`이면 끔).

**검토 단계가 계속 작성 단계로 되돌아간다**

- **원인**: 검토자가 결과의 `## 판정`에 "보완 요청"을 썼습니다(5절 "개념").
- **해결**:
  1. 단계 결과의 **"판정"** 배지와 검토 결과의 **"보완 사항"**을 확인합니다.
  2. 요구사항이 모호해서 생기는 일이면 업무 요청을 구체적으로 고쳐 다시 실행합니다.
- **참고**: 재시도 횟수를 다 쓰면 그 단계는 사람 승인으로 올라옵니다(무한 반복하지 않음).

**검토는 "승인"인데 검토자가 지적한 오타가 결과물에 그대로 남아 있다**

- **원인**: 검토자가 승인하면서 고칠 곳을 짚었습니다("조건부 승인"). 기본 설정은 다시 쓰는 시간이 들지 않게 이를 통과로 처리합니다.
- **해결**:
  1. 결과물을 결재하기 전에 단계 결과의 노란 **"조건부 승인"** 배지에 마우스를 올려 짚은 문장을 확인하고, 직접 고치거나 **"부분 수정 요청"**으로 그 부분만 고칩니다.
  2. 이런 일이 잦은 파이프라인이면 파이프라인 관리에서 그 검토 단계의 **"엄격 검토 켜기"**를 눌러 자동으로 되돌려 고치게 합니다(시간이 더 듦).

### 결과물

**결과물에 이상한 한국어 낱말(사전에 없는 단어)이 섞여 있다**

- **원인**: 자동 언어 교정은 한자·외국 문자만 고치고, 한국어 글자로 된 뜻 없는 낱말은 고치지 않습니다.
- **해결**:
  1. 결과물 카드의 **"⚠ 낱말 확인"** 배지에 마우스를 올려 낱말과 앞뒤 문맥을 확인합니다.
  2. **"부분 수정 요청"**으로 그 문장만 고쳐 달라고 하거나 직접 편집합니다.
- **배지가 아예 안 보이면**: 서버에 낱말 분석기(`korean` 확장)가 없거나 꺼져 있는 것입니다 — admin에게 문의하세요(14절).

**"평가 리포트" 버튼·링크가 안 보인다**

- **원인**(셋 중 하나):
  - 기능 도입(2026-11-25) 전에 만든 결과물·대화 응답이라 리포트가 없습니다.
  - Agent가 아니라 사람이 쓴 결과물입니다(평가 대상이 아님).
  - 서버가 `HAIR_EVAL_HTML_REPORT=0`으로 떠 있습니다.
- **해결**: 새로 실행한 결과물·응답부터 보입니다. 자세한 내용은 4절 "평가 리포트 — 확인과 활용"을 보세요.

**지식 베이스에 등록한 자료가 어떤 사람의 요청에서는 검색되지 않는다**

- **원인**: 그 문서의 **공개 범위** 밖에 있는 사람의 요청입니다. 검색은 요청한 사람 기준으로 거릅니다.
  - 전체 공개 — 모든 사람
  - manager 이상 — manager·admin
  - admin만 — admin
  - 팀 — 그 팀의 **사람 구성원** 중 **로그인 계정이 연결된 사람**("사람 인력 관리"에서 계정 연결)과 admin
- **해결**: 설정 → 지식·데이터 → **"지식 베이스"** 문서 목록의 **"공개 범위"**를 확인하고 필요하면 바꿉니다. 팀 범위인데 안 보이면, 그 사람이 팀 구성원으로 등록돼 있는지와 사람 인력에 로그인 계정이 연결돼 있는지 확인하세요.
- **참고**: 정기 실행·이벤트 트리거는 **등록한 사람**을 요청자로 봅니다. 요청자를 알 수 없는 경우(드물게 도구가 별도로 실행될 때)에는 **전체 공개 문서만** 씁니다. Agent 결과물에서 나온 지식은 늘 전체 공개입니다.

### 알림·비용·결재

**다른 탭·창에 있으면 결재 대기·실행 결과를 늦게 안다**

- **원인**: 브라우저 알림이 꺼져 있으면 새 항목이 인박스 탭의 건수 배지로만 표시됩니다.
- **해결**: 처음 로그인할 때 브라우저가 묻는 **알림 허용**을 누르세요(놓쳤다면 주소창 왼쪽 자물쇠 → 알림 → 허용). 허용하면 HAIR 탭이 열려 있는 동안 약 20초마다 확인해 **새로 생긴** 결재 대기·AI 실행 실패·파이프라인 실패·중단·품질 점검 미달·완료를 데스크톱 알림으로 띄웁니다(로그인 직후 이미 있던 항목은 알리지 않음). 알림을 누르면 결재 또는 인박스 화면으로 갑니다.
- **참고**: HAIR 탭을 모두 닫으면 알림이 오지 않습니다. 탭이 닫혀 있을 때도 받으려면 "연동 설정"의 외부 알림(웹훅)·메일 알림을 쓰세요.

**비용이 걱정된다**

- **모델을 호출하는(비용이 드는) 버튼**: 이름에 "실행"이 붙은 버튼(AI 에이전트 실행·팀 Agent 실행·파이프라인 실행·Crew 실행), "AI 의견 보기", "AI로 추천 받기", "AI로 분해 제안 받기", "부분 수정 요청"의 "수정안 만들기".
- **비용이 없는 것**: 설정 저장(모델 설정·파인튜닝·팀·파이프라인 등록), 홈의 "추천 받기".
- **실제 사용량·금액 확인**: "비용" 탭, "모델 레지스트리"의 실제 사용량 표.
- **한도**: admin이 "비용" 탭 맨 위 **"AI 사용 한도"**에서 **사용자별 한 달 한도**와 **조직 전체 한 달 한도**(USD), 경고 비율, viewer의 AI 호출 허용 여부를 정합니다. 기본은 제한 없음입니다(13절 "AI 사용 한도").
  - 비용은 이번 달(UTC 1일부터) 토큰 × "모델 레지스트리" 단가로 계산합니다. **단가를 등록하지 않은 모델(로컬 Ollama 등)은 0으로 셉니다** — 한도를 쓰려면 클라우드 모델 단가를 먼저 등록하세요.
  - admin은 사용자별 한도에서 빠지고 조직 전체 한도만 적용됩니다.

**"AI 비용 한도에 도달해 AI를 부르지 않았습니다"가 나온다**

- **원인**: 이번 달 내 사용(또는 조직 전체 사용)이 admin이 정한 한도에 닿았습니다. 그 실행은 모델을 부르지 않고 멈췄고, 비용은 들지 않았습니다.
- **해결**:
  1. 다음 달 1일(UTC)에 자동으로 다시 쓸 수 있습니다.
  2. 급하면 admin에게 한도 조정을 요청하세요("비용" 탭 → "AI 사용 한도").
  3. 단가가 없는 로컬 모델(Ollama)로 바꾸면 한도에 들어가지 않습니다("AI 에이전트 관리"의 모델 설정).
- **viewer 계정**이 "AI를 부를 수 없도록 설정돼 있습니다"를 보면, admin이 viewer의 AI 호출을 껐다는 뜻입니다.

**내가 요청한 배정을 내가 승인하고 싶다**

- **다른 사람·Agent·팀을 배정 요청한 경우**: 요청자는 승인할 수 없습니다(자기 승인 금지). 다른 admin·manager가 승인해야 합니다.
- **본인을 배정하는 셀프배정인 경우**: 처음부터 결재 없이 확정되므로 승인할 것이 없습니다.

<h2 id="agent">9. 사람·Agent·팀 준비</h2>

📍 **메뉴**: 설정 → 리소스 관리 ▾(리소스 매칭/배정 · 사람 인력 관리 · AI 에이전트 생성 · AI 에이전트 관리 · Crew 빌더 · 팀 관리) · 지식·데이터 ▾(도구/스킬 Pool · 지식 베이스)

일을 맡을 사람과 Agent를 등록하고, 여러 명을 팀으로 묶고, Agent가 쓸 스킬·지식을 준비합니다. 기본 Agent 39개와 스킬·도구는 처음부터 들어 있으므로, 필요한 것만 더하면 됩니다.

### 사람 인력 관리(admin·manager)

📍 **메뉴**: 설정 → 리소스 관리 → 사람 인력 관리

1. 먼저 admin이 **"사용자 관리"**에서 로그인 계정을 만듭니다(13절).
2. **"사람 인력 등록"**에서 계정을 고르고(이름이 채워짐) 역할·스킬(Enter 또는 "추가"로 칩)·비용·사번을 넣고 **"등록"**합니다. **계정을 연결해야** 그 사람이 "내 업무"에서 자기 일을 볼 수 있습니다 — 나중에 목록의 "계정 연결"로 이어도 됩니다.
3. 매칭 점수: 가용성 40%(성과점수가 없으면 60%)·적합도 35%·비용 25%(없으면 40%, 낮을수록 유리). 처음에는 가용성이 "가능"이어야 후보에 나옵니다.
4. **동의** — 성과 리뷰 사전 동의입니다. 동의한 사람만 성과점수를 넣을 수 있고, 동의를 철회하면 점수가 즉시 지워집니다.
5. **오프보딩**은 매칭 후보에서 빼는 것(되돌리는 버튼 없음), **삭제**(admin)는 기록 자체를 지웁니다(확정 배정이 있으면 막힘).

### 단일 Agent 만들기(admin·manager, "AI 에이전트 생성")
📍 **메뉴**: 설정 → 리소스 관리 → AI 에이전트 생성 · AI 에이전트 관리

1. 먼저 **업무 요청과 할 일**이 있어야 합니다(3절 1~2단계). 기본 Agent 39개 중 맞는 역할이 있으면 만들 필요가 없습니다. Agent는 할 일의 역할명을 이름으로 받아 만들어집니다.
2. 할 일을 하나 이상 고르고 생성 방식을 정합니다.
   - **crewai**(기본, 비용 발생): CrewAI Agent로 만듭니다. "Crew 빌더"·"팀 Agent 실행"·파이프라인에서 다른 Agent와 함께 일하려면 이 방식이어야 합니다.
   - **simple_llm**(비용 발생): 모델을 한 번 호출하는 가장 가벼운 Agent입니다.
   - **stub**(무료): 모델을 부르지 않는 자리표시자입니다. 흐름만 시험할 때 씁니다(실제 일은 못 함).
   - 필요 스킬에 내부지식검색·조직배정관계조회 등이 있으면 관련 도구가 생성 때부터 붙습니다.
   - 같은 할 일(역할)에 이미 Agent가 있으면 새로 만들지 않고 기존 Agent를 다시 씁니다("재사용" 배지).
3. 만든 Agent는 **"AI 에이전트 관리"**에서 admin이 **"온보딩 승인"**(온보딩 대기 → 활성)을 눌러야 배정·실행·대화에 쓸 수 있습니다.

### AI 에이전트 관리 — ⚙ 설정 창

📍 **메뉴**: 설정 → 리소스 관리 → AI 에이전트 관리

- **목록**: 맨 앞 열은 역할(이름을 정했으면 함께)과 코드, 그다음 스킬·상태·생성 방식·**LLM**(Agent별 모델을 정하지 않았으면 "기본 모델" — 플랫폼 기본 모델을 씀, 11절)·상세(소속팀·비용·성과점수·자동평가·최근 결과물). 행의 버튼은 **"실행(일 시키기)"**과 **"⚙ 설정"**, 새로 만든 Agent에는 **"온보딩 승인"**(admin)이 보입니다.
- **⚙ 설정 창**(모두 저장만 하므로 비용 없음)
  - **기본**: 이름, **LLM**(provider / model).
  - **파인튜닝**: 온도(temperature)·실행 시간 제한·최대 반복·추론 모드(reasoning)·품질 검토 등. 온도·실행 시간 제한·최대 반복·품질 검토는 대화 @멘션과 업무 실행을 포함한 **모든 실행**에, 분당 호출 수·재시도·코드 실행·컨텍스트 자동 축소는 **Crew 실행에만** 적용됩니다(창에 구역별로 표시). 품질 검토를 켜면 호출이 한 번 늘어 그만큼 느려집니다.
  - **스킬·도구·MCP 서버** 연결.
  - **⚡ 최적화 추천**: 역할 특성(심층추론·정밀/신속·표준 중 하나)에 맞는 provider·model·파인튜닝 값을 규칙으로 추천합니다(비용 없음). "등록된 모델 중 선택"에 레지스트리의 활성 모델이 순위대로 나오므로 1위가 아닌 모델을 골라도 됩니다(★ = admin이 모델 레지스트리에서 그 tier에 직접 매핑한 모델). **성능 테스트 결과를 반영합니다**: Agent가 도구를 쓰는데(스킬에 연결된 도구·직접 연결한 도구·파이프라인 단계의 필수 도구) 모델 레지스트리의 전체 점검에서 **도구 호출을 못 한 모델은 ✗로 표시되고 고를 수 없습니다**. 수치 변형·한국어 혼입, 그리고 추론을 끄는 Agent에 한해 "추론 끔 무시"는 ⚠로 표시하고 순위를 뒤로 미룹니다. 성능 테스트(전체 점검)를 하지 않은 모델은 능력을 판단하지 않으므로 먼저 모델 레지스트리에서 **전체 점검**을 돌리세요(11절). 추천값은 입력란에 채워질 뿐이니 저장은 직접 누르세요. **"AI 의견 보기"**는 AI에게 추가 검토를 받습니다(비용 발생).
  - **위험 구역**(admin, 창 맨 아래): **"오프보딩(사용 중지)"** — 새 일에 배정·실행되지 않게 멈춤(기록은 남고 이 화면에서 되돌리는 버튼은 없음). **"완전히 삭제"** — Agent 기록을 지움(되돌릴 수 없음). 둘 다 확인 창을 거칩니다.
- 여러 Agent의 모델을 한꺼번에 바꾸려면 **"LLM 설정 최적화"**(admin, 11절)를 씁니다.

### 여러 명을 묶는 두 가지 방법 — 팀과 Crew

한 업무에 사람 여러 명과 Agent 여러 개를 묶는 방법은 두 가지입니다 — 다시 쓸 **팀**으로 등록하거나(방법 A), **Crew 빌더**에서 그때그때 고르거나(방법 B).

### 방법 A — 팀(Team) 등록(재사용, 정식 업무에 적합)
📍 **메뉴**: 설정 → 리소스 관리 → 팀 관리(admin·manager)

1. **"팀 등록"**에 이름·설명을 넣습니다. **Task ID나 Brief ID를 넣으면 "TF팀"**(그 업무 전용 조직), 비우면 여러 업무에 다시 쓰는 **범용 팀**이 됩니다.
2. 팀 카드의 **"멤버 추가"**로 사람과 Agent를 역할 라벨과 함께 원하는 만큼 넣습니다(예: 사람 2명 + Agent 10개).
3. **실행 방식** — 팀은 멤버를 넣은 순서대로 앞 사람 결과를 이어받아 실행합니다(순차, sequential). 단계가 여러 개인 업무라면 아래 6번처럼 **파이프라인을 연결**하는 것이 가장 안정적입니다.
   - ⚠️ **위임형(hierarchical — 매니저가 팀원에게 일을 쪼개 위임)은 새로 지정할 수 없습니다.** 실측에서 매니저가 실제로 위임하지 않고 계획만 요약하거나 혼자 처리하는 문제가 반복됐기 때문입니다. "기본값 저장"에서 hierarchical을 고르거나 매니저를 지정하면 "신규로 hierarchical 모드를 지정할 수 없습니다" 오류가 납니다. 같은 이유로 새 팀에는 역할 라벨에 "매니저"가 들어간 Agent를 넣을 수 없습니다("리드"·"PM" 같은 라벨을 쓰세요). 예전에 위임형으로 만든 팀은 그대로 위임형으로 동작합니다.
4. **팀 상태** — 팀 카드 제목 옆 배지로 보입니다.
   - **온보딩 대기**: TF팀은 이 상태로 시작하며, 이때는 **대화 @멘션과 배정 후보에 나오지 않습니다**. 범용 팀은 바로 "활성"으로 시작합니다.
   - **활성**: **"온보딩 시작"**을 누르면 이 상태가 되고 그때부터 멘션·배정이 됩니다.
   - **비활성화됨**: "비활성화" 버튼이나, TF팀이면 **"미션 완료"**(완료 시각 기록)로 전환합니다. 이후로는 멘션·배정 후보에 나오지 않습니다.
   - **팀 삭제**는 그 팀에 확정 배정이 남아 있으면 막힙니다 — 할 일 상세의 "배정 취소"로 먼저 정리하세요.
5. **실행하는 곳** — 두 군데입니다.
   - 대화에서 **`@팀이름`** 멘션(2절 3단계): 파이프라인이 연결돼 있으면 그 파이프라인이, 아니면 멤버가 순서대로 실행돼 결과가 메시지로 올라옵니다.
   - 할 일에 팀을 배정한 뒤 협업 워크스페이스의 **"팀 Agent 실행"**: 결과가 Agent별 결과물과 결재로 그 할 일에 쌓입니다.
6. **파이프라인 연결** — 팀 카드 "기본값 저장" 폼의 **"연결 파이프라인"**을 고르면, 그 팀을 멘션할 때 단발 실행 대신 그 파이프라인(5절)을 탑니다. 예를 들어 "소프트웨어 개발 파이프라인"을 연결하면 멘션 한 번으로 요구분석부터 품질 관리까지 7단계가 진행됩니다.
   - **"자율 개발 크루"**는 기본으로 있는 팀이 아닙니다. "팀 관리"에서 **정확히 이 이름으로** 만들면 서버가 개발 7단계에 필요한 Agent들(요구사항 분석가·AA·DA·개발 계획 수립가·개발자 4명·UI 기획자·코드 검증가·테스트 계획 수립가·QA 기능테스터·품질 관리자 등)을 멤버로 채우고 "소프트웨어 개발 파이프라인"에 연결해 줍니다.
   - 팀은 `hair reset-data` 초기화 대상입니다. 남겨야 하면 팀 카드에서 **"초기화 시 보호"**를 켜 두세요. Agent 자체는 초기화돼도 남으므로 같은 이름으로 팀만 다시 만들면 됩니다.
7. **리포팅** — "성과 리뷰"·"비용" 탭에 팀도 한 행으로 나옵니다(팀 자체의 성과점수·단가는 없어 "확정 배정 수"만 집계 — 비용은 멤버 Agent 쪽에 잡힘). 팀 카드의 **"실행 이력 보기"**는 "Crew 빌더" 실행 이력을 그 팀 것만 보여 줍니다.

### 방법 B — Crew 빌더(즉석 조합, 등록 없이)
📍 **메뉴**: 설정 → 리소스 관리 → Crew 빌더(admin·manager)

팀으로 등록하지 않고 Agent를 골라 바로 함께 실행합니다. 하위 모드는 세 가지입니다.

- **"업무에 바로 실행"**(기본) — 실제 할 일에 결과를 남깁니다. Agent 여러 개와 처리 방식을 고릅니다.
  - **sequential(권장)**: 순서대로 앞 결과를 이어받습니다. Agent 행마다 **"병렬(독립 작업)"**을 체크하면 그 Agent는 앞 결과를 기다리지 않고 동시에 시작합니다(서로 결과가 필요 없는 독립 작업용 — 5절의 "계획 분담"과는 다른 기능).
  - "병렬"을 하나도 체크하지 않은 sequential이면 **"자기 검토"**를 켤 수 있습니다 — 각 Agent가 초안을 원 요구사항과 대조해 한 번 더 고친 뒤 제출합니다(결과물에는 최종본만, 초안은 실행 이력에만 남음).
  - hierarchical(매니저 위임)은 매니저가 실제로 위임하지 않고 끝나는 경우가 많아 권하지 않습니다.
- **"즉석 테스트(저장 안 됨)"** — 할 일에 연결하지 않고 협업 구조만 시험합니다. 결과가 남지 않습니다.
- **"실행 이력"** — 과거 실행의 협업 다이어그램·토큰 사용량·품질 점검 점수를 다시 봅니다. 같은 할 일을 다시 실행한 기록이 있으면 **"이전 실행과 비교"**로 최종 결과물과 Agent별 결과물을 줄 단위로 비교합니다(재시도하면서 전에 되던 내용이 사라지지 않았는지 확인하는 용도).

**조합 저장** — "업무에 바로 실행"을 한 번 하면 결과 아래 "이 조합을 저장해 다음에 재사용" 패널이 나옵니다(admin·manager). 방금 쓴 구성을 **"팀으로 저장"**하거나 기존 파이프라인에 **"파이프라인 단계로 저장"**할 수 있습니다(hierarchical로 실행한 조합은 매니저를 리드로 한 계획 분담 단계로 저장되며, 매니저를 직접 지정해 실행했을 때만 저장 가능).

### Agent 그룹(팀) 만들기
위 "방법 A"를 보세요. "AI 에이전트 생성"에서 할 일 여러 개로 Agent를 한꺼번에 만든 직후에는 결과 화면의 **"팀으로 묶기"**로 "팀 관리"에 가지 않고 바로 팀을 만들 수 있습니다.

### Skill 관리(admin·manager, "도구/스킬 Pool")
📍 **메뉴**: 설정 → 지식·데이터 → 도구/스킬 Pool

화면 맨 위의 **도구 N | 스킬 N** 버튼으로 도구 목록과 스킬 목록을 번갈아 봅니다(분류 필터 — 일반업무·개발업무 — 는 둘 다에 적용). 새로 만들 때는 각 목록 아래의 접힌 **"＋ 신규 도구 생성"·"＋ 신규 스킬 생성"·"＋ 마크다운으로 스킬 가져오기"**를 펼칩니다. 행에는 **"수정"**만 보이고, 내보내기·삭제는 **"⋯"**를 눌러 엽니다. 긴 설명은 두 줄까지만 보이고 마우스를 올리면 전체가 보입니다.

Skill은 이름표가 아니라 **Agent와 기본 AI에게 실제로 넣어 주는 작업 지침**입니다. 각 Skill은 네 칸으로 나뉩니다(모두 선택 입력).

- **지침(설명)** — 무엇을 어떻게 하는지(핵심).
- **출력 형식** — 결과물 구조(예: "배경 → 목표 → 실행계획 순서").
- **예시** — 실제로 어떻게 쓰는지 보여 주는 짧은 본보기.
- **제약사항** — 하지 말아야 할 것(예: "검색되지 않은 사실을 추측하지 않는다", "출처를 반드시 밝힌다").

네 칸 모두 대화·Agent 실행 어느 경로든 함께 들어갑니다. 지침만 쓴 Skill도 그대로 동작하고, 나머지 칸은 채운 만큼 지시가 구체해집니다.

- **마크다운 내보내기·가져오기** — Skill 행의 **"⋯" → "내보내기"**는 frontmatter(name·category·augmentation_mode·tool)와 `## 지침`·`## 출력 형식`·`## 예시`·`## 제약사항` 섹션으로 된 `.md` 파일을 내려받습니다. 아래 **"마크다운으로 스킬 가져오기"**에 그 형식의 파일을 올리거나 붙여 넣고 **"등록하기"**를 누르면 새 Skill이 됩니다(파일을 고르면 최소 형식을 먼저 점검해 보여 줌, 같은 이름이 있으면 거부). 다른 서버의 Skill을 옮기거나 여러 Skill을 편집기에서 한꺼번에 다듬을 때 씁니다.
- **"스킬생성"** Skill — 어떤 업무용 Skill이 필요한지 설명하면, 위 가져오기 형식의 마크다운으로 새 Skill 초안을 써 줍니다(대화 스킬 드롭다운에서 바로 선택 가능). 등록은 대신 하지 않으므로, 초안을 붙여 넣고 **"등록하기"**는 사람이 직접 누릅니다.

**도구** — Agent가 실제로 부르는 기능입니다. 종류는 native(플랫폼 내장)·mcp_remote·mcp_stdio(외부 MCP 서버)·custom_python(admin — Python 함수를 직접 등록, Docker가 있으면 네트워크 차단 컨테이너에서 실행)입니다. **"쓰기"** 배지는 외부로 메시지를 보내거나 데이터를 바꾸거나 명령을 실행하는 도구로, 외부 데이터를 이미 읽은 실행에서는 자동으로 쓰지 못하고 사람 승인으로 넘어갑니다(4절).

### 지식 베이스 운영(admin·manager)

📍 **메뉴**: 설정 → 지식·데이터 → 지식 베이스

- **등록**: "지식 자료실"에 문서를 올리거나 "텍스트 직접 입력"으로 넣습니다(admin이 넣으면 결재 없이 바로 등록). 대화 메시지·승인된 결과물의 **"지식베이스로 보내기"**는 **신청**으로 들어오고, admin이 결재에서 승인해야 등록(임베딩, 비용 발생)됩니다. 등록 내용은 그 시점의 사본이라, 원본을 고쳤으면 다시 보내 "갱신 요청"으로 바꿉니다.
- **공개 범위**: 문서마다 전체·manager 이상·admin만·특정 팀 중 하나. 검색은 **요청한 사람이 볼 수 있는 문서만** 씁니다(8절 "지식 베이스에 등록한 자료가…").
- **임베딩 설정**: 검색에 쓰는 임베딩 provider·모델은 시스템 전체에 하나입니다. 바꾸면 이전 모델로 색인한 자료는 검색되지 않으니 다시 등록해야 합니다. top_k(검색 1회 결과 수, 기본 3).
- **검색 엔진**: 화면 통계 줄의 검색 엔진이 `chroma`(벡터 DB, 빠름)인지 `sqlite`(하나씩 비교)인지 보입니다(14절 "지식 검색이 느리다").

<h2 id="design">10. 파이프라인 설계와 평가 기준</h2>

### 새 파이프라인 만들기(admin·manager, "파이프라인 관리")
📍 **메뉴**: 설정 → 지식·데이터 → 파이프라인 관리

화면에는 템플릿마다 **요약 한 줄**(이름·단계 수·사람 승인 단계 수·도메인과 단계 흐름 "요구분석 → 설계 → …")만 보입니다. **"편집"**을 누른 템플릿 하나만 펼쳐져 단계 카드와 설정이 보이고, 다른 템플릿을 편집하면 앞의 것은 접힙니다. 저장한 뒤에도 펼친 템플릿은 그대로 열려 있습니다.

1. **"파이프라인 등록"**으로 이름·설명·도메인(예: software_dev, biz_strategy)을 정합니다.
2. **"단계 추가"**로 단계를 하나씩 쌓습니다. 모드를 고르면 역할 선택 칸이 바뀝니다 — 단독은 1명, 순차 릴레이는 여러 명과 순서, **계획 분담은 첫 번째 역할이 리드이고 팀원이 1명 이상** 필요합니다.
   - 함께 정하는 것: 공통 지시문, Gate 통과 비율(%), 최대 재시도, **"사람 승인 필요"**, **산출물 형식**(텍스트·마크다운·HTML·코드 — 코드면 화면에 문법 강조), **"요구사항 정의 단계"**(요구사항 추적성의 기준 문서를 내는 단계, 지정이 없으면 1단계), **"요구사항 추적성 검사"**(이 단계 결과물을 그 요구사항과 대조).
   - 만든 뒤에도 단계 카드에서 요구사항 정의 단계·추적성 검사를 켜고 끌 수 있고, Gate 기준이 있는 단계에는 **"검토 실패 시"**(이 단계만 재시도 / 앞 단계로 되돌림) 선택이 보입니다.
   - **이 단계 모델**: 비워 두면 단계 대표 Agent의 모델로 실행합니다. 요구사항 정리·형식 검토처럼 가벼운 단계만 작은 로컬 모델로 보내면 큰 모델을 기다리는 시간이 줄어듭니다 — Agent 설정을 바꾸지 않으므로 같은 Agent를 쓰는 다른 파이프라인에는 영향이 없습니다(목록은 "모델 레지스트리"에 등록된 모델). 요구사항 추적성 판정 같은 짧은 내부 채점은 **보조 작업 모델**(LLM 설정 최적화)이 정해져 있으면 그 모델로 보냅니다.
   - 예전의 **병행 위임**(리드가 "Delegate work to coworker" 도구로 그때그때 위임)은 실측에서 위임 대신 계획만 요약하거나 혼자 처리하고 끝나는 경우가 반복돼 2026-11-26에 없앴습니다. 남아 있던 단계는 같은 리드·팀원의 **계획 분담**으로 자동 전환되고(활동 기록 `pipeline_stage_mode_migrated`), 리드가 빠뜨린 팀원도 자동으로 하위 작업을 받습니다.
   - **여러 Agent가 일을 나눠 맡아야 하면 계획 분담을 쓰세요** — 리드가 팀원별 하위 작업을 JSON 계획으로 내면 플랫폼이 팀원을 실행하고(클라우드 모델이면 최대 3명 동시, 로컬 Ollama는 한 명씩), 리드가 결과를 하나의 완성본으로 합칩니다. 계획을 읽지 못하면 단계에 적은 팀원별 지시로 대신 진행해 멈추지 않습니다. Gate는 합친 최종본으로 판정하며 두 실행엔진에서 모두 동작합니다. 로컬 모델에서는 리드 호출 2번(계획·병합)만큼 순차 릴레이보다 오래 걸립니다.
3. 단계 순서는 카드의 위·아래 버튼으로 나중에도 바꿀 수 있습니다.
4. 단계 카드에서 더 할 수 있는 것: **필수 도구** 추가·삭제(4절 "필수도구" 배지), **"엄격 검토 켜기"**(조건부 승인도 되돌려 고치게 — 5절 "개념"), **"검토 실패 시"** 되돌릴 단계, 템플릿 **"비활성화"**·**"템플릿 삭제"**(admin).
5. **결과물 실행 점검을 통과 조건으로**: 단계 Gate 목록에 `test_execution`(코드 테스트 실제 실행)이나 `browser_execution`(HTML 화면 실행)을 넣으면 기록만 하던 점검이 그 단계의 통과 조건이 됩니다.

### 평가 기준 설정(admin, "평가 기준" 화면)
📍 **메뉴**: 설정 → 운영 관리 → **평가 기준** 🔒

Gate A-G를 채점할 때 쓰는 기준을 화면에서 바꿉니다. **저장하면 다음 평가부터** 적용되고(서버 재시작 불필요), 이미 기록된 평가는 다시 채점하지 않습니다. 바꾼 내용은 "활동 기록"에 남습니다.

| 항목 | 기본값 | 무엇이 바뀌나 |
|---|---|---|
| 기본 통과 기준(0~1) | 0.7 | Gate별 기준을 비워 둔 Gate의 통과 기준 |
| Gate별 통과 기준(A~G, 0~1) | 비움(= 기본) | 그 Gate 점수가 기준 이상이면 통과 — 결과물·대화 배지, 인박스 "품질 점검 미달 경고", 그 Gate를 판정에 쓰는 파이프라인 단계의 통과 여부 |
| 응답 시간 SLA p95·p99(초) | 30초·60초 | Gate C(신뢰성)·D(성능 계약)의 기준 — AI 호출 한 번 기준(여러 호출로 이루어진 실행은 재지 않음) |
| 추론 표지(한 줄에 하나, 최대 30개) | 근거·때문·므로·이유·판단·그러므로·그래서 | Gate G(관측성) — 결과물에 이런 낱말이 있으면 근거를 밝혔다고 봄. 평가 도구 기본 표지(영어 중심, "따라서"·"왜냐하면")에 더해짐 |
| 도구 범위 위반 감점(0~1) | 0.5 | 허용 범위 밖 도구를 썼을 때 해당 점수에서 빼는 값 |
| 모델·파이프라인별 덮어쓰기 | 없음 | 특정 모델 종류(로컬 Ollama·OpenAI·Anthropic)나 파이프라인에서만 다른 Gate 통과 기준. 우선순위: 위 기준 < 모델 < 파이프라인. 모델 덮어쓰기는 그 실행의 AI 호출이 **모두** 그 종류일 때만 적용(섞였으면 위 기준). 응답 시간 SLA는 나눌 수 없음(전역 하나) |

**이렇게 정하세요**

- **로컬(Ollama) 대형 모델을 쓰면** 한 번 호출에 수십 초~몇 분이 걸려 Gate D가 늘 미달입니다. 두 가지 방법이 있습니다.
  - **로컬 모델만 다르게(권장 — 클라우드와 함께 쓸 때)**: "모델·파이프라인별 덮어쓰기"에 **"모델: 로컬(Ollama)"** 행을 추가하고 D를 0(또는 낮은 값)으로 둡니다. 클라우드 모델 실행은 원래 기준으로 계속 잽니다.
  - **로컬 모델만 쓸 때**: SLA를 실제 응답 시간에 맞게(예: p95 180초·p99 300초) 늘립니다. 실제 응답 시간은 "모델 레지스트리"의 성능 테스트나 "비용" 탭의 평균 소요로 확인합니다.
- **목표 달성(A)을 더 엄격하게** 보려면 Gate A만 0.8로 올립니다. 기본 템플릿의 검토 단계가 Gate A로 판정하므로, 올리면 미달 → 작성 단계로 되돌림·재시도가 늘어 시간과 호출이 늘어납니다 — 리포트의 Threshold Sensitivity로 통과율 변화를 먼저 보세요.
- **업무 문서에서 쓰는 근거 표현**이 Gate G에 안 잡히면(예: "결론적으로", "~에 따르면") 추론 표지에 더합니다.
- 기준을 낮추는 것은 문제를 가리는 것일 수 있습니다 — 낮추기 전에 리포트의 원인 진단을 먼저 보세요.

**평가 도구 CLI와 맞추기(.aoo/targets.json)** — 화면 아래 **"targets.json 내려받기"**는 평가 도구의 `agent-eval gate`가 읽는 목표 파일 형식(`gate_default`·`gates`)으로 Gate 기준을 내려받습니다. 저장소의 `.aoo/targets.json`으로 두면 저장된 평가 결과 파일을 CLI로 채점할 때도 같은 기준을 씁니다. 반대로 그 파일 내용을 붙여 넣고 **"Gate 기준 가져오기"**를 누르면 Gate 기준만 반영합니다(SLA·추론 표지·감점은 그대로).

- **"기본값으로 되돌리기"**는 위 표의 기본값으로 돌립니다. 공장 초기화(`hair reset-data`)를 해도 평가 기준은 조직 설정이라 남습니다.
- admin만 볼 수 있고 바꿀 수 있습니다(manager는 화면이 보이지 않음).

<h2 id="models">11. AI 모델 운영</h2>

📍 **메뉴**: 설정 → 모델 관리 ▾(LLM 설정 최적화 🔒 · 모델 레지스트리 🔒)

어느 AI 모델이 일을 하는지 정하고, 모델마다 성능·능력을 재서 Agent에 알맞게 배치합니다. 모두 admin 전용입니다.

### 기본 모델과 보조 작업 모델 — LLM 설정 최적화

- **플랫폼 공통 기본 LLM**(카드): 모델을 따로 정하지 않은 Agent·대화 기본 AI·대화 요약이 쓰는 모델입니다. 정하지 않으면 서버 환경변수 → 설치된 API 키로 자동 판별한 모델 순서로 정해집니다(2절 4단계).
- **보조 작업 모델**(카드): 결과물의 한자·외국 문자 교정, 근거 없는 수치 문장 교정, 요구사항 추적성 판정처럼 **짧은 보조 호출**만 보내는 모델입니다. 본 모델과 **동시에 돌 수 있는** 모델(클라우드 소형 모델, 또는 메모리가 넉넉할 때 로컬 소형 모델)이어야 빨라집니다 — 메모리가 부족하면 로컬 모델 두 개가 번갈아 올라가 오히려 느려집니다.
- **여러 Agent 한꺼번에**: 아래 표에서 Agent마다 추천 모델(역할 특성·성능 테스트 반영, 도구 호출 못 하는 모델은 ✗)과 근거를 보고, 체크한 Agent에 **"선택 적용"**합니다("변경 필요만 선택"으로 바꿔야 할 것만 고를 수 있음). 이미 적용한 Agent도 다시 체크해 다른 모델로 바꿀 수 있습니다. 근거가 길면 두 줄까지 보이고 마우스를 올리면 전체가 보입니다.

### 모델 레지스트리

📍 **메뉴**: 설정 → 모델 관리 → 모델 레지스트리

모델별로 다음을 정합니다.

- **화면 구성** — 맨 위 **"모델 추가"**에서 provider를 고른 뒤 **목록 불러오기**(실제 보유 모델 조회) 또는 이름을 입력해 **직접 등록**합니다. 아래 표는 provider별로 모델마다 한 줄 요약(최적화 Tier·컨텍스트 한도·생성 속도와 점검 결과)이고, **설정 ▾**을 누르면 그 모델의 설정 패널이 펼쳐집니다. 패널에서 Tier·컨텍스트 한도·최대 출력·top_k/top_p·단가를 이름 붙은 칸으로 고치고 **저장** 한 번으로 바뀐 항목만 저장합니다(저장하지 않은 변경이 있으면 "저장하지 않은 변경이 있습니다" 표시). 성능 테스트 결과·이력과 측정 버튼도 패널 안에 있습니다. 저장·측정 후에도 펼친 패널은 그대로 열려 있습니다.
- **컨텍스트 한도** — Ollama 모델은 이 값이 실제 컨텍스트 창(`num_ctx`)으로 전달됩니다. 크게 잡을수록 긴 결과물이 덜 잘리지만 메모리를 더 씁니다.
- **추천값** — 설정 패널의 "추천값 채우기" 버튼은 컨텍스트 한도·최대 출력·top_k/top_p 칸을 추천값으로 채웁니다(노란 칸, 저장은 직접). Ollama는 모델 정보(학습 최대 컨텍스트, 층·KV 헤드 구조로 계산한 토큰당 메모리, 생각 기능, 제작자가 Modelfile에 정한 권장 샘플링 값)와 이 PC 메모리의 75%를 기준으로 8K·16K·32K·64K 중 들어가는 가장 큰 값을 고릅니다. Anthropic·OpenAI는 모델 계열별 공개 한도 표 기준이며, 표에 없는 모델은 추천하지 않습니다. 등록할 때 "등록하면서 추천 기본값도 함께 저장"(기본 켬)을 두면 등록과 동시에 저장됩니다.
- **생성 옵션** — top_k·top_p·최대 출력 토큰(비우면 모델 기본값, Ollama는 최대 출력을 비우면 32,768). 요구사항 추적성 채점처럼 짧은 답만 필요한 내부 호출은 이 값과 별개로 더 작은 상한(4,096)을 씁니다.
- **동시 실행 상한** — 이 모델에 한 번에 보내는 호출 수. 넘는 호출은 플랫폼 안에서 기다리고, **대화 응답이 파이프라인·Crew·지식 등록보다 먼저** 다음 차례를 받습니다(이미 모델이 처리 중인 생성은 끊지 않음). 비우면 Ollama는 1(Ollama는 한 모델에 요청을 하나씩 처리하므로 처리량은 그대로 — 실측: 긴 생성 3개가 줄 서 있을 때 대화 응답 107~121초 → 39~42초), 클라우드는 상한 없음. Ollama를 `OLLAMA_NUM_PARALLEL`로 여러 개 동시 처리하게 했다면 그 값으로 올리세요(서버 기본값은 `HAIR_OLLAMA_MAX_CONCURRENT`). 기다리는 동안 진행 표시에 "모델 대기 — 앞에 N건"이 보입니다. 작업 프로세스(`hair worker`)를 쓰면 자리 하나는 늘 대화 응답용으로 남겨 둡니다. 바꾼 값은 작업 프로세스를 다시 시작해야 그쪽에 반영됩니다.
- **단가**(100만 토큰당 입력·출력) — 입력한 모델만 금액이 계산됩니다. 같은 화면 아래 **"실제 사용량(최근 30일)"** 표에서 provider·모델별 호출 수·토큰·금액을 봅니다.
- **최적화 Tier 매핑** — 모델마다 심층추론·정밀/신속·표준을 체크해 두면(여러 개 가능) ⚡ 최적화 추천이 이름 추정보다 이 매핑을 먼저 씁니다. 어느 tier가 맞을지 모르겠으면 성능 테스트를 돌리고 패널의 **"추천대로 체크"** → **저장**을 누르세요.
- **성능 테스트** — 두 가지입니다. 모델을 메모리에 올리는 첫 호출(예열)은 측정에서 빼고 "첫 로드 N초"로 따로 보이며, 같은 질문 3회의 중앙값을 씁니다.
  - **빠른 측정**(로컬 약 10~30초): **생성 속도(tok/s, 생각 토큰 포함)**·응답 시간. 생각 기능이 있는 모델은 **생각 끔**일 때 시간도 함께 잽니다. 추천은 출력 1,500토큰을 만드는 시간 기준으로 표준(1분 안)·정밀·신속(3분 안)만 — 느리다고 심층추론을 추천하지 않습니다.
  - **전체 점검**(로컬 약 30초~2분): 빠른 측정에 더해 규칙으로 판정하는 능력 점검 배지 — **도구 호출**(가짜 조회 도구를 실제로 부르고 결과를 옮기는지), **JSON 형식**, **수치 보존**(연봉·날짜·경력을 그대로 옮기는지), **한국어**(영어 독백·한자 섞임 없음), **생각 끄기**(끔 설정을 지키는지), **긴 문서**(약 7천 토큰을 읽고 내용을 답하는지, 입력 처리 속도). 이 값으로 **단계 1회 예상 시간**(입력 8,000토큰 읽기 + 출력 1,500토큰)을 내고, 표준은 예상 1분 안 + JSON·한국어 통과, 정밀·신속은 3분 안 + 수치·한국어 통과, 심층추론은 생각 기능 + 도구·수치 통과일 때 추천합니다. 실패한 점검은 경고로 보입니다(예: "도구를 쓰는 Agent에 배정하지 마세요").
  - 실측 예(2026-11-27, 이 PC): exaone 7.8B — 생성 27.7 tok/s, 긴 문서 368 tok/s, 단계 예상 76초, 도구 미지원 → 정밀·신속만. Ornith 35B — 생성 44 tok/s(생각 끔 1.5초), 긴 문서 683 tok/s, 단계 예상 46초, 점검 모두 통과 → 세 tier 모두. 예전 방식(짧은 질문 1회 글자/초)은 첫 로드가 섞여 같은 모델이 21.9자/초와 73.2자/초를 오갔습니다.
  - 클라우드 provider는 실제 API 비용이 듭니다(전체 점검은 짧은 호출 약 12건 + 긴 문서 1건). 클라우드의 입력 처리 속도는 벽시계 시간으로 계산한 근사입니다.

<h2 id="integrations">12. 연동·자동화</h2>

### 사람이 누르지 않아도 돌게 하기 — 연동 설정
📍 **메뉴**: 헤더 **⚙ 내 설정**(연동 설정, viewer 제외)

- **정기 실행**(admin·manager) — 이름·파이프라인·할 일 역할·업무 요청 내용·주기(매일 / 평일 / 매주 ○요일)·시각을 정하면, 그 시각마다 업무 요청 → 할 일 → 파이프라인 실행을 자동으로 만듭니다(예: 매주 월요일 09:00 "실적 보고 파이프라인").
  - **만든 사람의 이름으로** 실행되므로 1단계 사람 승인 같은 결재는 직접 실행할 때와 똑같이 거칩니다.
  - 시각은 서버 PC의 현지 시각입니다. `hair serve`로 띄운 서버가 30초마다 확인하므로, 서버가 꺼져 있거나 PC가 잠자기 상태인 동안은 돌지 않습니다. 표의 "끄기"로 잠시 멈출 수 있습니다.
- **이벤트 트리거**(admin·manager) — 시각이 아니라 **일이 생기면** 파이프라인을 시작합니다.
  - 조건: "파이프라인이 끝나면"(어느 파이프라인인지 고름) 또는 "결과물이 승인되면".
  - 동작: 고른 파이프라인을 새 업무 요청·할 일로 시작하면서, 앞 실행의 최종 결과물(또는 승인된 결과물)을 업무 요청 본문에 붙여 넘깁니다(예: 재무 분석 보고가 끝나면 그 결과로 발표자료 파이프라인 시작).
  - 안전장치: 만든 사람 이름으로 실행되고(결재·사람 승인은 그대로), 트리거를 만들거나 다시 켜기 **전에 이미 있던 일로는 실행하지 않으며**, 트리거끼리 서로 부르는 연쇄는 **3단계까지만** 갑니다. 같은 파이프라인이 끝나면 같은 파이프라인을 시작하는 트리거는 만들 수 없습니다.
- **외부 알림**(admin) — Slack·Teams의 수신 웹훅(Incoming Webhook) URL과 받을 일(결재 대기·파이프라인 사람 승인 대기·완료·실패·Agent 실행 실패)을 고르면 일이 생길 때마다 한 번씩 메시지를 보냅니다. 처음 저장할 때 이미 있던 일은 보내지 않습니다. **"테스트 전송"**으로 먼저 연결을 확인하세요.
- **메일 알림**(admin) — 같은 칸의 **"메일로도 받을 사람"**에 주소를 적으면(최대 20명) 같은 일을 메일로도 보냅니다.
  - 메일 서버는 서버를 띄울 때 환경변수로 지정합니다: `HAIR_SMTP_HOST`·`HAIR_SMTP_PORT`·`HAIR_SMTP_USER`·`HAIR_SMTP_PASSWORD`(필요하면 `HAIR_SMTP_FROM`, 465 포트면 `HAIR_SMTP_SSL=1`). 서버 PC에서 `hair init`으로 대화형으로 넣거나, `hair check`로 지금 뭐가 빠졌는지 확인할 수 있습니다. 비밀번호는 화면·DB에 저장하지 않습니다.
  - 환경변수가 없으면 메일은 보내지 않고 웹훅만 동작합니다. "테스트 전송"은 웹훅과 메일을 둘 다 시험합니다.
- **내 API 키**(admin·manager·member) — 외부 시스템(cron·메일 규칙·지라 등)이 **내 계정 권한 그대로** HAIR API를 부를 때 씁니다. 키는 발급 직후 한 번만 보이니 바로 복사해 두고, 요청 헤더에 `Authorization: Bearer 키`로 넣습니다(예: `POST /api/briefs`로 업무 요청 올리기, `POST /api/tasks/{id}/execute-pipeline`으로 파이프라인 시작). 키가 권한을 넓히지는 않으며, 폐기하거나 계정이 비활성화되면 즉시 막힙니다.
- **코드 저장소**(admin) — 서버 PC에 클론해 둔 Git 저장소의 이름·경로를 등록하면, 개발 Agent(코드베이스 분석가·백엔드/프론트엔드/풀스택/데이터·인프라 개발자·코드 검증가·AA — **코드저장소조회** 스킬)가 파일 목록·내용·코드 검색·최근 커밋을 직접 읽고 "경로:줄"을 근거로 답합니다.
  - **읽기 전용이고 커밋된 파일만** 봅니다 — 미커밋 변경, `.gitignore`로 빠진 파일, `.env`·키 같은 비밀 파일은 읽지 않습니다. 최신 코드를 보게 하려면 그 폴더에서 `git pull`을 해 두세요.
  - 대화에서는 "@코드베이스 분석가 shop-api 저장소의 주문 취소 흐름을 설명해 줘"처럼 저장소 이름을 함께 적습니다.
- **사내 DB**(admin) — 업무 DB(SQLite 파일·PostgreSQL·MySQL)를 등록하면 **사내DB조회** 스킬이 있는 Agent(데이터 분석가·재무 분석가·영업 분석가·실적 보고서 작성자)가 테이블 목록·열 구조를 확인하고 SELECT로 직접 조회해, 조회한 수치를 그대로 근거로 씁니다.
  - **읽기 전용**: SQL 검사(한 문장, SELECT·WITH·EXPLAIN만, 쓰기·DDL 거부)와 읽기 전용 연결 두 겹으로 막습니다. 한 번에 돌려주는 행 수(연결별, 기본 200)와 실행 시간(10초)에 상한이 있습니다. 가능하면 **조회 전용 DB 계정**을 쓰세요.
  - **비밀번호는 저장하지 않습니다** — 서버 PC 환경변수에 넣고 그 **이름**(예: `HAIR_DB_SALES_PASSWORD`)만 적습니다. PostgreSQL·MySQL은 서버에 `pip install "hair-platform[dbconnect]"`가 필요합니다. 등록 뒤 **"연결 확인"**으로 테이블이 보이는지 확인하세요.
  - **기록**: 조회마다 요청한 사람·연결·SQL·행 수가 "활동 기록"의 `data_query_executed`로 남습니다. 다른 Agent에게도 쓰게 하려면 "AI 에이전트 관리"에서 **사내DB조회** 스킬을 붙이세요.
- **메일 수신함**(admin) — 공용 업무 메일함(IMAP: Gmail·Microsoft 365·사내 메일 서버)을 등록하면 **메일수신함조회** 스킬이 있는 Agent(고객지원 상담원·영업 제안 작성자)가 최근 메일을 검색하고 본문을 읽어 문의 요약·회신 초안·업무 정리에 씁니다.
  - **읽기 전용**: 보내기·지우기·이동을 하지 않고 **읽음 표시도 바꾸지 않습니다**. 첨부는 이름·크기만 봅니다. 회신은 결과물(초안)로만 만듭니다.
  - **공개 범위**: 메일함마다 누구의 요청일 때 읽을지 정합니다(admin만·manager 이상·모든 사람 — 기본 admin만). 요청한 사람을 알 수 없는 실행에서는 읽지 않습니다.
  - **비밀번호**: 메일 서비스의 **앱 비밀번호**를 서버 PC 환경변수에 넣고 그 이름만 적습니다. 등록 뒤 **"연결 확인"**으로 접속을 확인하세요. 조회마다 활동 기록 `mail_inbox_read`가 남습니다.
- **연결 상태**(admin) — 사내 DB·메일 수신함·캘린더 표의 **"마지막 확인"** 칸에 마지막으로 연결을 연 결과(✓ 시각 / 실패 — 사유는 마우스를 올리면)가 보입니다. "연결 확인" 버튼뿐 아니라 **Agent가 실제로 조회할 때**도 기록하므로, 비밀번호 환경변수가 비었거나 서버 주소가 바뀌면 홈의 **관리 점검**에 "연결 실패"로 뜹니다(SQL을 틀린 것처럼 연결과 무관한 실패는 세지 않음). 한 번도 확인하지 않은 연결도 관리 점검에 안내됩니다.
- **캘린더**(admin) — 업무 캘린더의 **iCal(ICS) 주소**(Google 캘린더 "비공개 iCal 주소", Outlook "게시된 캘린더" ICS 링크, 그룹웨어 ICS 내보내기) 또는 서버의 `.ics` 파일을 등록하면 **캘린더조회** 스킬이 있는 Agent(PM·개발 계획 수립가·실적 보고서 작성자)가 기간 안의 일정을 읽어 회의 준비·주간 보고·일정 충돌 확인에 씁니다.
  - **읽기 전용**이고 반복 일정은 펼쳐서, 빠진 회차·옮긴 회차·취소 일정까지 반영해 보여 줍니다. **공개 범위**는 메일 수신함과 같습니다(기본 admin만).
  - 비공개 iCal 주소는 그 자체가 비밀 키라 **저장하지 않습니다** — 서버 PC 환경변수에 넣고 그 이름만 적습니다(https만). 시간대는 `HAIR_TIMEZONE`(예: `Asia/Seoul`), 없으면 서버 PC 시간대. 조회마다 활동 기록 `calendar_read`가 남습니다.
- **결과물을 저장소에 커밋**(admin) — 결재를 마친 결과물 카드의 **"저장소에 커밋"** → 저장소 선택 → **미리보기**를 누르면 쓸 파일(새 파일·수정)과 점검 결과가 나옵니다.
  - 코드 블록 중 **경로가 적힌 것만** 씁니다(블록 첫 줄 `# src/app.py` 또는 블록 바로 위 줄 `` `src/app.py` ``). 경로 없는 블록은 쓰지 않고 알려 줍니다.
  - 점검(결재 완료·저장소가 main/master 브랜치·미커밋 변경 없음·저장소 안 경로·비밀/무시 파일 아님·Python 문법·이 결과물의 테스트 실행 기록이 실패가 아님)을 **모두 통과해야** 커밋 버튼 두 개가 생깁니다. 누르면 서버가 한 번 더 점검합니다(작성자 "HAIR-Platform", 메시지에 결과물·업무 번호와 실행한 admin 아이디).
  - **"브랜치에 올려 PR 만들기"**(권장): main에서 새 브랜치 `hair/deliverable-<번호>`를 만들어 커밋하고 `origin`에 **push**합니다. 원격이 GitHub이고 서버에 `HAIR_GITHUB_TOKEN`(저장소 Contents·Pull requests 쓰기 권한)이 있으면 **PR을 자동으로 열고** 링크를 보여 줍니다. 토큰이 없으면 "여기서 PR 만들기" 링크를 드립니다. main은 그대로 두고, 저장소는 다시 main 브랜치로 돌아갑니다. push가 실패하면(원격 없음·권한 없음) 브랜치는 로컬에 남기고 이유를 알려 줍니다.
  - **"main에 바로 커밋"**: main 브랜치에 로컬 커밋만 합니다(push 없음).
  - 커밋 중 pre-commit 훅 등이 실패하면 쓴 파일을 되돌립니다(PR 방식이면 만든 브랜치도 지우고 main으로 돌아감). push에는 서버 PC의 git 인증(SSH 키·자격 증명)을 그대로 씁니다.

<h2 id="ops">13. 서버 운영</h2>

서버 PC와 플랫폼 전체를 관리하는 admin을 위한 절입니다. 화면에서 하는 일(시스템 상태·사용자·한도)과 서버 PC에서 하는 일(`hair` 명령·환경변수)을 함께 다룹니다.

### 시스템 상태

📍 **메뉴**: 설정 → 운영 관리 → **시스템 상태** 🔒

서버·데이터·실행·연결 상태를 한 화면에서 봅니다. 이 화면에 있는 동안 30초마다 다시 확인하며, 맨 위에 "모두 정상 / 확인할 것이 있습니다 / 문제가 있습니다"가 보입니다.

| 항목 | 보는 것 | ⚠·✗이면 |
|---|---|---|
| 서버 | HAIR 버전·켜진 시간·Python | — |
| 데이터베이스 | 무결성 점검·크기(쓰기 대기 포함) | ✗면 백업에서 복원 검토 |
| 백업 | 마지막 백업 시각·크기·자동 백업 여부 | 백업이 없거나 이틀 넘게 새 백업이 없음 — 아래 "백업과 복원" |
| 디스크 여유 | DB가 있는 디스크의 남은 공간 | 2GB 미만 — 오래된 기록·업로드 정리 또는 디스크 확장 |
| 작업 큐 | 실행 방식(웹 서버 안 / 작업 프로세스)·실행 중·대기·실패 수 | 작업 프로세스가 꺼짐·10분 넘게 대기 |
| 모델 대기 | 같은 모델 호출이 줄 서 있는 수 | 모델 레지스트리의 "동시 실행 상한" 검토(11절) |
| 기본 AI 모델 · 로컬 모델 서버(Ollama) | 지금 쓰는 기본 모델, Ollama 연결과 모델 수 | ✗면 서버 PC에서 Ollama가 켜져 있는지 확인 |
| 외부 연결 · 기본 구성 | 사내 DB·메일·캘린더 연결 결과, 기본 구성과 다른 곳 | 연동 설정·사용자 관리의 "기본 구성 점검" |

**바깥 감시 도구용 주소** — 가동 모니터링(예: 업타임 감시)은 로그인 없이 `GET /health`를 부르면 됩니다. DB를 읽을 수 있으면 200(`status`: ok·degraded), 읽을 수 없으면 503을 돌려주며, 경로·모델 이름 같은 내부 정보는 넣지 않습니다.

### 사용자·보안 관리

📍 **메뉴**: 설정 → 운영 관리 → **사용자 관리** 🔒

- **계정 만들기**: 아이디·비밀번호·유형(admin·manager·member·viewer)·사번. 첫 admin만 서버 PC에서 `hair bootstrap-admin -u <계정> -p <비밀번호>`로 만듭니다.
- **상사 지정**: 배정 결재가 조직도의 상사 순서대로 올라갑니다. 상사가 없으면 승인자 미지정 1단계 결재가 됩니다(admin·manager 누구나 처리).
- **비밀번호 재설정**: 비밀번호는 암호화돼 있어 조회할 수 없고 새로 지정만 합니다(새 비밀번호는 별도 채널로 전달). 재설정하면 그 계정의 **로그인 잠금도 풀리고, 다른 곳의 로그인은 모두 끊깁니다**. 사용자는 헤더의 내 계정 이름으로 직접 바꿀 수도 있습니다(1절).
- **계정 상태**: 지우지 않고 **비활성화**합니다(활동·배정 기록이 이 계정을 가리키므로). 비활성화하면 즉시 로그인이 막히고 기존 로그인도 끊깁니다.
- **로그인 보호**: 같은 아이디로 5번 틀리면 그 아이디를, 한 접속 주소에서 여러 아이디로 20번 틀리면 그 주소를 **15분** 막습니다(막힌 동안은 맞는 비밀번호도 거절). 처음 막힐 때 활동 기록에 `login_locked`가 남습니다. 서버를 다시 켜면 잠금이 풀립니다.
- **조직 정책**: 사번 형식, **결과물 언어**(모든 Agent가 이 언어로 씀 — 한국어가 아니면 한국어 전용 자동 교정은 꺼짐).
- **기본 구성 점검**: 새 버전에서 추가·변경된 기본 파이프라인·Agent 스킬·도구가 지금 데이터와 다른 곳을 보여 주고, 체크한 항목만 반영합니다(14절 "업그레이드한 뒤…").
- 사내망에서 여러 명이 접속하게 띄울 때는 세션 서명 키(`HAIR_PLATFORM_SECRET_KEY`)가 필수입니다 — 아래 "서버 PC 환경 설정".

### AI 사용 한도

📍 **메뉴**: 현황 → 비용 → 맨 위 **"AI 사용 한도"** 🔒

- **사용자별 한 달 한도**와 **조직 전체 한 달 한도**(USD), 경고 비율, viewer의 AI 호출 허용 여부를 정합니다. 기본은 제한 없음입니다.
- 비용은 이번 달(UTC 1일부터) 토큰 × "모델 레지스트리" 단가로 계산합니다. **단가를 등록하지 않은 모델(로컬 Ollama 등)은 0으로 셉니다** — 한도를 쓰려면 클라우드 모델 단가를 먼저 등록하세요(11절).
- admin은 사용자별 한도에서 빠지고 조직 전체 한도만 적용됩니다. 한도에 닿으면 그 실행은 AI를 부르지 않고 멈춥니다(비용 없음, 8절).

### 작업 프로세스 — 웹 서버를 재시작해도 실행 유지

기본(`embedded`)은 웹 서버가 AI 실행을 직접 돌려, `hair serve`를 재시작하면 실행 중이던 파이프라인·Agent 실행이 "중단됨"이 됩니다(화면에서 "이어서 실행" 가능).

1. `.env`에 `HAIR_WORKER_MODE=external`을 넣습니다(`hair init`의 "서버 운영"에서 `external` 입력).
2. 같은 폴더에서 터미널 두 개로 `hair serve`와 `hair worker`를 함께 띄웁니다 — **같은 `--db-path`**, 작업 프로세스는 **하나만**(두 번째는 시작을 거부).
3. 이제 웹 서버를 재시작해도 실행 중인 파이프라인·Agent 실행은 작업 프로세스에서 계속 돕니다. 작업 프로세스를 재시작하면 그때 실행 중이던 것만 "중단됨"이 되고 화면에서 "이어서 실행"할 수 있습니다.
4. 작업 프로세스는 자리 하나를 늘 대화 응답용으로 남겨 두고, 작업마다 자기 DB 연결로 실행합니다.
5. 작업 프로세스가 꺼져 있으면 AI 실행이 시작되지 않고 쌓입니다 — 홈의 **관리 점검**·시스템 상태·`hair check --db-path`에 경고가 뜹니다.

### 백업과 복원(`hair backup`·`hair restore`)
- **자동 백업**: `hair serve`가 켜져 있으면 하루에 한 번 백업을 뜨고 최근 7개(`HAIR_BACKUP_KEEP`)만 남깁니다. 저장 위치는 `HAIR_BACKUP_DIR`(비우면 DB 파일 옆 `backups/` 폴더) — 디스크 고장에 대비해 다른 디스크나 NAS를 권장합니다.
- **확인**: 설정 → 운영 관리 → **시스템 상태** 🔒의 "백업" 줄에 마지막 백업 시각이 보이고, 이틀 넘게 새 백업이 없으면 ⚠로 알립니다.
- **직접 뜨기**: 서버 PC에서 `hair backup`(서버가 켜져 있어도 됨). 목록은 `hair backup --list`.
- **되돌리기**: `hair serve`·`hair worker`를 끄고 `hair restore <백업 파일>`. 지금 데이터는 지우지 않고 `hair.db.before-restore-<시각>`으로 옆에 남겨 둡니다.
- 백업 하나에는 DB 전체(업무·대화·결과물·업로드 문서·평가 리포트)와 지식 베이스 검색 색인이 들어 있습니다. DB 파일을 그냥 복사하면 최근 변경이 빠질 수 있으니 이 명령을 쓰세요.

### 데이터 초기화(`hair reset-data`)
`hair reset-data`는 서버 PC에서 실행하는 명령입니다. 지우기 전에 **백업을 먼저 자동으로 뜨므로**(위 "백업과 복원"), 잘못 실행했으면 `hair restore`로 되돌릴 수 있습니다.

**초기화한 뒤 할 일**

2. 모델 레지스트리가 비었으니 쓰던 모델을 다시 등록합니다.

**초기화한 뒤 팀이 사라졌다**

- **원인**: 팀은 초기화 대상입니다.
- **해결**: "팀 관리"에서 다시 등록하세요. 앞으로 남겨야 하는 팀은 팀 카드의 **"초기화 시 보호"**를 켜 두면 초기화해도 유지됩니다.

**초기화한 뒤 팀이 사라졌다**

- **원인**: 팀은 초기화 대상입니다.
- **해결**: "팀 관리"에서 다시 등록하세요. 앞으로 남겨야 하는 팀은 팀 카드의 **"초기화 시 보호"**를 켜 두면 초기화해도 유지됩니다.

### 서버 PC 환경 설정(admin) — `hair init`·`hair check`·환경변수
API 키·메일 서버·작업 방식처럼 **화면이 아니라 서버 PC에서 정하는 값**은 환경변수로 둡니다. 서버를 띄우는 폴더의 `.env` 파일에 `이름=값` 한 줄씩 적으면 되고, 직접 고치는 대신 아래 명령을 쓰면 편합니다. 값을 바꾼 뒤에는 **`hair serve`(작업 프로세스를 쓰면 `hair worker`도) 재시작**이 필요합니다.

| 명령 | 하는 일 |
|---|---|
| `hair init` | 항목을 하나씩 물어 `.env`에 저장합니다. Enter는 지금 값 유지, 메일 알림·고급 옵션은 원할 때만 묻습니다. `.env`에 직접 추가한 줄(연동 비밀값 등)은 그대로 둡니다 |
| `hair check` | 실제로 적용될 값을 보여 주고(비밀값은 가림) 흔한 실수를 찾습니다 — API 키와 provider 불일치, SMTP 누락, 잘못된 값(작업 방식·시간대·0/1·숫자) |
| `hair check --db-path hair.db` | 위 내용 + 연동 설정에 등록한 연결이 쓰는 **비밀 환경변수가 채워졌는지**와, 작업 프로세스 모드일 때 **`hair worker`가 떠 있는지** |
| `hair init --help` | 묻는 항목 전체 목록 |

| 그룹 | 환경변수 | 언제 필요한가 |
|---|---|---|

| 저장소 PR | `HAIR_GITHUB_TOKEN` | 결과물을 브랜치로 올린 뒤 PR을 자동으로 열 때 |

| 백업 | `HAIR_BACKUP_DIR`·`HAIR_BACKUP_KEEP` | 백업 저장 폴더(다른 디스크·NAS 권장)·자동 백업 보관 개수(0이면 끔) — 위 "백업과 복원" |

**연동 비밀값 — 이름은 연동 설정 화면에서 정합니다**

사내 DB·메일 수신함·캘린더를 등록할 때 비밀번호·iCal 주소 대신 **환경변수 이름**(대문자·숫자·`_`)을 적습니다. 그 이름으로 서버 PC의 `.env`에 값을 넣으세요.

| 연결 | 등록할 때 적는 것 | `.env`에 넣는 줄(예) |
|---|---|---|
| 사내 DB(PostgreSQL·MySQL) | 비밀번호 환경변수 이름 | `HAIR_DB_SALES_PASSWORD=조회전용계정비밀번호` |
| 메일 수신함 | 앱 비밀번호 환경변수 이름 | `HAIR_MAIL_SUPPORT_PASSWORD=앱비밀번호` |
| 캘린더 | iCal 주소 환경변수 이름 | `HAIR_CAL_SALES_URL=https://...basic.ics` |

- 연동 설정 화면의 표에 **✓**(값 있음) 또는 **⚠ 비어 있음**이 보입니다. 값을 넣은 뒤 `hair serve`를 재시작하고 **"연결 확인"**을 누르세요.
- 작업 프로세스(`hair worker`)도 같은 `.env`를 읽어야 하므로 **같은 폴더에서 실행**합니다.

<h2 id="trouble-ops">14. 자주 겪는 문제 — 운영자</h2>

서버·설정·관리 화면에서 생기는 문제입니다. 사용자 화면의 문제는 8절에 있습니다.

### Agent·팀 만들기와 배정

**방금 만든 Agent가 배정 후보·실행 목록에 없다**

- **원인**: 새로 만든 Agent는 "온보딩 대기" 상태로 시작합니다.
- **해결**: "AI 에이전트 관리"에서 그 Agent의 **"온보딩 승인"**(온보딩 대기 → 활성)을 누릅니다. **admin만** 누를 수 있으니 manager라면 admin에게 요청하세요.

**"AI 에이전트 생성"에서 새 Agent가 아니라 "재사용" 배지만 뜬다**

- **원인**: 같은 할 일(역할)에 이미 Agent가 있어서 그것을 다시 쓴 것입니다. 오류가 아니라 의도된 동작입니다.
- **해결**: 새 Agent가 필요하면 다른 할 일을 골라 만드세요.

**Task ID·Brief ID를 넣어 만든 팀(TF팀)이 멘션·배정 후보에 없다**

- **원인**: TF팀은 "온보딩 대기" 상태로 시작합니다.
- **해결**: "팀 관리"에서 그 팀 카드의 **"온보딩 시작"**을 누르면 활성이 됩니다.

**팀 "기본값 저장"에서 "신규로 hierarchical 모드를 지정할 수 없습니다" 오류가 난다**

- **원인**: 위임형(hierarchical — 매니저가 팀원에게 일을 나눠 위임)은 실측에서 실제로 위임하지 않고 끝나는 경우가 반복돼 새로 지정할 수 없게 막아 두었습니다(9절 "방법 A" 3번).
- **해결**:
  1. 처리 방식을 sequential(순서대로 이어받기)로 둡니다.
  2. 여러 단계가 필요한 업무라면 팀에 **파이프라인을 연결**합니다(9절 "방법 A" 6번).
  3. "멤버 추가" 때 같은 오류가 나면 역할 라벨에서 "매니저"라는 말을 빼세요("리드"·"PM" 등은 됩니다).

**"조직도"와 "팀 관리"의 TF팀이 같은 것인가?**

- **답**: 다릅니다.
  - **조직도**: 확정된 배정을 모아 보여 주는 **읽기 전용 화면**입니다. 여기서 만들거나 지울 수 없습니다.
  - **TF팀**: "팀 관리"에서 **직접 만들고 활성화·해체하는 실제 조직**입니다.

**업그레이드한 뒤 기본 파이프라인·Agent 구성이 이 가이드와 다르다**(예: 사업/기획 파이프라인 2단계에 데이터 분석가가 없음)

- **원인**: 새 버전에서 추가·변경된 기본 구성은 이미 쓰던 데이터에 자동으로 들어가지 않습니다.
- **해결**:
  1. 설정 → 운영 관리 → **"사용자 관리"**(admin)를 엽니다.
  2. **"기본 구성 점검"**에서 빠진 항목(단계 참여 역할·단계 모드 업그레이드·Agent 기본 스킬·스킬·도구)을 체크합니다.
  3. **"선택한 항목 반영"**을 누릅니다.
- **참고**: admin이 일부러 바꾼 값(모드·판정 기준·사람 승인)은 차이만 보여 주고 덮어쓰지 않습니다. 홈의 "관리 점검"에 "기본 구성과 다른 곳 N건"이 보이면 같은 내용입니다.

### 삭제가 안 될 때
삭제가 막히면 **아무것도 지워지지 않은 상태로 되돌려지고**, 화면 위 메시지에 막은 이유가 나옵니다.

**업무 요청·할 일이 안 지워진다**

- **"확정된 배정이 있어 삭제할 수 없습니다(할 일 「…」 ← …)"가 나올 때**
  - **원인**: 메시지에 적힌 할 일에 확정(confirmed) 배정이 남아 있습니다. 확정 배정은 조직도·비용·성과에 반영돼 있어 보호합니다.
  - **해결**: 할 일 상세의 **"배정 취소"**(admin·manager)로 그 배정을 먼저 정리한 뒤 다시 지우세요.
- **"연결된 데이터가 남아 있어 삭제할 수 없습니다: …"가 나올 때**
  - **원인**: 삭제 기능이 아직 모르는 연결 데이터가 할 일을 가리키고 있습니다.
  - **해결**: 메시지에 나온 데이터 이름을 관리자(개발 담당)에게 알려 주세요.
- **함께 처리되는 것**: 할 일을 지우면 배정·결과물·실행 기록·참여자·선행 관계·Crew 실행 기록이 함께 지워집니다. **할 일에 연결된 대화는 지우지 않고** 연결만 끊어 독립 대화로 남깁니다(대화 내용은 보존).

**팀이 안 지워진다**

- **원인**: 그 팀에 확정 배정이 남아 있습니다.
- **해결**: 할 일 상세의 "배정 취소"로 먼저 정리하세요.

### 실행이 느리거나 실패할 때

**팀·파이프라인 실행이 오래 걸리거나 실패한다**

- **원인**: 참여 Agent가 많을수록(특히 순차 릴레이·계획 분담) 모델 호출이 늘어납니다. 로컬(Ollama) 대형 모델은 호출 한 번에 수십 초~몇 분이 걸립니다.
- **이미 적용돼 있는 것**: 로컬 모델에서는 **작업 전 계획(추론 모드)을 자동으로 끄고, 도구 반복 상한 기본값을 8회**로 둡니다(파인튜닝에서 `max_iter`를 직접 정한 Agent와 위임형 팀은 그 값을 씀). 실측: 예전 기본 설정(계획 2회 + 반복 16회)으로는 로컬 35B 모델의 조사 단계 하나가 1시간 50분·호출 92회에도 끝나지 않았고, 지금 설정으로는 24분·호출 4회에 끝났습니다. 클라우드 모델은 Agent 설정 그대로 계획을 씁니다.
- **해결**:
  1. 로컬 모델에서도 계획을 쓰고 싶으면 서버를 `HAIR_OLLAMA_AGENT_PLANNING=1`로 띄웁니다(느려짐).
  2. **로컬 추론형 모델(Ollama)은 "추론 모드"가 가장 큰 차이를 냅니다** — "AI 에이전트 관리"의 파인튜닝에서 **추론 모드(reasoning)를 끄면** 그 Agent의 호출이 사고 과정 없이 바로 답합니다(2026-11-26 실측, 35B 모델: 채용 공고 파이프라인 34분 → 8분, 토큰 9.7만 → 5.3만, 공고 품질 점검 결과는 같음). **기본 제공 Agent 중 요구사항 정리·검토 역할(업무 요구사항 분석가·요구사항 분석가·문서 검토자·재무 검토자)은 기본으로 추론을 끕니다**(2026-11-26 — 이미 설치된 서버도 admin이 바꾸지 않은 경우 다음 기동 때 한 번 맞춤). 본 결과물을 쓰는 역할(보고서·제안서·계약서 검토자·코드 검증가 등)은 그대로 둡니다. 지정하지 않은 Agent는 모델 기본값(생각 켬)이고, 언어 교정·요구사항 추적성 판정 같은 짧은 내부 채점은 항상 생각을 끕니다. 먼저 "⚡ 최적화 추천"을 써 봐도 됩니다.
  3. 실행 실패는 **"인박스"**에서 확인합니다. 로컬 모델 타임아웃은 Crew·파이프라인 기준 5,400초로 길게 잡혀 있지만, 35B급 모델은 한 단계에 수십 분이 걸릴 수 있습니다.
  4. **서버 PC가 잠자기에 들어가면 로컬 생성도 멈춥니다.** 긴 실행 중에는 잠자기를 꺼 두세요.

**대화 응답·실행이 "실행 중"인데 전혀 시작되지 않는다**

- **원인**: 서버가 `HAIR_WORKER_MODE=external`(작업 프로세스 모드)로 떠 있는데 `hair worker`가 꺼져 있습니다 — 웹 서버는 작업을 기록만 하고 실행은 작업 프로세스가 합니다.
- **확인**: 홈의 **관리 점검**(admin)이나 서버 PC에서 `hair check --db-path hair.db`에 "작업 프로세스가 실행되고 있지 않습니다" 경고가 보입니다.
- **해결**: 같은 폴더에서 `hair worker --db-path <hair serve와 같은 DB>`를 띄우면 쌓인 작업부터 실행합니다. 작업 프로세스를 쓰지 않으려면 `.env`에서 `HAIR_WORKER_MODE`를 지우고(또는 `embedded`) `hair serve`를 재시작하세요.

**긴 결과물(발표자료 덱·단일 파일 앱)이 중간에 잘린다**

- **원인**: 모델의 컨텍스트 창이 작아 앞 내용과 생성 중인 글이 다 들어가지 못했습니다.
- **해결**: "모델 레지스트리"(admin)에서 그 모델의 **컨텍스트 한도**를 늘리세요. Ollama는 이 값이 실제 컨텍스트 창이 되며, 크게 잡을수록 메모리를 더 씁니다.

**"LLM 연동을 쓰려면 provider를 명시하거나 ANTHROPIC_API_KEY 또는 OPENAI_API_KEY 환경변수가 필요합니다" 오류가 난다**

- **원인**: 어느 AI 모델을 쓸지 정해지지 않았습니다 — 클라우드 API 키도 없고, provider도 지정되지 않았습니다.
- **해결**(서버 PC에서, admin이 합니다 — manager·member라면 admin에게 요청):
  1. `hair check`로 어떤 환경변수가 비어 있는지 확인합니다.
  2. `hair init`으로 필요한 값을 채웁니다.
  3. 로컬 Ollama만 쓰려면 provider를 **명시적으로 "ollama"**로 지정해야 합니다(API 키처럼 자동으로 판별되지 않음).

### 결과물·평가·지식

**결과물이 한국어가 아닌 언어로 나와야 한다**

- **해결**: 설정 → 운영 관리 → **"사용자 관리"**(admin)의 조직 정책에서 **결과물 언어**를 바꿉니다. 모든 Agent에 그 언어로 쓰라고 지시합니다.
- **참고**: 한국어가 아닌 언어로 바꾸면 한국어 전용 자동 교정(한자·외국 문자 교정, 낱말확인)은 꺼집니다.

**"⚠ 낱말 확인" 배지가 아예 안 보인다**

- **원인**: 서버에 `korean` 확장(`pip install "hair-platform[korean]"`)이 없거나 `HAIR_LEXICON_CHECK=0`으로 꺼져 있습니다.
- **참고**: 분석기가 메모리를 약 360MB 쓰므로, 로컬 대형 모델과 메모리가 빠듯하면 꺼 두는 편이 낫습니다.

**"응답 시간"(Gate D)이 늘 미달이다(로컬 모델)**

- **원인**: 로컬 대형 모델은 호출 한 번에 수십 초~몇 분이 걸려 기본 응답 시간 SLA(p95 30초)를 넘습니다.
- **해결**: 설정 → 운영 관리 → **"평가 기준"**(admin)에서 둘 중 하나를 합니다(10절 "평가 기준 설정").
  1. **"모델·파이프라인별 덮어쓰기"**에 "모델: 로컬(Ollama)" 행을 추가하고 D를 0으로 — 로컬 모델 실행만 기준을 낮춥니다(클라우드와 함께 쓸 때 권장).
  2. 응답 시간 SLA를 실제 응답 시간에 맞게 늘립니다(모든 모델에 적용).

**지식 검색(내부지식검색)이 느리다 · 등록한 자료가 검색되지 않는다**

- **원인**: 지식 베이스 검색은 서버에 `vectordb` 확장(ChromaDB)이 있으면 벡터 DB로, 없으면 저장된 모든 자료와 하나씩 비교하는 방식으로 합니다. 하나씩 비교하는 방식은 자료가 많을수록 느려집니다(청크 1만 개에서 약 1.7초, 벡터 DB는 약 0.04초).
- **해결**:
  1. 설정 → 지식·데이터 → **"지식 베이스"** 화면 통계 줄의 **검색 엔진**이 `chroma`인지 확인합니다. `sqlite`라면 서버 PC에서 `pip install "hair-platform[vectordb]"`를 실행하고 `hair serve`를 재시작하세요.
  2. 처음 벡터 DB로 바꾼 뒤 첫 검색은 기존 자료를 옮기느라 몇 초 더 걸립니다(한 번만, 비용 없음).
  3. 등록한 자료가 계속 안 나오면 서버 PC에서 `hair reindex-vectors`를 실행합니다. SQLite에 저장된 임베딩으로 색인을 다시 맞추므로 **AI 비용이 들지 않습니다**.
- **참고**: 검색 결과는 **같은 임베딩 모델로 등록한 자료만** 비교합니다. 임베딩 모델을 바꾸면 그전에 등록한 자료는 다시 등록해야 검색됩니다.
