# rbac-permission-audit

v0~v4 개발 중 5개 버전 전부에서 독립적으로 같은 모양의 테스트를 반복 작성했다
(원칙4: 3회+ 반복 확인 후 스킬화 — 이번에 그 기준을 채웠다):

- v0 GC1: 뷰어는 F1(브리프 제출) 불가 → 403, Admin은 가능 → 201
- v1 GC9·GC10: 팀원은 F2/F6(Task 분해·매칭 실행) 불가, 매니저는 가능
- v2 GC12·GC14: 팀원은 F6(배정 요청) 불가, self-approval도 별도로 403
- v3 다수: F4(생성)·F9(온보딩)·F13(감사로그) 각각 역할별 경계
- v4 GC30·GC32·GC34: 동의 설정은 본인/Admin만, 성과리뷰·비용조회는 역할별 범위 다름

증상은 매번 같았다: "이 엔드포인트, RBAC 매트릭스대로 실제로 잠겨 있나?"
코드 리뷰만으로는 `require_role(...)` 데코레이터를 빼먹거나 매트릭스와 다른
role 조합을 실수로 넣는 걸 놓치기 쉽다 — 반드시 실행되는 테스트로 확인한다.

## 언제 발동하는가

- 새 API 엔드포인트를 추가할 때(그 엔드포인트가 쓰기 액션이면 특히)
- `docs/ADR.md` 결정 3(RBAC 권한 매트릭스)을 개정했을 때
- "이 권한 설정이 맞는지 모르겠다"는 의심이 들 때

## 절차

1. `docs/ADR.md` 결정 3 표에서 대상 엔드포인트(F-item)의 허용 role을 확인한다.
2. `tests/unit/conftest.py`의 `client_and_conn` 픽스처가 이미 시드한 4계정을
   그대로 쓴다(admin1/manager1/member1/viewer1) — 새 역할 계정을 임시로 만들지
   않는다. 단, 매니저 체인(F7 다단계 결재)이 필요한 케이스는 `create_user()`로
   추가 계정을 만들고 `users.manager_id`를 직접 연결한다(`test_gc25` 참고).
3. 각 엔드포인트마다 최소 2개 케이스를 작성한다(순서 고정):
   - 매트릭스상 **불허**된 최소 role로 로그인 → 시도 → `403` 확인
   - 매트릭스상 **허용**된 최소 role로 로그인 → 시도 → 성공 확인
4. 추가 제약이 있으면(self-approval 방지 — ADR 3-A, 본인/Admin만 — F8 동의)
   별도 케이스로 검증한다. "권한은 있지만 이 특정 리소스에 대해서는 안 된다"는
   경우를 일반 RBAC 체크와 섞지 않는다.
5. `pytest tests/ -q`로 전체 스위트를 돌려 회귀가 없는지 확인한다.

## 아직 스킬화하지 않은 후보 (SPEC.md §8, 3회+ 기준 미충족)

- `human-agent-assignment-check` — Assignment Engine 매칭 로직은 v1에서
  한 번 구축한 뒤 반복 재검증한 적이 없다.
- `org-chart-sync` — F5/F6 assignments 공유 정합성도 v2에서 한 번뿐이었다.
- `async-job-status-ui` — Job Queue 상태머신 패턴도 v3 한 번.

원칙4에 따라 실제로 3회+ 반복될 때까지 스킬화를 미룬다(억지로 미리 만들지
않는다) — `docs/LIMITS.md`에도 같은 판단을 기록해뒀다.
